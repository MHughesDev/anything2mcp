# Hypotheses

The design is a set of bets. This register lists the ones that matter most: what the design assumes, what else could be true, and how to find out. Testing these, and adding to them, is how the design gets better as the system is built.

## How to use the register

- **Before a slice,** find the hypotheses it can test. [Core first](../plan/roadmap.md) names them per slice.
- **While working,** add a hypothesis whenever something in the documents is assumed and not known, or a different design looks plausible.
- **After a test,** write the result as a file in this folder named for the hypothesis, such as `H-01-result.md`, using the [template](TEMPLATE.md). Set the status here. If a decision changes, add a decision record.
- A hypothesis is never deleted. A refuted one is the most useful kind.

**Status:** `open`, `supported`, `refuted`, or `changed` when the test led to a different design. The cell holds one of those words and nothing else, because the audit reads it; a status other than `open` needs a result file, and is given only on a named test and its result or on a measured number, never on a reading of the code. A bet of which a test or a number has settled a stated part is `partly`: its result file names the part, the test or record, and what is missing. Until the audit accepts that word the cell of such a bet stays `open`, and its result file's status line says `partly` ([decision 0451](../decisions/0451-a-bet-is-settled-only-by-a-named-test-or-a-measured-number-and-a-part-settled-is-marked-partly.md)); they are H-04, H-06, H-16, H-20, H-28, H-32, H-39, and H-40.

## Notes on open hypotheses

What the work has shown so far about a hypothesis that is still open. A note is not a result: the result file is written when the test in the register has been run.

- **H-01, 2026-11-17.** Partly supported by the browser spike ([research note 17](../research/17-browser-engine-base.md)): a direct client works, is small, and meets the budgets on Linux. No sidecar was compared, no memory figure was taken, and nothing ran on Windows or macOS.
- **H-01, 2026-11-17, the browser engine as built.** The direct client in `a2m-pack-web-browser` also does input, request interception, and requests made from inside the page, with no outside base library ([decision 0110](../decisions/0110-the-browser-engines-interface-as-building-it-settled-it.md)). Still no sidecar comparison, no long run, and no run on Windows.
- **H-02, 2026-11-17.** In the browser engine's tests, every field and action of the test application's form was found by role and name. Only the status line needed a selector.
- **H-03, 2026-11-17.** Supported on the late-element case, in the same spike. The re-render case was not measured.
- **H-03, 2026-11-17, the browser engine as built.** A late element is noticed by an in-page observer when it arrives, with no polling, and a wait under way survives a navigation: it is re-armed in the new document. No comparison with polling was measured, there was no long run, and Windows has not run it.
- **H-04, 2026-11-17.** The part of the bet that is one renewer is supported in one process and on one store: ten concurrent callers that meet an expired session cause one renewal, also on real threads, in the tests of `a2m-auth`. It is not shown across two processes, and no browser has shared tabs yet.
- **H-04, 2026-11-18, the web sign-in ([decision 0245](../decisions/0245-a-web-application-is-signed-in-to-through-its-own-sign-in-page-with-a-credential-stored-for-the-person.md)).** The design still rests on the bet: the tabs of one session share one browser. What they share changed: it is the browser's in-memory context, made when the browser starts, and holds the session's cookies; it is no longer the profile folder, which holds no cookie or page storage of any page. No test has run parallel tabs and a write on one session yet, so the cross-talk test the register names is still owed, and the status stays open.
- **H-05, 2026-11-18.** Not tested. `form_login` signs in with a credential the person stored, through the application's own sign-in page; it does not sign in through the device's account, so nothing it did bears on this bet.
- **H-05, 2026-11-23.** Not tested. [Research note 35](../research/35-web-sign-in-methods-and-engine-owned-profiles.md), from search summaries only: Chrome on Windows signs in silently through the device's account only in a managed, signed-in profile with the vendor's extension, and a fresh engine-owned data directory has neither. Nothing was found for Edge, macOS, or Linux.

Not shown: a run on Windows or macOS, where the channel has never run, and an engine started on demand. A command that finds no engine still runs one inside itself without the engine lock, so two such commands on a fresh installation can race ([decision 0138](../decisions/0138-the-vault-and-the-session-keeper-after-their-safety-audit.md)).
