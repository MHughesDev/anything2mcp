# Sessions and secrets: a review round, 2026-11-24

The round of package 2.7, by a new lens, lens 18 in the [design review lenses](../plan/design-review-lenses.md): *from the moment a session or a secret is made to the moment it is destroyed, where can it be seen, kept, reused, widened, or left behind: by a person, an agent, a log, a trace, a finding, a recommendation, another target, or a restart?*

It read [spec section 215](../spec/2-kernel/215-sessions-and-the-session-keeper.md) in full and the sign-in parts of [section 503](../spec/5-security/503-approval-and-sign-in-surfaces.md), the designs of [`a2m-auth`](../architecture/crates/a2m-auth.md) and [`a2m-vault`](../architecture/crates/a2m-vault.md), the open lists of [decision 0248](../decisions/0248-a-sign-in-goes-only-where-a-published-version-says-and-a-credential-belongs-to-its-target.md), and the code of the web pack's sign-in (`form_login`, `window_login`, the expiry signs) where a document named it. It changed no code for the review as such; the code in this round's package, auth discovery, was built first, as [decision 0367](../decisions/0367-auth-detect-recommends-a-mode-and-a-provider-by-fixed-rules-and-marks-it-inferred.md) says, and the review looked at what building it showed.

The evidence came first. The proof of the package, `five_signed_in_reads_give_one_trace_signature` (`crates/anything2mcp/tests/sign_in_signature.rs`), runs five identical reads through the product of a service behind a bearer token, the first of which has the session keeper sign in, and compares their trace signatures, their events, and what the traces hold. `crates/anything2mcp/tests/sign_in_detect.rs` runs `auth.detect` against the three sign-in variants of the test application and asks the application afterwards what it was sent.

## What the question found and did not

The secret-facing questions found nothing new that could reach a caller. The password and the session cookie of a signed-in web read, the bearer token of a read behind one, and the stored secrets of both are in no command's output and no file under the engine's home or the project, as the product's earlier tests show, and the recommendation adds nothing a system supplied. Another target's secret could not be named by this target's files, and the vault would not open it under another target (decision 0248, point 3). A sign-in recommendation is never a credential and never a settled method.

The finding the lens turned up most was a different kind from the one it asked for: the documents about sessions had drifted apart from each other (findings 1 to 3), because a package was built across three of them over several weeks and each mark was changed where it was built.

## Returns

The round found most from building: findings 4 and 6 came from the code of auth discovery and a test, and 1 to 3 from reading the rows the build changed. The next gain is more likely from a round with lens 8 (the security reviewer) over the server path, which the sessions-and-secrets lens did not reach, and from running the sign-in classifications on the other two operating systems.
