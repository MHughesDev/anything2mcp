# Field test results

What the product showed when it was run against existing software that the project runs itself ([decision 0293](../decisions/0293-software-we-run-ourselves-is-tested-against-during-the-build-and-may-be-written-to.md)). Each system is described by its kind and never named (rule 9). How a field test is run is in [decision 0295](../decisions/0295-a-field-test-is-run-from-a-recipe-kept-outside-the-repository.md). A finding stays here until a stand holds it as a case and CI passes with it. Since decision 0310 the runner runs the system and the product's binary in containers on a closed network (`--internal`, no published port); the field test 1 results below were got before that, with the system's port published on this machine.

## Field test 1: an HTTP service with a published description, reads only (2026-11-23)

**The system.** A self-hosted application for hosting source code, started from its maker's container image, pinned by digest. It keeps its state in one embedded database file. It publishes a description of several hundred operations in the Swagger 2.0 form. It was given one invented administrator, one repository, and three issues. Its database file was read directly to confirm the three issues before the product was started.

**What was run.** `init`, `target add` with the kind `http`, `scout run` with the description as a file, `lint`, `draft delete`, and `try` on three drafted reads. Nothing was written through the product, and nothing was published. Linux only. The recipe ran three times with the same result.

**What worked.** The target was registered. A description in the OpenAPI 3.0 form was read into 20 findings and 39 drafts. One drafted read, of the system's version, ran and returned the right value. Every failure had a class, a code, and a next step.

**Findings.**

**What this field test does not show.** A write, a sign-in, a publish, a second operating system, or any kind of system but a request service. Findings 1 and 4 were got past by hand, with a conversion of the description and an edit of each draft, so that the later steps could run; the recipe keeps both as steps.

## Field test 2: the same service, one verified write with its answer lost (2026-11-23)

**The system.** The application of field test 1, started the same way, on the runner's closed network ([decision 0310](../decisions/0310-the-field-harness-runs-in-a-closed-network-and-says-in-the-ledger-what-it-is.md)), with the fault proxy between it and the product. Every command of the product ran as a thin client of the field harness, which the runner built into a build folder of its own for each run and deleted after it.

**What was run.** The 23 steps of field test 1, then a write: a second target written by hand, with one surface, one declared test record (one invented issue), a sign-in by `http_basic` from a stored invented password, a read of an issue and a change of its title by `PATCH`, and an offline test of each against a fixture written by hand. `lint`, `secret set`, `test run`, `version publish` carried out by the runner's `person` step on the engine's own page, then `tool call` of the write with the proxy set to cut the answer to that `PATCH` once, the `person` step once with another hash and once with the change's own, and `run resume` twice. Linux only. Three runs, all 60 steps alike in each.

**What it showed.**

- The write rested at `needs_approval`, and nothing was sent to the system before the approval.
- A prompt answered with another hash passed nothing: the page said so, the run still waited, and the system's database still held the old title.
- With the change's short hash, the approval was recorded. The ledger's approval row and the audit log record its presence as `field_harness`, once.
- The first `run resume` sent the write once, lost its answer, and stopped as `possible_commit`, `no_confirmation`, not retry-safe. The second reconciled by reading the record back, found the new title, and completed without sending again. The proxy's record shows one `PATCH`.
- The system's own database holds the new title exactly once, and its own interface, asked directly, answers it.
- The invented password appears in no step's output, report, or harness log.

**Findings.** Got while the recipe was written, by hand; none is in the recipe.

| # | What happened | Why it matters | Where it belongs | State |
| --- | --- | --- | --- | --- |
| 12 | A password of one character was stored and registered with the redactor, which then replaced that letter everywhere in every answer | A short secret ruins every answer and log; no secret of one character is a real one | `a2m-vault` or the redactor in `a2m-telemetry`: a lower bound on a secret's length, or a refusal by name | Fixed in `a2m-vault` by [decision 0338](../decisions/0338-a-secret-a-person-chooses-has-at-least-eight-bytes-and-a-replaced-one-stays-masked.md): a chosen secret under eight bytes is refused with `secret_too_short`, once `a2m-auth`'s `put` calls `Vault::register_chosen` |
| 13 | After that secret was replaced, the offline test of the write still stopped as `input_invalid`, a value it would write holding a registered secret, until the engine was restarted; the cause was not looked into | A replaced value stays a secret for the engine's life, and refuses writes that no longer hold one | The redactor and `secret.set` | Closed as caused by finding 12: the old value was one character, so it matched everywhere. A replaced value of eight bytes or more stays masked for the life of the process, which is intended ([decision 0338](../decisions/0338-a-secret-a-person-chooses-has-at-least-eight-bytes-and-a-replaced-one-stays-masked.md)) |
| 14 | `secret set` with a plain name stores `vault://<name>`, which a target's `auth.yaml` refuses as `credential_of_another_target`; a name of the form `<target>/service/<name>` is taken, though the command's help says only letters, digits, and underscores | A person follows the help and cannot store a credential a target can use | `a2m-actions`, the help of `secret.set` | Fixed on 2026-11-23: the help of `secret.set` states the accepted form (one to four parts joined by `/`, each of lowercase letters, digits, `_`, `-`, and `.`) and that a target's `auth.yaml` takes a secret whose first part is the target's name |
| 15 | A drafted write cannot be tried in the sandbox, so a first write needs an offline test with a fixture written by hand and a publish | Known: `draft.try` says a trial that writes needs the publish gates' test records, which are not built. The cost of the first write is a fixture by hand | Roadmap, the trial of a write on a declared test record | Open |

**What this field test does not show.** A write the system cannot read back, a connection cut before the request, a kill of the engine between intent and act, a sign-in typed on the engine's own page, or a second operating system.

## Field test 3: a database server, reads and one approved write (2026-11-24)

**The system.** A widely used open-source relational database server, started from its maker's container image through a registry mirror, pinned by digest, with no data folder kept after the run. It was given one invented sign-in role, one database, and an invented shop: customers, items, orders, order lines with a key of two columns, a table with no key, and a view. Its own command-line client, run inside its container, confirmed the rows before the product was started and after the write. Its container shares the network of the product's box (`"network": "box"`, a runner option added for this test), because the data pack reaches a server only on the loopback address.

**What was run.** Two recipes. The first, with the product's engine built as it is shipped: `init` and `target add` of each kind of database surface; 8 steps. The second, with the field harness built with the data pack's feature `postgres` (`"harness_features"`, a runner option added for this test, which each report states): a target written by hand, `secret set`, `session login` carried out by the runner's `person` step, `scout run` (first with a role that owns the tables, then with one that owns nothing and holds reads and one column's update), `lint`, five `try` reads; then a second target written by hand with one update statement, its offline tests, `version publish` by the `person` step, `tool call` of the write, the `person` step once with another hash and once with the change's own, `run resume`, and reads of the store straight from its own client; 53 steps. Linux only. Each recipe ran three times with the same result.

**What it showed.**

- The scout read the store's catalog under the signed-in role and drafted 9 files that compile and 3 that wait in the holding folder. Its own trials proved the two drafted lists it could try. The reads tried by hand returned what the store holds: a date, an exact total with its two places, a row found by a key of two columns.
- A role that owns the tables was refused by name, `identity_is_administrator`, before anything was drafted.
- The write rested at `needs_approval`, and nothing reached the store before it. A prompt answered with another hash passed nothing. With the change's hash the run went on, completed, and read the row back; the store's own client shows the new quantity on that row and the old one on every other. The role could not change a column it was not granted, as the store itself says.
- The invented password appears in no step's output and not in the audit log.

**Findings.**

**What this field test does not show.** A link that is encrypted or not on this machine, which the pack does not make; a write whose answer is lost; a guarded update by version; an insert or a delete; a second operating system.

## Field test 4: a folder of office documents, reads and one approved write (2026-11-24)

**The system.** A folder of an imaginary office's documents with invented data, made by the recipe on each run: delimited text with a header row, quotes, and Windows line endings; a JSON document of customer records; a settings file in the INI form; a property list; a growing log; a Markdown note; and a workbook in both the common format and the office suite's own, made by an open-source office suite, headless, from delimited text. No container holds it: the recipe says `"system": {"kind": "folder"}` (a runner option added for this test), and the folder is read straight from the file system to check what the product did.

**What was run.** `init`, `target add` of a `file` surface, `scout run`, `lint`, six `try` reads, then a second target written by hand with a document whose quantity column is writable, its offline tests, `version publish` by the `person` step, `tool call` of an update of one row, the `person` step once with another hash and once with the change's own, `run resume`, and reads of the file from disk; 43 steps. Linux only. Three runs, all alike.

**What it showed.**

- The scout found five documents, a folder, and a growing file, and drafted 13 files that compile and 2 that wait in the holding folder. Its trials proved four reads. The folder's entries, one entry by name, a settings section, a property list's values, and the growing file's lines were read as the files hold them. The settings file's password and the JSON document's `api_key` were left out of every draft.
- The write rested at `needs_approval`, and the file was unchanged until the approval. A prompt answered with another hash passed nothing. After the approval the run completed and read the row back. On disk the one value changed and every other byte stayed, the quotes of the other rows and all four Windows line endings included.

**Findings.**

| # | What happened | Why it matters | Where it belongs | State |
| --- | --- | --- | --- | --- |
| 24 | The drafted list of the delimited text stops at the first empty cell: `output_unexpected`, "has no value, and the output is not declared `may_be_absent`". The scout's own trial of it failed the same way, and its summary counted one failed read | Most delimited text in use has empty cells; the one read drafted over it fails on the first | `a2m-pack-file`, the drafter | Fixed: the list was already built by [decision 0342](../decisions/0342-a-documents-cell-may-be-empty-unless-it-is-a-key-or-declared-required.md), which this run did not yet have; a test of empty cells at the start, middle, and end of a row now holds it ([decision 0346](../decisions/0346-a-drafter-reads-a-sheet-with-no-table-and-types-json-by-its-values-and-a-committing-step-carries-what-it-writes.md)) |
| 25 | The workbook the office suite saved, rows under a header on a sheet with no table object, was drafted as a document with `records: {}` and no read | That is how a person's spreadsheet is saved; its rows are not reached | `a2m-pack-file`, the drafter and the workbook reader | Fixed: a sheet that defines no table is a record kind placed by `sheet`, drafted and listed; tested over a package built in the shape the office suite writes (decision 0399) |
| 26 | The JSON document of records waits in the holding folder with an open question for the type of every field, though the drafter gives every field of the delimited text the type `untrusted_text` and drafts a list of it | Two drafters of the same pack disagree, and a list of JSON records needs answers from a person that a list of delimited text does not | `a2m-pack-file`, the drafter | Fixed: a JSON field has the type its values hold; only a key of mixed, nested, or no values, and the list's key, stay questions (decision 0399) |
| - | The offline test of the write could not hold the value written | See finding 22 | | |

**What this field test does not show.** A file open in another program, a lock signal, a write to a settings file or a folder, a save that is cut, the office suite's own format (the pack does not read it, and whether the scout says so was not checked), or a second operating system.
