# The less review, 2026-11-25

One design review round, by [lens 7](../plan/design-review-lenses.md): what can be removed from the first release without losing the core, and what is designed and not needed? The first release is close.

**The core, as measured.** [H-18's result](../hypotheses/H-18-result.md) gives the path a new agent takes. In the second measurement, three agents with no knowledge of the repository each ran `init`, `add`, `ready`, waited for the person's press, then ran `ready` or `publish request` again, `tool search`, and `tool call`. Each took 15 to 20 commands and 68 to 79 seconds. None used a setting, a shortcut other than those three, an action with no handler, or a spec section. Everything below is weighed against that path. A part off the path keeps its place only if its absence would make a run unsafe, or would take a kind of software out of reach.

**What was read:** the [action catalog](../reference/action-catalog.md) against `handler_for` in `crates/a2m-actions/src/handlers/mod.rs`; `SHORTCUTS` in `crates/a2m-actions/src/faces.rs` and its test in `src/tests/second.rs`; the capture's handler; [section 226](../spec/2-kernel/226-configuration.md) against `crates/a2m-actions/src/settings/schema.rs`; the packs' manifests against [section 201](../spec/2-kernel/201-archetypes-and-modes.md); every crate's `failure_codes!` table against the code that refers to each code; `tools/contracts.py`; the README, [section 404](../spec/4-building-tools/404-setup-and-ease-of-use.md), [section 220](../spec/2-kernel/220-actions-and-the-authoring-interface.md), and the guidance file `init` writes; and each row left in [the line](../plan/build-order.md#the-line-every-package-left-and-whether-a-worker-can-take-it).

## Each thing asked about, and what it costs a user

**The action catalog: 116 actions, 27 with no handler.** Kept whole. The 27 are not listed up front ([decision 0306](../decisions/0306-the-short-path-is-add-then-a-trial-and-only-a-built-action-is-listed-up-front.md)) and have no client method (YL5). Each answers `action_not_built` by name, and the command help marks each "(not built)". A user meets them only by asking for one by name, or by reading `--help`. Removing them from the catalog would save that user a few lines of help. It would also leave designed interfaces with records and no row in the catalog. Cost to a user of keeping them: a longer help listing. Of removing them: none they meet, and a catalog that disagrees with its designs. Finding 6 corrects the list.

**The shortcuts.** Cut from eighteen to fourteen, and `learn` corrected (findings 1 and 2). Cost to a user: no `diff`, `bundle`, `rollback`, or `migrate` word, where each did nothing anyway. A person who wants to undo a publish still has no command for it, which [SCOPE.md](../../SCOPE.md) already says ("Not yet").

**The settings.** The kernel's schema declares 100 settings. 55 are marked not built: a value for one is refused by name, and `config show` says what happens instead. The packs declare 28 more, all built, 13 of which the kept contract misses (finding 11). No agent in H-18 set a setting. The not-built ones were not cut from the schema. The schema is how a value meant for a part not built is refused with its reason, not as an unknown key (rule 7). They were cut from what a release freezes (finding 7). Cost to a user: none today. `config show` lists 55 entries marked `built: false`, which is honest and long. A shorter default listing was weighed and not decided, because no measurement shows anyone stopped by it.

**The packs and their modes.** Kept, all ten modes. Each is built and proven against its stand, and every kind but the desktop has met existing software in a field test. Cutting the desktop or the device pack would take a kind of software out of a person's reach, the North Star's first measure, and save nothing a user pays for: a pack that is never used costs that user nothing. `site_tools` serves few sites. It is built, and it is the web pack's. What a first release should say instead is how far each pack has been tested, which SCOPE.md does per kind. Finding 4 sets the desktop pack's field test.

**The failure codes: 426.** Kept, but for two (finding 8). A user meets one code at a time, each with its meaning and its next step, and an agent branches on the class, of which there are a closed few ([decision 0437](../decisions/0437-what-a-release-publishes-is-kept-and-every-later-build-is-checked-against-it.md), point 4). The count is a cost to whoever reviews the table, not to a user. The two codes nothing raises are the only ones that promise nothing.

**The spec sections and references a first-time user meets.** A first-time user, or their agent, meets the README, `--help`, the guidance file that `init` writes, the built-in guides of `docs get`, and the scout's report. They meet no spec section unless a guide points to one. The README and section 404 taught paths nobody takes (finding 5). The guidance file gives the ten-step long way before "the short way". All three agents in the second measurement took the short way all the same. Putting the short way first goes to row 5.6c, which already changes the guidance (decision 0456, point 7). Nothing in the guides was found to be unneeded. The smallest, `pack-desktop.md`, is 682 bytes.

## Checked and found sound

- **What the first hour needs is all built.** Every action on the measured path has a handler, and every shortcut on it runs only built steps.
- **The unbuilt actions are already kept away from a user's first hour.** They are not listed up front, have no client method, and the help marks each one.
- **The unbuilt settings are refused, not ignored.** A value for one is an error that names it. That is why they stay in the schema.
- **No pack or mode was found that nothing reads.** Each mode is in a pack's manifest. Each built setting is read by code, as the tests named in principle 3 of section 226 hold.

## What this round did not look at

The built actions that only a server needs: `toolset.*`, `grant.*`, `policy.*`, `audit.query`, and `session.list` and `session.end`, which act on someone else's session. Each is built and small on one machine, but a person there holds every role. Whether they belong in a first release that serves one machine is a question for lens 12, simpler. So is `spec.import`, which is exactly `scout.run` with one file, and is built. The failure codes were counted and searched for, not read one by one.

The next gain is more likely from building than from another round of this lens. LS1 and LS2 are small, and the third measurement that 5.6c's proof asks for will show whether the first hour has anything left to lose.
