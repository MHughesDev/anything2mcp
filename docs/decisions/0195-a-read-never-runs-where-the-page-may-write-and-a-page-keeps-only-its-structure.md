# 0195. A read never runs where the page may write, and a page keeps only its structure

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the drivers, lowering, and drafting rules of [`a2m-pack-web-ui`](../architecture/crates/a2m-pack-web-ui.md), the recording of [`a2m-pack-web-browser`](../architecture/crates/a2m-pack-web-browser.md), the discoverers of [`a2m-pack-web-probe`](../architecture/crates/a2m-pack-web-probe.md), additions to the test application's web interface (`/orders/{order_id}/summary`, `/orders/{order_id}/lengths-by-query`, `/orders/{order_id}/lengths-by-header`, `/api/orders/{order_id}/lengths`, `/notes/{note_id}`, `/invitations/{token}` and its two requests), and sentences of [spec section 301](../spec/3-packs/301-the-web-pack.md). ## Consequences

- Decision 0190's sentence "An application that needs one answers otherwise, and the read stops" did not hold: it read another variant with the same shape. A read is no longer drafted from such a request.
- The test application's page of an order's totals sends a query and headers its script set, so it now drafts an entry with a question; the `page_http` tests read through `/orders/{order_id}/summary`, which asks for the same totals with nothing more. The measurement of decision 0190 was made on the totals page and was not repeated.
- A `ui` read opens one tab, as before; a write opens two, the observing one at prepare and the acting one at its first `goto`.

## Revisit if

The provider contract gives `prepare` the operation and its effect; or the browser engine offers a read with the cache and the page's storage set aside, so that a write's read-back need not trust the same profile.
