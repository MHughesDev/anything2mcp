# 0209. The desktop pack reads Windows applications through UI Automation, on a thread of its own

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the desktop pack's build order step 6 (reads only), its failure table, and its registration of platforms in [its design](../architecture/crates/a2m-pack-desktop.md); [spec section 305](../spec/3-packs/305-the-desktop-pack.md) where it says the pack reads on Linux only. Carries out, for Windows, what [decision 0198](0198-the-desktop-pack-reads-linux-applications-through-a-look-only-back-end.md) settled for Linux, under [decision 0208](0208-the-first-release-reaches-what-the-persons-machine-reaches-and-serves-on-that-machine-only.md), which puts a person's own desktop applications in the first release on all three systems.

## Context

The driver, the screens, the lowering, discovery, and drafting stand on one look-only back end per system. Windows had `none.rs`, which stops every call with `busy`/`system_not_built`. [Research note 26](../research/26-desktop-pack-before-it-is-built.md) found that the workspace's `windows` crate carries UI Automation behind features, that UI Automation's own threading rules are where a first client goes wrong, and that GitHub's hosted Windows machine is reported, not seen, to have an interactive desktop. Nothing of this was run here: the work was type-checked and linted for Windows from Linux, and its first run is CI's.

## Decision

1. **Threading.** Each `Look` owns one thread, which joins the multithreaded apartment, makes the automation object (`CUIAutomation8`), and runs the jobs the async methods send it over a channel, one at a time. Every COM object (the automation object, its control-view walker, every element of a walk) is made, kept, and released on that thread, which leaves the apartment last. An element is known outside the thread only as a key in an `El` (`window:<handle>` for a top-level window, `walk:<walk>.<index>` for an element of one of the last two walks). An async method sends a job and waits for its answer with a bound (five seconds, or a walk's deadline plus five), so a call the application never answers costs the step its deadline and never blocks an async thread; UI Automation's own connection and transaction timeouts (`IUIAutomation2`) bound each call on the thread to the same five seconds. The process checks are plain system calls on the same thread.
2. **Events.** A wait listens to the system's accessibility events through an out-of-context event hook (`SetWinEventHook` with `WINEVENT_OUTOFCONTEXT`), which the system filters to the declared application's process. The hook loads nothing into the application and calls back on the thread that set it, so each watch has a thread of its own that sets the hooks, pumps its messages, and removes the hooks when the watch is dropped. Standard controls send these events themselves; UI Automation's own events and property changes arrive through the same mechanism, in their own ranges. The listener reads nothing of an event; it wakes the wait, which reads afresh. Location changes are not listened to: a caret sends them many times a second. *Instead of* UI Automation's own event handlers: they cannot be filtered by process, a handler for windows opening must sit on the desktop's root, and they run a COM object of ours on UI Automation's threads.
3. **Reads only.** Every UI Automation call goes through one function, `ask`, that makes only the members of a fixed list: `ElementFromHandle`, `ControlViewWalker`, `GetFirstChildElement`, `GetNextSiblingElement`, `CompareElements`, `CurrentProcessId`, `CurrentControlType`, `CurrentName`, `CurrentIsPassword`, `CurrentIsOffscreen`, `CurrentLabeledBy`, `GetCurrentPropertyValue` (of `IsValuePatternAvailable` only), `GetCurrentPatternAs` (of the value pattern only), `CurrentValue`, and the client's own `SetConnectionTimeout` and `SetTransactionTimeout`. One test holds the list against the members that act (`Invoke`, `SetValue`, `Toggle`, `Select`, `Expand`, `SetFocus`, `DoDefaultAction`, `ScrollIntoView`, `SetWindowVisualState`, `Close`, and the rest). A second reads the module's own source and finds every method called on a UI Automation object inside an `ask` that names it, and no call of a member that acts. The `AutomationId` is not read: a locator is a role and a name (decision 0198).
4. **Only the declared application, proven before it is asked anything.** The top-level windows of the desktop are listed by the system (`EnumWindows`); for each shown window the system says its process (`GetWindowThreadProcessId`) and that process's program (`QueryFullProcessImageNameW`), compared with the surface's `program` in the plain resolved form that `resolved_path` of `a2m-provider` gives. Only for a process that runs the program: its session must be the engine's, else `policy`/`application_not_owned`; its token's user must equal the engine's by `EqualSid`, else `application_not_owned`; a token the engine may not open, or an elevated token when the engine's is not, is `busy`/`target_elevated`; the `digest` is checked against the program file. Then its name: UI Automation has no element for an application, so **an application's name on Windows is its program's file name without the extension**. None: `application_not_running`; several processes: `application_ambiguous`. Its windows are its shown top-level windows; a walk reads only elements whose process is the application's, and a window is checked again to be the application's before each walk.
5. **Roles: one table.** UI Automation's control types are mapped to the pack's role words in one table in the back end, with two refinements: an edit that says it holds a password is `password_text`, and a text, an edit, or a custom element directly under a `table_row` is a `table_cell`. A list view in report view is a data grid (`table`) whose header (`table_row`) holds header items (`table_column_header`) and whose data items are `table_row`. A control type with no word is `other`, the word the Linux back end already uses for the same thing; it is shown in a snapshot and never matched by a locator. `showing` is `IsOffscreen` reversed; an element has a value to read when the value pattern is available, else its name is its text.
6. **A password edit is never read.** `IsPassword` marks it secret in the walk; a read of it is `password_read_refused` before any job is sent, and the job checks `IsPassword` again before it gets the value pattern.
7. **The stand on Windows is in `targets/example-desk`, behind `cfg(windows)`,** not a sibling crate: the stand's interface (`Session`, `Desk`, `Truth`, `Order`) and the tests over it stay one, and a second crate would duplicate it. It is a window of plain Win32 controls (statics before edits, which name them; a report-view list view; a button), shown on screen without taking the focus (`SW_SHOWNOACTIVATE`) because UI Automation reports an element of a hidden window as not there and one off the screen as not shown. It runs in a process of its own: the test's own program, copied by `Session::start` into a folder of the session's own as `example-desk.exe` and started again with one test alone, which every test binary that starts a stand declares with `example_desk::stand_child!()`. So the program the pack proves is a file no other process runs, the name is the stand's, and there is no build step to go stale. One session at a time in a test process holds a seat, because two windows of one program would be two applications. The control interface is a line protocol on the process's standard input and output.
8. **What the stand witnesses.** Each control is subclassed, so every message another process sends it passes the stand first. It counts, by control and name, the messages that read or change a standard control (`WM_GETTEXT`, `WM_GETOBJECT`, the list view's getters; `WM_SETTEXT`, `BM_CLICK`, `WM_SETFOCUS`, keys, and the list view's setters as acts), every message that asks the password edit for its text or its length, and Save's notice to its window as a write. It cannot witness a call a UI Automation client answers without a message to the control (the proxies for standard controls run in the client), nor what the client does with what it read. That the pack never asks for the password's value is proven by the list of point 3 and the check of point 6; the stand's count is the second witness.
9. **No new crate.** `windows` 0.62.2 gained features in the two crates that use it here: for the back end `Win32_Security`, `Win32_System_Com`, `Win32_System_Ole`, `Win32_System_RemoteDesktop`, `Win32_System_Threading`, `Win32_System_Variant`, `Win32_UI_Accessibility`, `Win32_UI_WindowsAndMessaging`; for the stand `Win32_Graphics_Gdi`, `Win32_System_Diagnostics_Debug`, `Win32_System_LibraryLoader`, `Win32_System_StationsAndDesktops`, `Win32_UI_Controls`, `Win32_UI_WindowsAndMessaging`; both `Win32_Foundation`. `sha2` and Tokio, already in the workspace, are now used on Windows too. Every system call is in `backend/windows.rs` or the stand's `win/` module, each under `#[allow(unsafe_code)]` with a comment on each block.
10. **Two failure codes:** `busy`/`target_elevated` (named in the design's table before) and `policy`/`application_not_owned`, declared in the manifest. `system_not_built` remains for macOS.

## Alternatives considered

- **A single-threaded apartment with a message loop for the UI Automation thread.** It would let UI Automation event handlers run on our thread, but the documentation's guidance for clients is the multithreaded apartment, and a single-threaded client that blocks in a call to a hung application blocks its own loop.
- **A bounded re-read of the condition instead of events.** It needs no hook and no second thread, and it would be polling, which the design's invariant "nothing waits by polling" forbids.
- **The stand in the test's own process, its window on a thread of its own,** as the Linux stand is hosted. Simpler, with no copy and no protocol, but the pack's proof of the process would only ever meet itself, and UI Automation in-process takes paths that a real client never does.
- **A stand built as a UI Automation provider of its own,** which could witness every property and pattern asked. It would test a provider nobody ships instead of the system's proxies for standard controls, which are what a real Win32 application exposes.
- **The application's name from the program's version resource** (its product name). Closer to what a person calls the program, but the copied test program has no such resource, so it could not be proven here. It may replace the file name when a stand can carry one.

## Unproven until CI's Windows runner runs it

All of it. In particular, from the documentation and memory, not seen: that an edit's name is the static just before it; that a report-view list view is a data grid of data items whose children include one element for every column, the first included, and whose header is its first child; that the hosted runner's session is interactive and its windows are not reported as off the screen; that standard controls' value changes reach an out-of-context hook; that `QueryFullProcessImageNameW` on the hosted machine gives a path `resolved_path` resolves to the same form; that the copy of a test program runs. The back end's own test against the stand prints the walk (role, control type, name, flags) when it fails, and the pack's tests print the window's shape, so a failure on the runner says what UI Automation gave.

## Not built

Writes, starting an application, `desktop_probe`, the lint rules, and the macOS back end, as for Linux. A real toolkit's tree (WinForms, WPF, Qt) is not in the loop; nor is an elevated application, another user's, or a locked session.
