# 0179. What each pack drafts, so that a scout ends with reads that work

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the drafting rules of the HTTP, data, and MCP packs, and the HTTP pack's description import; one built-in field type in [`a2m-files`](../architecture/crates/a2m-files.md); the designs of [`a2m-pack-http`](../architecture/crates/a2m-pack-http.md), [`a2m-pack-data`](../architecture/crates/a2m-pack-data.md), and [`a2m-pack-mcp`](../architecture/crates/a2m-pack-mcp.md); sentences of spec sections [402](../spec/4-building-tools/402-the-scout-and-who-does-what.md), [303](../spec/3-packs/303-the-http-pack.md), [304](../spec/3-packs/304-the-mcp-pack.md), and [307](../spec/3-packs/307-the-data-pack.md); the built-in types in the [file formats](../reference/file-formats.md). Answers gap 1 of [decision 0170](0170-the-scout-identifies-each-surface-with-one-discovery-job-and-stores-each-stage.md): of the shipped packs only the stream pack drafted a read operation, so the scout's try stage had nothing to try.

## Decision

| Question | Decided | Alternative weighed |
| --- | --- | --- |
| What the HTTP pack drafts | Beside each endpoint entry, one read operation for each GET a published description states: `{target}_{object}_{get or list}`, the object being the last two plain words of the path. An answer that is a list gives `verb: list`, with one list output per plain property of an item, taken by `*.name`; any other gives `verb: read`, with one output per plain property. The inputs are the path's placeholders, which form the key. Nothing is drafted for a HEAD (its answer has no body), for any other method, for a placeholder the description states no parameter for, for a required parameter outside the path, or for an answer with no plain value | One read per safe method, HEAD included, as section 402 said. A HEAD read returns nothing to compare |
| What the HTTP import now reads | Each operation's parameters (name, place, whether required, schema type, and its own example when that is text or a whole number), and whether it needs a credential by the format's rule (no `security` stated, an empty one, or one with an empty requirement); an endpoint so described is drafted `auth: none`. A schema with no `type` whose `enum` or `const` holds only text is text. With no path named, the description is looked for at `/openapi.json`, then `/api/openapi.json`, one GET each. The finding's format is 2; a finding of format 1 is still read, as stating no parameter and needing a credential | Leaving `auth` to its default, the session's credential: every drafted read of an open service then stops with `needs_login` though nothing asked for one |
| What the data pack drafts | For a table with a declared key whose every column has a type the store states: in the statements file, beside the read by key, `{record}_list`, the catalog's own columns quoted by the store's dialect, in the order of the key, `returns: many`, `max_rows` the pack's `max_rows` setting; and two operations, `{target}_{record}_get` (the key as inputs, every other column as an output) and `{target}_{record}_list` (no input, one list output per column, and `more`). Nothing for a table with no key, a view, or a column of a type the store does not state: the statements file holds that question once | Only a read by key, as section 307 had it, leaving lists to the developer. A read by key has no example to try (below), so the scout of a database file would still try nothing |
| What the MCP pack drafts | One pass-through read, `{target}_{tool}`, for each tool the server marks read-only whose entry is settled: not one whose whole input is one string, which the server may run. Its inputs are the input schema's plain properties, passed by name; its outputs the output schema's plain properties, or `text` where it states none. A mapping entry left with a question now goes to `mappings/{surface}_undecided.yaml`, apart from the settled entries, so that its question does not hold up the reads beside it | Drafting the read for a tool whose input is one string, with `free_text: false`. That is the judgment the open question exists for |
| An output's type | From what was observed: an integer, a number (as `decimal`), a boolean, and text, which is always of the new built-in type `untrusted_text` (`text`, marked untrusted). A type the description leaves open is an open question; a nested value is left out, because an output is one value or a list of values | Each pack looking in the target's `types.yaml` for a type marked untrusted. A target that `add` just made has none, and the output would be plain `text` with the compiler's warning |
| What an example may be | Only a value the system published about itself, as the description of its interface: an OpenAPI parameter's or schema's `example`, a tool's input schema `examples` or `default`, for every required input, or none. The operation's description says the example is the description's own. A value of the system's data is never kept as an example: section 218 keeps shapes, not values, and the data pack's discoverer reads no row. A read with no example and a required input is drafted, and the scout says it could not be tried and why | Keeping the first key a catalog's sample read returned, as section 307 suggested for the scout. It is a value of a person's data in a target file |
| What a drafted fixture may hold | Nothing: no test and no fixture is drafted. The drafter may draft only `operation` and `source` of the kernel's kinds ([decision 0153](0153-what-the-compiler-the-plan-and-the-redactor-hold-by-themselves-after-the-safety-audit.md)); an observed answer is the system's data, which a fixture holds only once scrubbed by `fixture.record`; and an open question in a drafted test would stop the whole target compiling. `kernel.operation_without_test` stays a warning on a draft and an error at publish | Drafting a test with its fixture left as an open question for a person. It blocks every other draft's compile, and so every try |
| The command, device, file, web, and stream packs | Unchanged here. The command pack drafts no operation by design (section 402). The device pack's discoverer observes no register, so there is nothing to read by rule. The file pack's document draft leaves every type and the key as questions, so no read over it can compile. The web pack has no drafting rule. The stream pack's read already follows these rules: its name, its key from what the broker states, and no example | Typing every delimited cell as `untrusted_text` and drafting the file pack's `list` read now. It changes what the file pack's design and its tests hold, that a draft states no type the file did not, and is left as a judgment to make |

## Consequences

- Against the test application, the description it serves gives six reads that compile in draft mode; with the description's own examples, three run through the driver's handle and return what the application stores, and nothing is written (`the_test_applications_description_drafts_reads_that_read_what_it_stores`).
- Against the database file, every keyed table gives a read by key and a list; without the two drafts that hold a question, they compile, the read by key returns the stored row, and the list returns every customer, with nothing written (`the_stands_catalog_drafts_reads_that_read_what_it_stores`).
- Against the MCP stand, one read is drafted (`orders_report`); with the undecided mapping set aside it compiles and returns the stand's count, with no other tool called (`the_stands_tool_list_drafts_reads_that_read_what_it_stores`).
- The scout's try stage compiles the whole target, and one draft that holds a question stops it compiling, since a file kind's section is not made while one of its files fails. The scout should compile without the drafts that hold an open question (the files the drafter's report names in `open_questions`). Until it does, the scout of the database file still tries nothing.
- The engine shapes a read's result from its declared outputs alone, and the data pack's list answers `rows` as records: through the engine the drafted list returns only `more` until outputs can be records or the driver also gives each column as a list.
