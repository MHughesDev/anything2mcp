# 0244. The desktop pack reads macOS applications, and every act proves the record again

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the desktop pack's build order steps 7 and 8, its dependencies, its failure table, and its invariants in [its design](../architecture/crates/a2m-pack-desktop.md); [spec section 305](../spec/3-packs/305-the-desktop-pack.md) where it says macOS is not built, where it gives the macOS permission as `runner_unavailable`, and where it names the failure of a window the screen does not declare; the second-window case of [decision 0218](0218-the-desktop-pack-writes-on-linux-through-a-second-closed-list-and-reads-back-what-is-stored.md), point 1, whose write now stops. Carries out for macOS what [decision 0198](0198-the-desktop-pack-reads-linux-applications-through-a-look-only-back-end.md) settled for Linux and [decision 0209](0209-the-desktop-pack-reads-windows-applications-through-ui-automation-on-a-thread-of-its-own.md) for Windows, under the owner's answers in [decision 0242](0242-the-owner-takes-the-recommended-answer-to-every-open-question.md), points 1 and 14.

## Context

On macOS the pack stopped every call with `system_not_built`. Decision 0242 settled the two questions that held it: a permission the person grants the engine in the system's own settings is within rule 5, so the back end may rest on the Accessibility permission; and on the CI runner only, a machine made for the run and thrown away, the permission may be granted by writing the runner's permission settings as an administrator. [Research note 26](../research/26-desktop-pack-before-it-is-built.md) named the bindings and found the CI grant reported to work by one 2026 project and reported impossible by two older answers. Nothing here was run: the work was type-checked and linted for `aarch64-apple-darwin` from Linux, and its first run is CI's.

A safety audit of the Linux writes found, in code that exists, that `set` and `invoke` prove the application's process again before they act but not that the window still shows the record the `wait` proved: an application that moves the window to another record, or raises a dialog, between the two lets the act land on another record. The second half of this record settles that.

## Decision: the macOS back end

1. **Threading.** Each `Look` owns one thread, which makes every accessibility element of a walk, keeps it, releases it, and runs the jobs the async methods send it, one at a time; an element is known outside the thread only as a key in an `El` (`application`, `window:<listing>.<index>`, `walk:<walk>.<index>`; the last four listings and walks are kept). An async method waits for its job's answer with a bound (five seconds, or a walk's deadline plus five). The client's own messaging timeout, set on the system-wide element, bounds each call on the thread to five seconds. *Instead of* sharing elements across Tokio tasks: the bindings do not mark them safe to share, and one owner thread is what the Windows back end does for COM.
2. **Notifications.** A wait listens through an `AXObserver` made on a thread of the watch's own, registered for a fixed list of notifications (value or title changed, an element made or destroyed, a window made, moved between its states, or focused, a layout or a row count changed, the application hidden or shown) on the application's element and on each of its windows, whose run-loop source runs on that thread's run loop until the watch stops it. A second thread waits on a kernel queue for the application's process to exit (`EVFILT_PROC`, `NOTE_EXIT`) or for the watch's own stop event. The listener reads nothing of a notification; it wakes the wait, which reads afresh. Moves and resizes are not listened to. No thread polls.
3. **Reads only, by two closed lists.** Every call into the accessibility interface goes through `ask`, which makes only `AXIsProcessTrusted`, `AXUIElementCreateApplication`, `AXUIElementCreateSystemWide`, `AXUIElementSetMessagingTimeout`, `AXUIElementCopyAttributeValue`, `AXObserverCreate`, `AXObserverAddNotification`, and `AXObserverGetRunLoopSource`. Every attribute is copied through `copy`, which asks only `AXRole`, `AXSubrole`, `AXTitle`, `AXDescription`, `AXValue`, `AXTitleUIElement`, `AXChildren`, `AXWindows`, `AXRows`, `AXColumnHeaderUIElements`, and `AXHeader`. One test holds the calls against those that act (`AXUIElementSetAttributeValue`, `AXUIElementPerformAction`, `AXUIElementPostKeyboardEvent`, `AXMakeProcessTrusted`, `AXIsProcessTrustedWithOptions`, event posting) and the attributes against those a client sets; a second reads the module's source and finds every method of the bindings it names inside an `ask` that names its call, and no method that acts named at all. A write on macOS stops as `busy`/`writes_not_built` before anything is sent, as before.
4. **The permission and its named stop.** Before any read, the back end asks `AXIsProcessTrusted`, which never shows the system's prompt. When it says no, or when a call answers `kAXErrorAPIDisabled` although it said yes, the stop is `busy`/`accessibility_off`, the form the Linux back end uses for a session whose accessibility is off. Its message says the program may not use the accessibility interface and that the pack never allows it or prompts; its next step says to open System Settings, Privacy & Security, Accessibility, and allow the program that started the engine, such as the terminal or the agent application that runs it, and, if that one is allowed already, the engine's own program by its path. Which program the system judges is from note 19's forum sources and from note 28's reading of the analogous Local Network permission, where the system attributes a helper's request to the application responsible for it: not verified for Accessibility, so the message names both programs. Product code never writes the permission database and never asks the system to prompt. *Rule:* rule 5 and decision 0242, point 1.
5. **Proof of the application before it is asked anything.** The process table is read (`proc_listallpids`, `proc_pidpath`, `proc_pidinfo` with `PROC_PIDTBSDINFO`): a process whose program, in the resolved form `resolved_path` of `a2m-provider` gives, is the surface's `program`; its effective user must be the engine's, else `policy`/`application_not_owned`; the stated `digest` must be that of the running program's file, else `unknown_variant`/`application_not_proven`; its start time is kept. As on Windows, **an application's name on macOS is its program's file name**: the application's own title is not asked before the process is proven. None: `application_not_running`; several: `application_ambiguous`. Only then is the application's element made, and one real read made of it, since the permission check is reported to say yes while calls still fail. Before every later question, the process is proved again: the same start time and the same program, so a number given to another process is never asked.
6. **Roles: one table.** The interface's roles map to the pack's words in one table (`AXWindow` `frame`, `AXSheet` `dialog`, `AXGroup` `panel`, `AXStaticText` `label`, `AXTextField` `entry`, `AXTextArea` `text`, `AXButton` `push_button`, `AXTable` `table`, `AXRow` `table_row`, `AXCell` `table_cell`, and the rest in the module), with four refinements: a text field whose subrole is `AXSecureTextField` is `password_text`, is marked secret, and its value is never asked for (its subrole is read again before any value is); a window whose subrole is a dialog's is `dialog`; a cell, a static text, or a text field directly under a row is a `table_cell`; and a table's headings (`AXColumnHeaderUIElements`, else the children of `AXHeader`) form a `table_row` of `table_column_header`s, ahead of the rows of `AXRows`, while the table's columns, which hold the same cells again, are not walked. A role with no word is `other`. A name is the element's title, else its description, else its title element's name, else, for a static text or a table's heading, the text it shows; a cell's is the text of the static text in it. A field's value is its `AXValue`. Every element listed is taken as shown: the interface leaves out what the application hides.
7. **The stand on macOS** is a window of AppKit's own controls (text fields titled by labels through their title element, a secure text field, a view-based table in a scroll view, a button), in a process of its own, through the harness the Windows half already used, now `child.rs` for both systems: the test's program copied as `example-desk` and started again. AppKit makes windows on the main thread only, which no test of the test harness runs on, so `stand_child!()` also declares a function in the program's initializer section, which the system calls on the main thread before `main`; in the stand's process it serves the window and its control interface and never returns, and in every other process it returns at once. *Instead of* a stand program of its own, built apart: no build step can be relied on from another crate's tests, and the copy is never stale. *Instead of* AccessKit's macOS adapter: it is the egui stand that decision 0198 set aside, and it tests a provider no AppKit application ships. *Instead of* a cell-based table: view-based tables are what current applications use.
8. **What the stand witnesses.** Its text fields, secure text field, and Save are subclasses that count each time AppKit's accessibility asks one for its value, sets its value or its focus, or presses it, and Save counts each run of its action as a write. It cannot witness a question AppKit answers without asking the control (a title, a role, the children, a label's text, a table's cells), nor what a client does with an answer. That the pack never asks for the password's value is proven by the closed lists of point 3 and the subrole check of point 6; the stand's count is the second witness, and the stand's own test asks the secure field for its value as a client to prove the count works.
9. **Dependencies.** `objc2-application-services` 0.3.2 (features `AXError`, `AXUIElement`, `HIServices`, `libc`) and `objc2-app-kit` 0.3.2, new to the lock, from the project and the release of the `objc2` crates already in the workspace; `objc2-core-foundation` 0.3.2 and `libc` 0.2.191, already in the lock. Each is `Zlib OR Apache-2.0 OR MIT` or `MIT OR Apache-2.0`, on the closed list. All are confined by `cfg(target_os = "macos")`; `objc2-app-kit` is the stand's alone. None compiles C.
10. **The CI grant and its limits.** The job (in the report of this slice, for the lead) builds the test programs first, so their paths are known, then, as an administrator, writes one row per program into the runner's system permission database (`/Library/Application Support/com.apple.TCC/TCC.db`, service `kTCCServiceAccessibility`, client by path, allowed) for each test program and for each program above the job's shell, reads the rows back, prints them, and restarts the permission daemon; then it runs the same tests with `A2M_REQUIRE_DESKTOP=1`. A grant that did not take is recognisable: the stand's `Session::start` fails, naming the test program that may not use the interface. This act is the runner's only, as decision 0242 allows, and no product code or instruction to a person does it. *Rule:* decision 0242, point 14.

## Decision: every act proves the record again

11. **Before every act, on the walk it acts on.** The driver's `before_act`, which every `set` and every `invoke` calls just before it acts (after the fresh walk that finds its element, and for the committing `invoke` after its checks of the confirmation and the variants, immediately before the press), proves that the window still shows the run's record, by the check the `wait` makes, and lists the application's windows: any window that no screen of the target names, by role and title, is a stop. Both stop as `unknown_variant`/`unexpected_page`, nothing sent, with an unknown window's title carried as what the application said. The lowering gives each `set` and `invoke` step the key arguments of its `wait`. The function lives in the driver, above the three back ends, so the Windows and macOS acting halves inherit it when they are built; today only Linux has a caller. *Instead of* keeping the key the `wait` proved in the driver's state: a step that carries its own key proves what the plan says, with nothing hidden between steps.
12. **A window no screen names stops a write.** Decision 0218's test that wrote with a second window of another title open now expects the stop. *Instead of* stopping only on a window of the role `dialog`: an application may raise a modal window of any role, and a window the screens do not know is unknown, which is a stop (rule 7). A target whose application keeps another window open declares a screen for it.
13. **The stand learns two faults,** additions only: once the field labelled `Order number` has next been read, the window shows another order number (`Fault::AnotherRecordAfterRead`), or the application raises a dialog titled `Example notice` (`Fault::DialogAfterRead`). The new test of each failed before the fix: the value was set into the other record.
14. **The digest of the running program, on Windows and macOS.** The audit found the Windows back end hashed the file at the program's path, where Linux hashes the running image. Both back ends now take the digest only when, once the file is read, the system still gives that same path for the process's program: the system's path follows the image's file, so a file moved away and another put in its place during the read is not taken for the running one. What it would take to hash the image itself: on Windows, reading the file through the process's own image mapping, and on macOS likewise, neither of which the back ends do. What remains: a change of the file's content in place while it runs. Windows refuses to write a file mapped as a running image, from memory and not verified here; on macOS an Apple-silicon process whose signed pages change is reported to be stopped by the system, also not verified here. The path proven at the same moment narrows the gap; it does not make the question moot.
15. **Two findings are not changed here.** The per-field check after a `set` reads the field the value was typed into: the audit says so itself, and it is a check that the field took the value, not a proof of storage; the operation's read-back, a window reached afresh whose `wait` proves the record, is that proof. The code's comment now says so. The driver's hold on the desktop is per driver, so two engines in one login session do not share it, and the scheduler's exclusive key is per surface (`a2m-engine/src/engine.rs`, `exclusive_needs`, which keys each need by `kind` and `surface.name`). A hold per login session needs a lock the system keeps for that session, which two engines both see: the pack could take one in a per-session folder of the system's own, or the kernel could give `exclusive = "screen"` one key per machine session instead of one per surface. Neither is built; both are *Not yet*.

## Unproven until CI's macOS runner runs it

All of it. In particular, from the bindings' documentation and memory, not seen: that a test program a job starts is judged by its own path, so that a row for it takes; that the hosted image lets an administrator write the system permission database (two older reports say no); that a function in the initializer section may run AppKit's event loop before `main`; that a window of a non-bundled program with the regular activation policy, never activated, is listed by `AXWindows`; that a text field's `AXTitle` and `AXDescription` are empty and its title element is its label; that a view-based table answers `AXColumnHeaderUIElements` and `AXRows`, and that its rows' children are cells or the cell views' static texts; that a notification registered on the application's element is delivered for its descendants; that the stand's posted value change reaches the observer; that `CFRunLoopStop` from the watch's side ends a run loop that had not yet begun; that AppKit asks the subclasses' own methods for a value, a set, and a press. The back end's own test prints the walk (role, subrole, name, flags) when it fails, and the tests' named stop says when the grant did not take.

## Not built

Writes on macOS and Windows; starting an application; `desktop_probe`; the lint rules; `unexpected_dialog` as a code of its own; a hold on the desktop per login session; a real toolkit's tree other than AppKit's.
