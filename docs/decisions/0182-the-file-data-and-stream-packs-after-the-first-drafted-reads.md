# 0182. The file, data, and stream packs after the first drafted reads

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the drivers and drafting rules of [`a2m-pack-data`](../architecture/crates/a2m-pack-data.md), [`a2m-pack-file`](../architecture/crates/a2m-pack-file.md), and [`a2m-pack-stream`](../architecture/crates/a2m-pack-stream.md); the file pack's save; one refusal in [`a2m-files`](../architecture/crates/a2m-files.md); one seed file of the file stand; sentences of spec sections [307](../spec/3-packs/307-the-data-pack.md), [308](../spec/3-packs/308-the-file-pack.md), [309](../spec/3-packs/309-the-stream-pack.md), and [402](../spec/4-building-tools/402-the-scout-and-who-does-what.md). Takes up the open points of [decision 0179](0179-what-each-pack-drafts-so-that-a-scout-ends-with-reads-that-work.md) and the four contract additions [decision 0173](0173-the-stream-and-file-packs-take-up-the-kernels-second-pass.md) asked for, which [decision 0176](0176-the-action-registry-takes-up-the-kernels-second-pass.md) built.

## Decision

The lead ruled on each point; this record says what was built and what the building showed.

| Point | Built | Alternative weighed |
| --- | --- | --- |
| 1. The data pack's list returns its rows through the engine | A `many` statement's `fetch` gives, beside `rows` (the records) and `more`, each field of the statement's record as a list of its values in row order, `null` where a row has none. A field named `rows` or `more` is the field's list. Both dialects. A server's `numeric(p,s)` whose scale the built-in `decimal` keeps (six places or fewer) is drafted as `decimal`, so that a table of exact decimals drafts its reads on the server too; the embedded engine's `NUMERIC` may hold a float and stays a question | Outputs that are records, which the engine shapes as one value or a list of values. A kernel question, not built |
| 2. The file pack drafts a `list` read | A cell of delimited text or a workbook whose type nobody stated is drafted as the built-in `untrusted_text`, and the record kind has no key. The document holds no question and compiles. Beside it: `{target}_{object}_list`, one list output per field and `truncated`; and `{target}_{object}_get`, which holds the questions (the key, the input of each key field, and each key field's type) and does not compile until they are answered. The document's rules refuse the rest: a record kind of rows with no key lowers `list` and nothing else, and a field of the type `untrusted_text` is never a key and never `writable`. A write over the drafted document does not compile, and says that its rows have no key, which is the question of the read by key. A JSON value has a type of its own, so a JSON document keeps its types and key as questions, and no read is drafted over it. The `list` driver gives each field as a list, as the data pack's does | The questions left in the document. A file that holds one does not compile ([decision 0178](0178-an-effect-left-as-an-open-question-is-undecided-not-a-write.md)), so no list over it could be tried |
| 3. The save uses the contract's `Temporary` | `CheckedPath::create_temporary`, `Temporary::keep_owner_and_mode` before the first write and after the last, `write`, `flush`, `read_back`, `replace`, and `CheckedPath::flush_folder`. The pack's own temporary file, its name of the record's token (decision [0149](0149-the-file-pack-after-its-safety-audit.md), which this supersedes on that one point: the contract's name is `.a2m-new-` and 128 random bits, and says the file is the engine's but not whose record), and its removal at release are deleted: the contract's temporary file is removed when the save does not finish, while its name still holds its own file. On Unix a `false` from `keep_owner_and_mode` stops the save, unsent, with `metadata_not_kept`: a set-user, set-group, or sticky bit is never carried, and an owner the engine's user may not give is not given. On Windows the answer is always `false`, the new file takes its folder's access list, and only the read-only mark is kept, as the design states; the save goes on there, and a file marked read-only is never replaced | Keeping the pack's own temporary file. Every reason decision 0173 gave for it is gone |
| 4. A target cannot redefine a built-in field type | `kernel.built_in_type_redefined`, at lint and at compile alike (a lint is a draft compile): a `types.yaml` entry named as a complete built-in is refused. `money` and `choice`, which need more, are still completed by a target's type of their name | Letting the target's type win, as before. A target's `untrusted_text` of `base: text` would drop the mark from every drafted output unseen |
| 5. The stream pack's drafted read returns something | The channel finding carries `schema_fields`: the plain fields the broker's registered schema states, by name and JSON type, where the pack reads the schema; a drafting rule sees one finding at a time. A read of a retained key outputs each of them but the key (`string` as `untrusted_text`, `number` as `decimal`); with no schema the pack reads, its outputs are a question. A `list` outputs `count` and `more`, which every look states. Over NATS the drafts never compiled: the channel file now carries the duplicate window the server states (`dedupe_window_ms`, also given by the `channels` step), and a retained channel whose key field the broker does not name holds that question. Descriptions name the channel, so that two drafted lists are told apart | Leaving the read as it was and naming what the rule interface lacks. The finding could carry what the rule needs without a change to the kernel |
| 6. The device pack | Nothing built. The design drafts a device read from a register map a vendor published (`published_description`); the discoverer observes no register, and the pack has no finding kind for a published map nor a rule from one | — |

## Consequences

- Each is proven against the pack's stand, by a test that fails before it: `the_drafted_list_returns_the_stands_rows_column_by_column_through_the_plans_outputs` and `the_drafted_list_returns_the_servers_rows_column_by_column_through_the_plans_outputs` (data); `the_drafted_list_reads_every_row_as_marked_text_and_a_write_waits_for_the_key` and `a_file_whose_bits_cannot_be_kept_is_not_replaced` (file); `a_target_cannot_redefine_a_complete_built_in_type_and_may_complete_an_incomplete_one` (`a2m-files`); `the_drafted_reads_return_what_the_broker_holds` and `the_drafted_reads_over_nats_return_what_the_server_holds` (stream).
- "Through the engine" is shown with the registry's driver handle and the plan's declared outputs, each normalized by its field type, as the engine's `outputs_of` does: a pack cannot depend on the engine. One difference the tests found: the engine hands a list output's normalizer the whole list, which a normalizer refuses (`value_unparsable`). The test helpers normalize a list value by value. **Until the engine does the same, every list output with a field type fails in the engine, the HTTP pack's included.**
- A stream channel file holds the `role` question, which no read needs; a drafted stream read cannot be tried until a person answers it. The file pack's drafted document names no surface, so in a target of several file surfaces it lands on the first.

## Revisit if

The engine shapes a record output: the lists beside `rows` can go. Or the drafter is given several findings at once: the stream channel finding need not carry the schema's fields.
