# 0170. The scout identifies each surface with one discovery job and stores each stage

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the design of [`a2m-actions`](../architecture/crates/a2m-actions.md) and its guides; the `add` shortcut of the [action catalog](../reference/action-catalog.md); the [ledger schema](../reference/ledger-schema.md), by migration `0014`; one sentence of spec section [402](../spec/4-building-tools/402-the-scout-and-who-does-what.md); the failure codes of the [technical reference](../reference/technical-reference.md#failure-codes). Builds on [decision 0164](0164-the-authoring-actions-served-through-the-engine.md), which served `discover.run` and left the scout unbuilt.

## Context

Section 402 gives the scout eight stages and roadmap row E5 asks for them, built on `target.probe`, `auth.detect`, `discover.run`, the drafter, `draft.lint`, and `draft.try`. The engine's `Discover` job runs every registered discoverer that suits a surface, each within the bounds its manifest declares; no manifest marks a discoverer as the one that identifies, and no finding kind is marked as being about sign-in. The packs' drafting rules exist; a pack's rule may draft its own kinds and a read operation, and of the shipped packs only the stream pack's rules draft a read operation. Migration `0009` made `actions_scout_stages`, keyed by a run and a stage.

## Decision

| Question | Decided | Alternative weighed |
| --- | --- | --- |
| What `target.probe` does | For each declared surface, or the one named: what the registry says (the surface kind, its archetype, the provider that serves it, whether its kind keeps a session, and each discoverer that suits it with its declared kinds, sources, highest level, and bounds), then one `Discover` job of a run of its own, as `discover.run` submits it. The result per surface is a state (`identified`, `needs_login`, `refused`, `failed`, `working`, or, with no job, `no_provider`, `no_discoverer`, `not_observed`), the failure, the findings by kind and level, and what each discoverer reported. A surface with no provider or no suitable discoverer is said to have none and nothing runs for it | A discovery job that runs one identifying discoverer. The engine runs every discoverer that suits a surface in one job, and no manifest says which identifies; naming one in the kernel would be pack knowledge |
| What a discoverer reported | The run's control keeps, beside the findings, one row per discoverer of a discovery run in the new table `actions_discovery_results`: the surface, the identifiers of its findings, and its coverage, the bounds it reached, what it dropped, or its failure's class and code. The engine already sent this and nothing kept it | Telling a run's findings apart by their provider. Two surfaces of one kind share their discoverers, and the findings store keeps no run |
| What `auth.detect` says | Claims for a person to confirm, per surface: whether its kind keeps a session (the pack registered it), the mode and provider `auth.yaml` declares for it, and what its probe met (`answered`, `needs_sign_in`, `refused`, `failed`). The method and identity mode are the declared ones; with none declared both are named in `unknown`. Never a credential | Recommending a mode from findings. No registered word says which finding kind is a sign-in method, and no rule maps one to a mode; a recommendation would be a guess |
| What a scout is | Not a ledger run: a row of the new table `actions_scouts` (the person, the target, when it started and finished, its report's hash) whose identifier keys its stages in `actions_scout_stages`. Its system work is ordinary runs, one discovery per surface and one trial per try, each followed with `run.get`, `trace.show`, and the run events | A run of a new tool kind with a scheduler job kind of its own. The run states and the job kinds belong to the ledger and the scheduler, and a pipeline of the kernel's own actions has no step for the engine to run |
| Resuming | `scout.run` continues the newest unfinished scout of the target by the same person; each stage is stored, with the hash of the stage before it as its input, before the next begins. A stage whose runs have not ended within `wait_seconds` is not stored, and the call answers `state: working` with `next` the same call; the same discovery or trial, not yet ended, is given back by the ledger's rule 6 rather than started again. `fresh: true` starts a new scout | Storing a stage's runs before they end. A stored stage is final; a half-finished one would be read as done |
| The stages | 0: consent (the person who added the target, on one machine) and the dispatcher's decision; the budget is stated as not in force. 1 and 2: identify and discover share the one discovery job per surface; stage 2 stores the findings of those runs, with each text the system gave under `untrusted`. 3, compare: the drafter run over a copy of the target's folder in the engine's cache folder, so nothing in the project changes; each file it would write where the target holds one a person wrote is a difference and an open question in the unknowns ledger. 4, draft: the drafter in the target's folder; it writes new files and its own unchanged drafts only, never a write, and its open questions go to the unknowns ledger, each asked once. 5, check: the drafts compiled in draft mode. 6, try: each drafted operation that reads, with its first example as input or with none when it needs none, tried five times one after another through `draft.try`'s submission; `proven` when all five completed with one result, which moves it to `executed`. One that needs an input it states no example of is not tried. Stages 3 to 6 need a project that holds the target's folder; without one each says so | A comparison by each pack's rule, described against observed (section 218, roadmap E3). It is not built in `a2m-provider`; the drafter's comparison is the one a rule gives today |
| Drafts that do not compile | Stage 1 reports that no surface can be observed, with the first problem, and the scout goes on to its report, so that a target just added gets a report and not an error | Failing `scout.run` with `lint_failed`. The `add` shortcut would fail on every new target |
| `authoring.scout.run` | `off` refuses `scout.run` with `policy`, `scout_off`. `authoring.scout.try_reads` off skips stage 6 and says so. The budget settings are not kept, and stage 0 and the report say so | Reading the budget as kept because each discoverer has bounds. A limit is never reported that is not kept |
| The `add` shortcut | `target.add`, `scout.run`, `scout.report`, `session.login`: the scout holds the probe and the sign-in detection. It stops before `session.login`, which is not built, by name | Keeping `target.probe` and `auth.detect` as steps. The scout runs both again, so each would be observed twice |

## Consequences

- An agent can identify a target's surfaces, see how each signs in as claims, scout the target to a report, stop and continue the scout, and read the report later, through any door, and nothing it does reaches the system except discovery and trial runs in the sandbox.
- Proven against the test application (`a_scout_identifies_reports_the_same_twice_and_writes_nothing`) and, in a project with the compiler's test pack, through every stage to a drafted read tried five times (`a_scout_drafts_reads_by_rule_tries_them_and_never_writes`); both ask the stand what was touched.
- Not shown: the scout against the shipped packs and their stands (the web and HTTP packs on the test application, the data pack on the database file, the command pack on the command-line program). A kernel crate's tests cannot name a pack, so that proof belongs to the product crate's tests. Not built: a probe at an address with no declared surface, which needs a discovery job that names an address and no plan; a budget for a whole scout; the comparison of E3.
- Gaps below: of the shipped packs only the stream pack drafts a read operation, so on the test application, the database file, and the command-line program stage 6 finds nothing to try. Section 402 says the HTTP pack's description import drafts one read operation for each method a description marks safe, and the data pack a read by key for each keyed table; neither drafts the operation file, only the endpoint entries and the statements. The command pack drafts none, as section 402 says. No manifest marks a discoverer as identifying or a finding kind as a sign-in method.
