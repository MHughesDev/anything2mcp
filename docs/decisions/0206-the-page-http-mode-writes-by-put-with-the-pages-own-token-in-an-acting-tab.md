## The plan, as written before building

1. The browser engine gains a write from inside the page, on `ActTab` alone, separate from the read: a method from a closed list, a `PagePath`, a typed body whose field names are plain, and the place of the page's token, which the helper in the page reads and sends in the same call and never hands back.
2. `page_requests/` gains a write form, checked at compile; the lowering serves `update` with its commit point and read-back; the manifest says what saves and when the guard lifts; `web.page_http_writes` stays for what is not built.
3. The test application gains case 5, a write refused without the token its page gave; the mode writes there once, verified by the stand.
4. The fault rows a pack can meet at its own level, against the stand.

*Alternatives weighed.* **The token handed to Rust** as a `Secret` and registered with the redactor, then sent by a second in-page call. The kernel gives a driver no way to register a secret it learns during a step (`Redact` has no `register`; only a session lease's `apply` registers), so the token would have reached Rust unregistered; and between the two calls the page could change. Reading and sending in one call keeps the token in the page: nothing of the engine ever holds it. **A `token` step**, as section 301 listed: the token would be held between steps in the driver's state. **POST first:** the form posts of case 5 are POSTs. PUT was built first because it writes the whole record at its own path, so the same write sent twice leaves the record as once; the measurement below shows the browser itself can send a write twice. **The engine's `fetch` on `ActTab`** (method, headers, and body the caller's): it takes any header, and a caller's text could name one.

## Measured

Chrome for Testing, headless, on Linux, against the test application.

- **The browser sends a write again by itself.** With the stand's fault "lost after commit" on the note's path (the PUT is carried out, then the connection closed with no answer), the stand saw two PUTs from one `write_from_page`: the browser sent it again by itself once the connection closed unanswered. The page's token was used up by the first, so the application refused the second as `forgery_token_invalid`, and the record was written once. An answer to a write is therefore the answer to the last sending, not the first: a token refusal was first built as `rejected` (nothing written), and the test showed that would have settled a write that landed. It leaves the write in doubt now. Without a single-use token the second PUT is written again, which a PUT makes harmless to the record and a POST would not. Whether the browser does the same for POST was not measured.
- One write, from the page's meta element to a header, from a hidden input to a body field, and from the cookie to a header in a form body, each landed once with exactly the value sent; the stand's token count shows one token used per write.

## Consequences

- `an_acting_tab_writes_from_inside_its_page_with_the_page_s_own_token_which_never_leaves_it` (engine): three token places, JSON and form; an application that quotes a refused body back, token and all, is handed `[redacted]`; without the token the stand answers 403; a token not on the page sends nothing; a page with no origin sends nothing. `an_observing_tab_has_no_write_and_its_browser_fails_one_made_beneath_it`. `a_write_names_only_plain_names_and_no_header_the_browser_sets`.
- `a_write_entry_states_its_token_its_answers_and_its_read_back_or_does_not_compile` (web UI): the compiled steps, every refusal above by name, and the drafter's refusal of a write entry.
- `the_anti_forgery_case_a_write_lands_once_with_the_page_s_token_and_reads_back_equal`: without the ledger's token, `intent_missing`; the unmarked request, `step_not_usable`; with it, one write, one token used, the read-back in the observing tab equal to what was sent and to what the stand holds, an absent record absent; with the token step taken out (`anti_forgery: none`), the stand refuses and stores nothing, and the write is in doubt; no token of any page in any value, capture, failure, or log file, by bytes.
- `each_fault_of_a_write_stops_by_name_unsent_or_in_doubt_as_the_request_left`: a key that leaves its segment, unsent; a refused note, `rejected`, answered, nothing stored; a stale page (its token used), in doubt and nothing more stored; a lost connection, in doubt, the browser's second sending refused, the read-back reading what landed; a run that may only look, `read_only_posture`, unsent; an expired session (the page answered by the sign-in page), `unexpected_page`, unsent.
- The test application has case 5: `/orders/{order_id}/note`, `GET` and `PUT /api/orders/{order_id}/note`, and `/__control/notes` (`TestApp::stored_notes`).
- The pack declares `anti_forgery_not_found` (`drift`) and `anti_forgery_unreadable` (`unknown_variant`).

## Not done

- POST, PATCH, DELETE; `create`, `upsert`, `delete`, `submit`; `path_params` and `query`; a number with a fraction in a body; an answer of 204 with no body.
- The token is never registered with the run's redactor, because it never reaches the engine; the kernel has no call by which a driver registers a secret it learns in a step. If one is added, a token that must leave the page could be registered there.
- The browser's own profile holds the token's cookie and its cache may hold the page, as it holds the session: the engine's own folder, not a capture.
- An expired session is told only as a page answered from another path; the session's provider is not asked (`detect_expiry`), so the stop is not `session_expired`.
- A blocked surface during the write's steps is the origin guard of decision 0143, not tested again here.
- The product's own test, through the engine loop with approval, is the product crate's to write.

## Revisit if

The browser engine offers a request that is never sent again by the browser, or the kernel lets a driver register a secret it learns during a step.
