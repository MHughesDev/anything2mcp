# 0156. The clients are generated from the served document, and reach Windows by the pipe

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Settles:** roadmap package 5.4 (the clients), the open points of [decision 0135](0135-the-wheel-carries-the-binary-and-a-thin-client-and-npm-uses-platform-packages.md) about generated methods, the Python client on Windows, and `a2m` from pip on Windows. Partly supersedes 0135, which said the generated methods wait for a step that writes the faces out and that the Python client is not built on Windows.

## Context

Spec section 605 says a client is generated from the action registry and that CI fails when a generated file differs. Decision 0135 left the client with one `call(action, input)` because the binary had no step that writes the registry's faces out. The engine does serve one: an OpenAPI document at `GET /api/v1/openapi.json`, made from the registry's route faces, with the action's name in an `x-action` field of every operation. Its 91 actions each have a `POST /api/v1/actions/<action>` operation with a request schema (every one closed: `additionalProperties: false`) and a summary.

## Decision

**Generate from the served document.** `bindings/python/tools/openapi.json` is a saved copy of the document, written with sorted keys by `tools/fetch_openapi.py` from a running engine (taken from the debug binary of this commit; fetched twice, byte for byte the same). One generator per language reads it: `tools/generate_actions.py` writes `src/anything2mcp/_actions.py`, and `bindings/npm/scripts/generate-actions.js` writes `actions.js` and `actions.d.ts` in the launcher's `client/`. The generated files are committed. A test in each language fails when the committed file differs from what the generator writes, so a method cannot drift from the saved document. When the engine's actions change, the document is saved again and both generators are run. Neither generator guesses: a request body with a field it does not name, an action with no summary, or an enum it cannot read stops it. *Instead of:* a new command in the binary that writes the faces out, which is a change to the product crate and the action registry for a file the engine already serves; and the `sdk_methods` of `a2m-actions` named in 0135, which the document carries as well, in a form every language can read.

**Thin methods.** A generated method names its action and passes its input to `call`. Python: `client.tool_call(tool=..., input=...)`, keyword-only, `Optional` for what the schema does not require; a field named `from` is `from_` and is sent as `from`; a field left as `None` is left out of the request. Node: `client.toolCall({ tool, input })`, one object, with a type per action in `actions.d.ts`. The answer is the engine's `Response`, as `call` returns it. Every action is reached by the one route `POST /api/v1/actions/<action>`, not by the shorter routes some actions also have. Nothing is decided in a method.

**Standard library only, both languages.** No dependency for the generators or the clients. The Node client needs no compile step, because the declarations are written by the generator beside plain JavaScript. *Instead of:* generating with a schema-to-code tool (a dependency tree per language, a result shaped by someone else) and shipping TypeScript that needs a compiler. The declarations were checked once with `tsc` 5.6.3 under strict settings, including that a missing required input and an unknown input are refused; that check is not in CI, which has no `tsc`.

**The Node client lives in the launcher package**, as section 605 says ("the `anything2mcp` command and a TypeScript client"): `anything2mcp/client/`, with `main`, `types`, and `exports` in the launcher's manifest and `client/` in `files`. `bin/anything2mcp.js` does not load it, so the start time of the command is unchanged. *Instead of:* a second package `@anything2mcp/client`, which would be a ninth name for the owner to create and publish at the same version, for no gain.

**The Python client on Windows uses a named pipe through `ctypes`.** `_winapi` has `CreateFile`, `ReadFile`, `WriteFile`, and `WaitNamedPipe`, and not the two things the check needs: the process that serves a pipe (`GetNamedPipeServerProcessId`) and the user of a process (`OpenProcessToken`, `GetTokenInformation`, `ConvertSidToStringSidW`). `ctypes` is public, standard on Windows, and has all of it, so one module does everything. The client finds the pipe as the engine names it (`\\.\pipe\anything2mcp.<SID>.<tag>`, the tag being the first 16 hex digits of the SHA-256 of the runtime directory's text, joined by Windows rules and not normalised). It opens the pipe at the identification level so the engine cannot act as the client, reads the user of the server process, and refuses with `peer_not_allowed`, before sending a byte, unless it is the client's own user. A server whose user cannot be read is refused. A busy pipe is waited for with `WaitNamedPipe`, a bounded number of times. This is the check the engine's own client makes. Two limits: a read on the pipe has no timeout, so `timeout` is not honoured on Windows; and none of this has run on Windows yet (below).

**The Node client on Windows refuses by default.** Node's standard library cannot say who serves a pipe, and a client that connects without the check would let a program that made the pipe first answer in the engine's place. So `connect` on Windows rejects with `client_not_built` unless the caller passes `verifyPipeServer` (a function that resolves to true only when the server is the user's) and `sid`. The transport, the pipe's name, and the hello are built and tested; the check is the one thing missing. *Instead of:* starting `whoami` or PowerShell from the client (a process started by a client, slow, and it still cannot read the server's user without compiling code at run time); a native add-on (another language, a build per platform, a dependency); connecting with no check (rule 2: safe first). A later package can supply the check.

**`a2m` on pip for Windows is a command file.** `wheel-data/scripts/a2m.cmd` runs `anything2mcp.exe` beside it with every argument (`%*`) and returns its exit code, and stops with the same message and code 4 as the Unix script when the program is missing. pip installs a file from the wheel's data `scripts` folder into the environment's scripts folder as it is, so the file is the command. It is also carried by the wheels for macOS and Linux, where it does nothing, because maturin's data folder is the same for every target. `.gitattributes` in `bindings/python` keeps its line endings as CRLF. *Instead of:* a console script (maturin refuses one beside a binary, research note 21); a second `.exe` (doubles the wheel).

## Consequences

- **Proven here (Linux):** both generators and their drift tests; the typed methods against a fake engine and against the real binary, in both languages; the Windows pieces that are plain code (the pipe's name, the runtime directory text, framing, the whole HTTP exchange over a stream, the busy, missing, and foreign-server cases against a stand-in for the operating system); `maturin sdist` carries `a2m.cmd`.
- **Not proven:** every call into Windows (`ctypes`), the real pipe, the real server check, and `a2m.cmd` running. The wheel was not built, because it needs the product built. The next Windows run of the `bindings` job must show the tests marked Windows-only passing, `a2m.cmd --version` printing the product's version, and both tests against the real engine over its pipe.
- The pip wheel on every platform now carries `a2m.cmd`.
- The document is large (about 485 kB). A change in the engine's actions shows as a change in it and in three generated files.
- The README of `bindings/`, both package READMEs, and spec section 605 say what is built.
