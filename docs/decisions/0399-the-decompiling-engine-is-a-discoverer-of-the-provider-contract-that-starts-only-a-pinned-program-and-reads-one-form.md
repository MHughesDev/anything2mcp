# 0399. The decompiling engine is a discoverer of the provider contract that starts only a pinned program and reads one form

**Status:** Accepted. Design decision, made under [decision 0294](0294-the-owner-hands-the-open-questions-to-the-agents.md). The owner had not read this record when it was merged. Builds point 4 of [decision 0276](0276-what-the-scout-may-learn-from-a-program-itself-and-by-which-means.md), package X6, after [H-48](../hypotheses/H-48-result.md) left the engine as written.

**Date:** 2026-11-24

**Changes:** `a2m-provider` gains the module `decompiler` (`Decompiler`, `DecompilerSpec`, `DecompilerDiscoverer`, `DecompilerDescriber`) and five failure codes: `decompiler_not_installed`, `decompiler_not_pinned`, `decompiler_spec_invalid`, `decompiler_failed`, `decompiler_output_unknown`. The test stand `targets/example-decompiler` stands in for an installed engine. `a2m-engine` changes in its tests only. Nothing in a pack, in `a2m-actions`, or in the product crate.

## Decision

1. **The engine is a discoverer, as any other.** A pack that wants decompiled text registers a `DecompilerDiscoverer` and its manifest declares it: the kind `decompiled_function`, the source `artifact`, the level `inferred`, the file name `decompile`. The discovery job of the engine runs it beside the pack's other discoverers, under the same bound of time and size, and takes what it finds through the same sink. There is no second route from an engine's text into the product.
2. **The person installs it and names it; the product never fetches it.** A `Decompiler` holds the place the person named (none by default) and the digests the product pins, each the digest of one release of the program. Before every start it digests the file at that place. With no place, or no file there, it fails with `busy`/`decompiler_not_installed`; with a digest that is not pinned, `policy`/`decompiler_not_pinned`, and nothing starts. The failure of one discoverer in a job is reported and the job goes on to the next, so with no engine installed the scout says so and carries on with everything else. The digest that was looked at is the digest the supervisor requires of the file it starts, so a program replaced between the look and the start is refused too.
3. **It is started as any program the product starts.** The path is checked by `check_program` as a `Program` (a shell, a launcher, an interpreter, and a file another user could change are refused), started by the supervisor with no environment but the pairs the spec lists, no standard input, a time limit, and a bound on what is kept of its output. A variable of the engine's own (`A2M_`) is refused as for any program.
4. **It is handed a file and never a process.** The one thing the engine program is told is the path of a regular file, as the one argument the spec marks `{file}`. The path is a `CheckedPath` that a discovery was handed from the project's `sources` folder; the function takes no process identifier and has no form that does. The file is read as bytes, for its digest, and is never started, loaded, or opened for writing.
5. **Its output is read in one form, and what is not in it is a stop.** One JSON object to a line: any number of `{"function", "address", "text"}`, then once `{"end": true, "functions": n}`. A line of another form, an end line whose count is not the number of functions printed, text after the end, a missing end line, or an exit that is not success is a named stop (`decompiler_output_unknown`, `decompiler_failed`) and none of what was printed is used. Output cut at its bound is not a stop: the whole lines before the cut are kept and the finding says it is partial.
6. **Its facts are `inferred`, from the source `artifact`.** The row of the roadmap said "stored at `discovered`", and decision 0276 said "never above `discovered`". The kernel gives `discovered` only to what the running system was seen to do (`Source::highest_level`), and a decompiler reads a file and sees nothing run, so a finding of the engine's text is at `inferred`, the same as the reader of a binary's plain facts, which is below the limit 0276 states and is what the kernel allows. The finding carries the digest of the engine that made it as `produced_by.component`, the limitation `not_exercised`, and, where output was cut or dropped, `truncated`.
7. **Nothing it prints reaches a run.** A finding is evidence for a person or an agent that drafts. No plan, step, or operation reads one. The describer states how many functions there are and lists the engine's text apart as untrusted, never in its own sentence; the text of each finding passes the redactor when the finding is made and again in the describer; and the engine's sink holds back a finding that still holds a registered secret.
8. **The first engine's program is not named in this record.** What makes the first engine's output into the form of point 5, and its pinned digests, are data a release carries once a person has tried the engine on each system. The contract here asks of an engine one thing: that its program, or an adapter the person installs beside it as a program of its own form, prints the lines of point 5 for the file it is handed. The headless launcher of the first engine is a script; `check_program` refuses scripts as programs, so a release that pins it names the adapter's compiled program, not the script.

## Alternatives

| Alternative | Why not |
| --- | --- |
| The engine as a pack of its own, with a driver | It has no surface to drive; it only reads a file. A discoverer is the contract's one place for it, and the findings gain the manifest's check of kind and level for nothing |
| Take the pinned digests and the place from the pack's manifest, and use the scoped supervisor | A manifest names a program's path when it is written; here the person chooses the place. The unscoped supervisor with the digest on the program is the same check, made on the place the person named, and the pins are the data a release carries |
| Store the findings at `discovered` as the roadmap said | The kernel refuses it for a source that is not the running system, and it would tell a drafter more than a file's text shows |
| Run the engine on a process, to read its memory | It would start or attach to what the person is running. Rule 5 and decision 0276 point 9 rule it out; the file is the whole input |
| Parse any output and skip lines that are not understood | An engine that changed its form would be believed in part. Unknown means stop |

## Proof

`crates/a2m-provider/tests/decompiler.rs`: no engine installed, or none at the place, fails by name and starts nothing; a spec that pins nothing or names no `{file}` is refused; a pinned engine is started once with the file's path as its only argument, and the command-line stand used as the inspected file is never started; a program replaced after it was pinned, and a digest that is not the pinned one, are refused with nothing started; a folder is not handed over; a failing engine, a line that is not JSON, and a missing end line are named stops; output beyond the bound of functions is counted and dropped, and output cut at its byte bound is said; a variable of the engine's own is refused. `crates/a2m-engine/tests/decompile.rs`, through the discovery job: with no engine the other discoverer's finding stands and the engine's absence is reported; an unpinned program is not started; the findings are `artifact`, `inferred`, carry the engine's digest, and nothing of their text appears in a result, a trace, or a capture of the job; a registered secret the engine prints is not kept.

## What this leaves open

Wiring in the product: the settings that name the place and the pack that registers the discoverer with the host's supervisor, which are changes to `a2m-actions`, a pack, and the product crate. The adapter and the pinned digests of the first engine, which need an engine installed on each system. The same form for a decompiler of .NET and one for Java, which the contract serves and nothing yet tries. A real engine has not been run: nothing in this change is proven against one.
