# 0183. The web pack drafts a read of each table a snapshot names

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the drafting rules and the driver of [`a2m-pack-web-ui`](../architecture/crates/a2m-pack-web-ui.md), a test of [`a2m-pack-web-probe`](../architecture/crates/a2m-pack-web-probe.md), and sentences of spec sections [301](../spec/3-packs/301-the-web-pack.md) and [402](../spec/4-building-tools/402-the-scout-and-who-does-what.md). Answers, for the web pack, what [decision 0179](0179-what-each-pack-drafts-so-that-a-scout-ends-with-reads-that-work.md) left: the web pack had no drafting rule, so a scout of a web application ended with nothing to try.

## The route, and why it was taken first

Of the two routes, a read over a screen and a read over a request the page made, the code as it stood supported the first with less new surface. The probe's `screen` finding already keeps what a screen model needs: each element's role and depth, and the name of a table and of each column header. The `ui` driver already reads a table by its declared headings and gives each column as a list. The second route needed what is not there: `web_capture` sees only the documents the tab is sent to, not the requests a page's own scripts make (the base has no stream of exchanges), and the pack has no in-page request mode (`page_http` is not built). It is also the one only this pack can do. So this slice builds the first route, and not the second.

## Decision

| Question | Decided | Alternative weighed |
| --- | --- | --- |
| What is drafted from a `screen` finding | For each table the page names that can be read row by row (one row of headings, one cell under each heading in every other row, no table inside it), inside a part of the page the snapshot names once (`main`, `region`, and the like): a screen, `screens/{page}_{table}.yaml`, and a read, `operations/{page}_{table}_list.yaml`, named `{target}_{page}_{table}_list`. The screen's `reach` is the page's path as observed; `ready` is that the table shows; its `rows` locate the table by role and name, take that part of the page as the fingerprint, declare every heading in order, and name one column for each heading. The read is `effect: read`, `verb: list`, no input, one list output for each column | Drafting the page's labelled values as fields. The test application shows them in a description list, whose terms the finding keeps as a type only and whose definitions have no role a locator can name; nothing could locate them by role and name |
| Locators | Role and name only, as the finding states them; never a selector, a label, or a position | Adding the label as a second locator, as the hand-written screens do. The finding does not say which element a label belongs to |
| Types | Every column and output is `untrusted_text`. The finding's types of what filled a cell are one sample's, which nobody stated | Typing a column by the type the cells showed: a guessed number, which rule 7 refuses |
| What is never drafted | A field, an action, a form, or a button, whatever the page holds; a table with no name; a column whose heading another column shares, or whose name another heading also gives; a page whose snapshot was cut short; a page of an origin that is not exactly one `web` surface of the target; a page whose path holds a character a screen's address cannot hold as written; an example; a test. A drafted screen with an action is refused by the drafter, as before (tested for this pack's kind) | Drafting a form's fields as a read of what it shows. A form is how a page writes, and section 402 leaves every action, and so every form, to the developer |
| Two tables with one name | The screen is drafted once with an open question in place of its locator, naming the page and saying that more than one table has that name; no read is drafted over it, since a screen that holds a question does not compile | Taking the first. That is a guess (rule 7) |
| The screen's address | The page's own path. Joining the snapshots of several pages of one screen into one address with placeholders is screen matching, which is not built; a rule sees one finding, so each page drafts its own screen, and the name is made from the whole path so that two pages never draft one file. A drafted read of `/orders/A-100` reads that order's line items and is named for it | Making identifier segments placeholders, as the design had it. Two pages of one screen would each draft the same screen, and the duplicate stops the whole target compiling. `A-100` is not an identifier by the probe's format rule either |
| Where a read that may only look runs | In an observing tab. In discovery, and in the sandbox where no declared test record may be written, the driver opens its tab through the base's observer, so the browser fails every request of the page whose method could change the system; the run stops on it, `unknown_variant`, `unexpected_page`. Every other run has an acting tab, as before | Keeping one acting tab for every run, with the posture guard alone. The guard stops the driver's own inputs; it does not stop a page's script that writes when it loads |
| How the two crates prove one path without naming each other | The snapshot of `/orders/A-100` is kept as data in `a2m-pack-web-ui`'s `tests/fixtures/findings/`. A test of the probe holds that discovery of the page gives exactly it, the same twice; a test of the drafting rules drafts from it, compiles, and runs the read | One test of the whole path. It needs a crate that names both, which only the product crate may: the test is owed there |
| The `screen` finding kind | Not declared under `reads` in this pack's manifest: a registry with only this pack would then report a missing owner. With no discoverer of the kind, the rules are never called | Declaring it, as the probe declares `endpoint` |

## Consequences

- Against the test application, the snapshot of the page of order `A-100` drafts one screen and one read; both compile in draft mode; the read, run through the driver's handle in a run that may only look, returns the item code, description, quantity, and length of each line item exactly as the control interface reports them, and nothing is written. Drafting twice gives the same bytes (`a_snapshot_of_a_page_that_shows_an_order_drafts_a_read_that_reads_what_it_holds`, with `a_page_that_shows_an_order_gives_the_screen_the_web_pack_drafts_from_the_same_twice` in the probe).
- A drafted screen whose heading the page does not show stops the read with `drift`, `fingerprint_mismatch`, and one whose table the page does not show stops it with `unknown_variant`, `unexpected_page`; neither takes the nearest match. A page that moves to another origin is stopped by the existing rule, held for hand-written screens by `a_page_that_moves_to_another_origin_is_stopped_before_anything_is_typed`.
- A run that may only look, on a page that sends a write when it loads, stops, and the write never reaches the application (`a_run_that_may_only_look_has_a_tab_that_cannot_write`) Built with an acting tab, as before, the same read succeeded.
- A scout with no focus snapshots the start page and the pages its plain links lead to, and each page with a named table drafts its own read: the list of orders gives `example_orders_all_orders_list`. The names are provisional and hold the page's own words, a record's number among them; a person renames them. This was not run here.
- Not built: the read over a request the page made, which waits for the base's stream of exchanges and for `page_http`; fields and labelled values; screen matching and keys; a `site_tools` read.
