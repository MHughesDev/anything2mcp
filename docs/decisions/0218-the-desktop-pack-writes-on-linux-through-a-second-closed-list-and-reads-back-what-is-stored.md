# 0218. The desktop pack writes on Linux through a second closed list, and reads back what is stored

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the desktop pack's build order step 5, its registrations, its failure table, and its invariants in [its design](../architecture/crates/a2m-pack-desktop.md); [spec section 305](../spec/3-packs/305-the-desktop-pack.md) (the build order, the entry bar, the failures). Carries out, for Linux writes, [decision 0208](0208-the-first-release-reaches-what-the-persons-machine-reaches-and-serves-on-that-machine-only.md), which puts changing an application on the person's machine in the first release. Builds on [decision 0198](0198-the-desktop-pack-reads-linux-applications-through-a-look-only-back-end.md) (the look-only back end) and follows [decision 0112](0112-the-ui-driver-as-built-five-step-kinds-and-a-commit-that-waits-for-its-confirmation.md) for the shape of a write.

## Context

The pack read and never wrote: its back end had one closed list of members that only ask. A write through a window is hard for reasons a web form shares and some it does not: what is typed into a field is not what is stored; the application may change a value as it is typed (cut it, format it); it may refuse a value and say so; Save may store and then the application may exit before it confirms; a second window of the same program may hold a field of the same name; and a person's screen is one resource that two runs must never type into at once.

## Decision

1. **The stand holds the hard part.** Case 28 (`targets/example-desk`) has edit fields (`New customer`, `New status`) apart from the labelled values that show what is stored (`Customer`, `Status`). Only Save stores, and only values its own rule takes (a status of `open`, `held`, or `closed`; a customer that is not empty); otherwise it shows a message under `Problem` and stores nothing. `New customer` cuts text past 24 characters. Its control interface switches on, for the next press: Save that stores nothing and says nothing; Save that stores and then the application leaves the bus before it confirms (`Desk::restart` starts it again with what it stored); a confirmation that arrives late; and, until the stand ends, a read-only field and a second window with a `New customer` field of its own. `Truth` reports what is stored, how many times Save stored and was pressed, and every value set into each field, with its window. The Windows half of the stand writes nothing; its `Truth` has these fields empty.
2. **A second closed list, reachable only through one function.** The Linux back end's acting half is `Hands`, which only the driver's `set` and `invoke` make, over the proof of the application's process taken at prepare. It sends through `act_call`, the one function that sends a member of `ACT_MEMBERS`: `EditableText.SetTextContents` and `Action.DoAction`. Tests hold that no member of the reading list is in the acting list and that the reading path's own check refuses every acting member; that each acting member is one of AT-SPI's members that act; that neither list has a member that makes a key or pointer event; and, from the module's source, that `act_call` is called only inside `Hands`. Reading which actions an element offers (`Action.GetActions`) joins the reading list. The value interface is not used: no control of this version needs it, and its value is a floating-point number, which a write of a business value must not go through.
3. **Before every act, the proof again.** `set` and `invoke` find their element in a fresh walk of the window the `goto` found, and then prove that the element is the application's and that the bus daemon still says the application's connection is owned by the process proven at prepare, with the same start time (from the process table), the same program, and, when the surface states one, the same digest. Otherwise `unknown_variant`/`application_not_proven`, nothing sent. A password field is never set: a field whose locator names `password_text` is refused at compile time (`desktop.password_set`), and an element that holds a secret is refused at run time (`policy`/`password_set_refused`).
4. **`update` and `upsert` lower as `ui` writes do.** `goto`, `wait`, one `set` per field, and the `invoke` of the binding's action, marked as the commit point when the action declares `commits: true`; then a read-back: `goto`, `wait`, `read` on the screen `read_back` names, a window reached afresh and read where it shows what is stored. There is no separate `locate` step: each `set` and `invoke` locates its own element (decision 0112). The committing `invoke` refuses to act when the window already shows the action's confirmation or a declared refusal; subscribes to the application's signals and to the bus's word that its connection ended before it acts; and then waits, by those signals only, for the confirmation, a refusal, the application's exit, or the deadline. When the operation has a key, every `wait` carries it and the driver stops (`unexpected_page`, nothing sent) unless the window shows exactly that record in the screen's field of the key input's name; a screen that shows no such field does not compile (`desktop.key_unshown`). The window has no state for a record that is not there, so `upsert` changes the record the window shows, as `update` does; `create`, `delete`, `submit`, and `upload` are not built.
5. **Every value written is read back, or the operation says it cannot be** (entry bar item 2). A field written that is not an output of the operation, and so is never read back, compiles only when the operation declares `effect: irreversible` (`desktop.unreadable_write`). A binding with no `read_back` is `irreversible` by its least effect. Values are compared by the engine after normalization, as for every pack.
6. **Every failure says whether the act was sent.** Before a field is set: `field_read_only`, `unexpected_control`, `password_set_refused`, `locator_*`, nothing sent. A field that, after the set, holds another value than the one set: `unknown_variant`/`value_not_held`, answered, before Save. A refusal the window shows after Save: `rejected`/`app_validation_error`, answered, with the application's words carried as `said`, never as the sentence. Save sent and no confirmation by the deadline, the application exited, or the window could no longer be read: `possible_commit`/`no_confirmation`. A resume reads the stored value before it would write again: where Save stored, it finds the value and presses nothing; where it stored nothing, it writes once.
7. **One desktop at a time.** The mode declares `exclusive = "screen"`, so the scheduler holds a write's surface alone. The driver also holds its one desktop from a write's first `set` to the end of its committing `invoke`, waiting until the step's deadline and then stopping as `busy`/`session_in_use`, nothing sent: the kernel's exclusive key is per surface, and two surfaces can show windows on one desktop. Reads do not take it.
8. **Windows and macOS stop before anything is sent.** There a `set` or `invoke` in a posture that may act is `busy`/`writes_not_built`, nothing sent; Windows' reading half has not yet run once, and its acting half is a later package.

*Instead of* synthetic key presses or pointer clicks: they go to whatever window has the focus, cannot be bound to an element, and are refused until a test shows one can be (decision 0198). *Instead of* reading back the field the value was typed into: it holds what was typed whether or not anything was stored, so a Save that stored nothing would read back as landed; the stand's silent Save proves the difference. *Instead of* relying on the scheduler's key alone: it is per surface, and it is not in the pack's tests' reach; the driver's hold is proven to keep two concurrent writes' sets apart, and a test without it shows them interleaved.

## Consequences

- The pack's tests (`tests/write.rs`) prove, against the stand: a preview that acts on nothing, an act refused without the ledger's token, one approved write stored once and read back afresh, both resumes, a late confirmation ended by its event, each stop with whether it was sent, a second window, and two concurrent writes.
- The pack's payload format is 2: a screen has `actions` and `variants`, and `set` and `invoke` carry payloads.
- Open: the value interface for number fields; a field the application formats as it is typed (a date, a quantity), which needs a control with its own comparison rather than `value_not_held`; a refusal declared without a visible element; a key per desktop in the kernel, for a scheduler that serializes across surfaces.
