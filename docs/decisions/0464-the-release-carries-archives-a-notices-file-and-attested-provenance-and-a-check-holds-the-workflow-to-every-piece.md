# 0464. The release carries archives, a notices file, and attested provenance, and a check holds the workflow to every piece

**Status:** Accepted. Design decision. The owner had not read this record when it was merged. It adds to [decision 0186](0186-the-release-workflow-builds-checks-and-publishes-the-npm-packages.md) and answers what that record left open; it changes nothing in the product's code.

**Date:** 2026-11-25

**Changes:** the release workflow, [RELEASING.md](../../RELEASING.md), [publishing setup](../plan/publishing-setup.md), and [spec section 605](../spec/6-running-it/605-packaging-and-release.md), under "Standalone installs" and "The release pipeline". Settles the question section 605 left to package 5.5, whether to adopt the `dist` tool for the standalone installs.

## Context

Package 5.5 asks for a release pipeline for pip, crates.io, npm, and standalone binaries, signed, with a bill of materials; package R1 asks for a changelog, a notices file of third-party licence texts, and a wheel that carries the binary. The workflow built and checked the wheels and the npm packages, and a plain-text list of the crates per target. Decision 0186 left open: signing, build provenance for the binaries, the release page with archives and checksums, the licence texts, and a bill of materials in an exchange format, for which it named three tools and chose none. Nothing in the workflow failed when one of these was missing.

## Decision

1. **A standalone archive per target, from the wheel's binary.** The job `archives` (eight matrix entries, on Linux) takes the one `anything2mcp` out of the wheel of the same target, as `npm-platform` does, and packs it with `tools/release_files.py archive`: a `.tar.gz` for Linux and macOS holding the program, `a2m` as a link to it, `LICENSE`, and `THIRD-PARTY-NOTICES.txt`; a `.zip` for Windows holding `anything2mcp.exe`, the wheel's `a2m.cmd`, and the same two texts. Members are sorted, owned by nobody, and dated by the commit, so one binary gives one archive byte for byte. The wheel, the npm package, and the archive of a target therefore carry one binary, built once.
2. **`dist` is not adopted.** It builds its own binaries from source per target, so a release would hold a second set to audit and attest beside the wheels', which spec section 605 refuses ("Nothing is recompiled per package"), and its workflow would be a second file that the registries' trusted publishers do not name. The archives are hand-written in about a hundred lines of Python. The shell and PowerShell installers, Homebrew, winget, the container image, and the offline bundle stay unbuilt; each is weighed again when it is wanted, and `dist` with it.
3. **The bill of materials in an exchange format is maturin's.** maturin 1.16, the build tool already pinned, writes a CycloneDX 1.5 bill of the crates it compiled into each wheel, at `.dist-info/sboms/anything2mcp.cyclonedx.json` (found by building a wheel on 2026-11-25). The job `release-files` takes it out of each wheel as `anything2mcp-<version>-<target>.cdx.json`. No new tool is added, which answers the question decision 0186 left open. The plain-text lists of `bill-of-materials` stay, as a run artifact.
4. **The notices file is written by `tools/notices.py`, and checked in.** It lists every third-party crate that `cargo tree` gives for the product crate, normal dependencies only, on any of the eight targets (the set the bill of materials lists), with its licence and repository, and then every distinct licence text in those crates' published sources once, under the crates that carry it. Seven crates of one project publish no licence text; for a crate whose expression offers MIT, the tool supplies the MIT text from this repository's `LICENSE`, with a copyright line naming the crate's authors and repository, and says that it did. A crate with no text and no MIT choice stops the tool. The file is kept at the root and, byte for byte, in `bindings/python/`, because a wheel's licence files must lie under its project folder; the audit holds the copy to the root. CI's `dependencies` job runs `python3 tools/notices.py check` on every pull request, so a change to `Cargo.lock` that leaves the file behind fails there. The wheel names it in `license-files`, the npm platform packages carry it, and so does each archive.
5. **Every file is attested, not signed with a key.** The job `publish-release` attests the build provenance of every file `SHA256SUMS` names, with `actions/attest-build-provenance` v4.2.2, pinned by its commit `4d101475d8b20a2381f78447822ac1eab6504dd8` (checked against the action's repository on 2026-11-25; its inner `actions/attest` is pinned by commit too). The statement is signed with the run's short-lived credential through Sigstore and kept by GitHub and in the public transparency log; `gh attestation verify <file> --repo MHughesDev/anything2mcp` checks one. No signing key exists to be kept or lost. PyPI's attestations and npm's provenance stay as they were, on the registries' side.
6. **The release page comes first, then PyPI and npm.** `publish-release` runs only when `decide` says to publish, in a GitHub environment named `release`, with `contents: write`, `id-token: write`, and `attestations: write` on that job alone. It checks the files against their checksums again, attests them, and makes the page `v<version>` with every file and the changelog's section for the version as its notes, marked a pre-release before 1.0. A run started by hand makes the tag on the commit it checked. Run again, it adds a file the page lacks and never replaces one. `publish-pypi` and `publish-npm` now wait for it, which is spec section 605's order; they still do not wait for each other.
7. **A published version has its changelog.** `decide`, when it is to publish, refuses a version unless `CHANGELOG.md` has a section headed `## [<version>] - <date>` that lists something, a link line for it at the foot, and an empty Unreleased section (`python3 tools/release_files.py changelog <version>`).
8. **The whole set is checked on every pull request that touches it.** The job `release-files` gathers the eight archives, the eight wheels and the source distribution, the nine npm packages, the eight bills of materials, and the notices file, writes `SHA256SUMS`, and fails unless each file is there and no other, the checksums are each file's own, every wheel, platform package, and archive carries `LICENSE` and the notices file as the tree has them, each holds one binary, and for each target its three packages hold the same binary. It runs on pull requests, as the npm jobs do, and publishes nothing.
9. **The workflow is held to its pieces.** `python3 tools/release_files.py workflow`, in CI's documents job and in `tools/gate.py`, fails when a job of the release is missing, when a matrix leaves out a target or adds one, when the pull-request paths leave out a file the release is built from, or when any job that may write outside the run is not one of the three publish jobs, gated on `decide`, in an environment, and after every file is built and checked.
10. **crates.io stays as decision 0242 left it.** The product is not published there (point 16), so package 5.5's "crates.io" is met by that decision, and no job is added.

## Alternatives weighed

| Alternative | Why not |
| --- | --- |
| `cargo-about` for the notices file | Not installed, and a new tool in CI needs the same checks as a new dependency. The tool reads cargo's own output and the crates' own files, in the standard library, and its output is held to `Cargo.lock` on every pull request |
| Write the notices file at release time only | Nobody would read it before a release, and a crate with no licence text would be found on the day of the release |
| Sign with a key (minisign, or cosign with a key) | A key must be kept, rotated, and never leaked, and the owner would hold one more secret. Attestations need none, and are what `self.update` can check later |
| One job per piece of the publish (attest, then the page) | Two approvals for one act, and nothing gained: the steps are pinned, and the job's three permissions end with it |
| A draft release page that a person then publishes | One more step for the owner, and the registries would publish before the page did |
| `cargo-cyclonedx` for the bill of materials | maturin already writes one, from the build itself |

## What is owed

- **Nothing here has published, and `publish-release` has never run.** Unproven until the first release: that the attestation action accepts `subject-checksums` as written; that `gh release create` makes the tag on a run started by hand; that maturin writes the bill of materials into the wheels built on macOS and Windows as it did on Linux (`release-files` fails if not).
- **The owner's setup:** the GitHub environment `release`, with required reviewers if a person should approve, as for `pypi` and `npm` ([publishing setup](../plan/publishing-setup.md)).
- **Not built:** the shell and PowerShell installers, Homebrew, winget, the container image, the offline bundle, and `self.update`'s check of a signature. The `a2m.cmd` in the Windows archive is the wheel's; its message for a missing program names a pip reinstall.

## What would reopen it

A registry or a person's tooling that needs a signature file beside each file rather than an attestation; a second binary in any package; maturin ceasing to write the bill of materials; or an installer route that needs `dist`.
