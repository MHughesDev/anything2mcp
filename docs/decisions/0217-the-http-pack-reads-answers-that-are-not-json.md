# 0217. The HTTP pack reads answers that are not JSON

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the endpoint catalog of [`a2m-pack-http`](../architecture/crates/a2m-pack-http.md) (a new key `answer`), its driver's `validate` and `extract` steps, one failure code, and the test application's routes under `/views/`; sentences of spec sections [303](../spec/3-packs/303-the-http-pack.md) and [106](../spec/1-product/106-what-it-latches-onto.md), the [file formats](../reference/file-formats.md#endpointsyaml), and the [coverage map](../plan/coverage-map.md). Answers finding 3 of the [coverage review of 2026-11-18](../plan/coverage-review-2026-11-18.md).

## Decision

The owner's scope is anything the person's machine can reach ([decision 0208](0208-the-first-release-reaches-what-the-persons-machine-reaches-and-serves-on-that-machine-only.md)). The pack read JSON answers only, so feeds, XML services, object-store listings, plain-text status pages, and many devices' own pages could not be read. The lead ruled that an endpoint declares the form of its answer; this record says what was built and what the building showed.

| Point | Built | Alternative weighed |
| --- | --- | --- |
| 1. The form is declared on the endpoint | `answer: {form: json \| xml \| text \| bytes, content_type: [...]}`. JSON is the default and is read as before; an endpoint that declares nothing is written into the plan byte for byte as before. An answer that is not JSON has no `response_schema`: its **record**, the values the answer declares, is the shape the `extract` paths are checked against when the target compiles, and what the driver checks and takes values from at run time. So the extraction, the version precondition, the absent status, and the read-back are the same code for every form | Converting a whole XML document to JSON and checking it against a `response_schema`. It builds the whole tree in memory, has no single mapping (attributes, repeated elements, mixed content, namespaces each need a convention), and checks the shape of a document nobody declared |
| 2. `xml` | `namespaces` (a prefix-to-URI table the catalog owns) and `fields`, each a `path` or an `each`. A path is steps from the root element, joined by `/`: a name, or a declared prefix, a colon, and a name; the last may be `@` and a name, for an attribute; otherwise the value is the element's text, its two ends' white space removed. `each` gives a list, one entry for each element the path matches: with `fields`, a record of paths from that element (`@code`, `o:quantity`); without, the element's text. A path that matches nothing, for a field not marked `required: false`, and a path that matches more than one place, for one value, are `drift`, `response_schema_mismatch`. Values are text, typed by `type: string \| integer \| number \| boolean`, and an output takes them by the same rules as a JSON value of that type (an exact number from text through the decimal type, never a float) | A general XPath. Its functions, predicates, and axes make a path that can match anything a document holds, and its engines build trees. The closed language covers the stand's views and the feeds the coverage review names; a nested `each`, the text of the repeated element beside its attributes, and a choice by an attribute's value are not built |
| 3. The XML reader | `quick-xml` 0.42.0 (MIT, published 2026-08-22, released every few weeks this year), no default features; its one dependency, `memchr`, was already in the tree. It is a pull parser: the pack keeps only the names of the open elements and the declared values. Without its `encoding` feature it reads UTF-8 only; the pack checks the declaration's encoding and the charset of the content type. It does not process a document type; the pack refuses one on sight, with the new code `unknown_variant`, `document_type_refused`, before any value is read. It reports each reference as an event, so the pack reads character references and the format's five names and refuses any other. It never opens a file or an address. Bounds: the answer's existing ceiling, `max_depth` (64 unless the endpoint says) and `max_elements` (100,000), each past its bound `unknown_variant`, `response_too_large`; the reader's own limit of 128 namespace bindings in scope. `cargo deny check licenses bans sources` passes | The XML reader of `a2m-sources`, which reads workbook parts. It is private to that crate and drops namespaces; making it public and namespace-aware is a change to another crate's interface for one user. Writing one in this pack: a well-formedness checker is the larger part of `quick-xml`, and is what a hostile answer tests |
| 4. `text` | The whole body is the record's `text`, decoded by `charset` (`utf-8` unless the endpoint says, or `us-ascii`, `iso-8859-1`); a body that does not decode, or whose content type names another charset, is `drift`, and no character is ever replaced. An optional `pattern` must match the whole text: it is compiled as the command pack compiles its patterns, the same `regex` crate with the same anchoring and size limit, so a pattern means one thing in every pack. Its named groups are the record's fields, typed under `fields`; one that matched nothing, unless marked `required: false`, is `drift` | A pattern language of the pack's own, or the date formats of `a2m-expr`. There is no kernel pattern facility, and packs share data, never code, so the command pack's module cannot be called; its crate and its rules are what is shared |
| 5. `bytes` | The body is not interpreted: the record is its `length` and its `digest` (the kernel's SHA-256, as 64 hexadecimal characters). Saving the body to a file is a later package (downloads, section 303) | Returning the body as text or base64. A caller cannot judge bytes, and a value that size does not belong in a tool result |
| 6. The content type | Checked for every form that is not plain JSON: `xml` takes `application/xml`, `text/xml`, and `application/*+xml` unless the endpoint lists others; `text` takes `text/plain`; `bytes` `application/octet-stream`. A JSON endpoint may now list its types and is then checked too; one that lists none is not, as before. An answer of another type is `drift` | **The lead's premise did not hold**: there was no content-type check for JSON to extend. JSON's check is the parse itself. Checking every JSON answer's type now would change JSON endpoints that work |
| 7. The redactor and the system's words | Every value the `extract` step returns passes the redactor, as JSON's always did; a `text` body passes it whole before its pattern is matched, as the command pack's output does. No message quotes a value of the answer: it names a field or a byte position | |
| 8. Writes | A write whose read-back is an `xml` read works with no change in the engine: proven against the stand with its JSON write and its XML view of the same line item, whose `version` attribute is the version the write sends back. A request body that is neither JSON nor a form is not built | |
| 9. Calendar days | An output of the type `date` is now taken from a text `YYYY-MM-DD`, for JSON and every other form. A moment is not: the core has no reader of a moment's text, and the HTTP pack is not the place for one | |

## Consequences

- Proven against the test application by `tests/forms.rs`: each form read end to end and compared with what the control interface stores; a path that matches nothing and one that matches more than once; the document-type refusal; the depth and element bounds and the answer's ceiling; a wrong content type; a body that does not decode and a pattern that does not match; a registered secret in an XML and a text answer redacted; the JSON write read back through XML, with the stored record asked for; the declarations refused where they are written. Unit tests hold the reader's rules (`xml.rs`, `forms.rs`).
- The OpenAPI import still drafts only JSON answers: an operation whose answer is `application/xml` or `text/plain` is drafted with `response_schema` as an open question, as before. Drafting `answer: {form: ...}` with an open question for each path is owed; it needs the `described_operation` finding to carry the media type, a new format of its `found`.
- Two XML readers are now in the workspace, the workbook reader of `a2m-sources` and `quick-xml` here. If a third user appears, one of them should become the kernel's.

## Revisit if

- A system needs a path the closed language cannot write, more than once: widen the language by one step, never to XPath.
- `quick-xml` stops being released, or starts to resolve entities by default.
