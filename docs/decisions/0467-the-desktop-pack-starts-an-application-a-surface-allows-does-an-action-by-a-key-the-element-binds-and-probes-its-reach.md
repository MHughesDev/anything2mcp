# 0467. The desktop pack starts an application a surface allows, does an action by a key the element binds, and probes its reach

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-25

**Changes:** the desktop pack's registrations, failure table, invariants, and build order in [its design](../architecture/crates/a2m-pack-desktop.md); [spec section 305](../spec/3-packs/305-the-desktop-pack.md) (what it reaches, the driver, discovery, the failures, the build order); the stand `targets/example-desk` on Linux; the desktop rows of [SCOPE.md](../../SCOPE.md) and [section 704](../spec/7-project/704-readiness.md); row 8.3 of the [roadmap](../plan/roadmap.md). Carries out, under [decision 0465](0465-while-the-first-release-waits-on-the-owner-agents-build-the-one-machine-packages-moved-after-it.md), the three pieces of package 8.3 that [decision 0397](0397-what-the-first-release-needs-of-the-packages-left-and-what-waits-until-after-it.md) moved after the first release. It leaves the writes of [decisions 0218](0218-the-desktop-pack-writes-on-linux-through-a-second-closed-list-and-reads-back-what-is-stored.md) and [0399](0399-the-desktop-pack-writes-on-windows-and-macos-through-a-closed-list-of-its-own-on-each.md) as they are.

## Context

The pack found an application already running and started nothing ([decision 0198](0198-the-desktop-pack-reads-linux-applications-through-a-look-only-back-end.md), point 5); it pressed an element's named action and sent no key, because a synthetic key goes to whatever window has the focus and cannot be bound to an element (decision 0218); and its design named a discoverer, `desktop_probe`, that was not built. Spec section 305 said what each should be (an application started by path and digest; a key only when it can be bound to its window; a surface finding with the program, its version and digest, how many controls have no name, and a support tier) and left the rest open. The design's open point on starting a program asked for a link kind of the supervisor for a program watched until stopped.

## Decision

1. **Starting an application.** A surface of the kind `desktop` may state `start: true`. Then, when no application of its program runs, the driver starts the program at prepare, and otherwise attaches as before. It starts it only in a run (`Posture::Live`): a discovery or a sandbox starts nothing and stops as `application_not_running`. It starts nothing while any process of the engine's user runs the program (one that runs and publishes no tree is not started twice). The program's file is first held to the provider's check of who may change a program, as the command and MCP packs hold theirs (a shell, an interpreter, a script, or a file another user can replace is refused, as `policy`/`program_refused`); then it is started through the supervisor the pack's context scopes to the programs of the published compiled target (the manifest now says `compiled_target_programs = true`), which measures the digest the surface states and refuses another as `policy`/`effect_not_declared`. It is given no argument, nothing on its standard input, and the variables of a closed list (the display, the session bus, the runtime folder, the settings folders, home, user, language, and the search path), and what it writes is read and dropped. The driver then waits, by the accessibility bus's signals (the registry's, and the bus daemon's word of a new connection), reading the list of applications again on each, until the application publishes itself, and proves it as it proves one it found running. One that does not by the prepare's deadline is stopped, as `busy`/`application_not_started`: the pack leaves nothing running that it started and could not prove. One that does stays running for the engine's life, as an application a person started would, and the supervisor ends it when the engine stops. *Rule 5:* only the program the target declares, by path, with its digest checked; no argument, and no message addressed by name to the system.
2. **It uses the supervisor's link over standard streams.** A desktop application ignores the pipes, and the supervisor already starts, counts, and stops such a program in its job object or process group. *Instead of* a new link kind of the supervisor for a program watched until stopped, as the design's open point asked: the existing link does the work with no change to a kernel contract. What it lacks is the process number of what it started: the proof is the same as for an application found running (the program, the user, the start time, and the digest), and an application of the program a person starts in the same moment would make two, which stops as `application_ambiguous`.
3. **The review says so.** A binding over a surface that states `start: true` states the program it starts, by path and digest, and the variables it passes, and does not state where it sends: what a started program reaches is the program's. A surface without it states, as before, that it starts nothing and sends to no address.
4. **Windows and macOS start nothing yet,** as `busy`/`start_not_built`: neither back end has an event that says a new application's window appeared, and a wait polls nothing. The driver's code that starts is shared; what each system lacks is that wait.
5. **An action by a key.** A screen's action may state `key`, one of a closed list, `enter` and `escape`, in place of `perform`; both at once is `desktop.key_and_perform`, and any other key is refused by the schema. The driver does it as the element's own action that the element binds to that key: on Linux, the one action of AT-SPI's action interface whose key binding is the key alone, by a closed table of spellings (`Return`, `KP_Enter`, `Escape`, each also in angle brackets), through the same `act_call`, the same proofs before the act, the same commit point, confirmation, and read-back as a press. No key event is sent: no member of either closed list makes one. An element that binds the key to no action, or to more than one, is `unknown_variant`/`unexpected_control`, nothing sent. An action by a key that commits is a write like any other: recorded before it is sent, its confirmation waited for by events, and what is stored read back afresh; an operation whose binding reads nothing back is `irreversible` by its least effect, as before.
6. **A click is the element's press, as built.** On Linux `perform` names any action the element offers; on Windows and macOS it is `click`, the system's one press (decision 0399). A click by position is never sent (spec section 305, "Refused").
7. **Keys on Windows and macOS stop before the press,** as `busy`/`keys_not_built`, nothing pressed: UI Automation names an element's accelerator and access key but not a key a field's action is bound to, and the accessibility interface names a menu item's command key only. The fields a write sets before its committing action are set; the press is not sent.
8. **`desktop_probe`.** One `surface` finding, at `discovered`, from the `snapshot` step, which only looks: the program the surface declares; the digest of its file at that path, which the running process was proven to run; its version, `null`, with a limitation that says no accessibility interface gives it; how many windows the application shows, how many controls they hold (by a closed list of the pack's role words a person acts on or reads a value from), and how many of those have no name; and a support tier by a closed rule: `unsupported` when it shows no window, `partial` when a control has no name (it cannot be located, decision 0198) or a walk stopped at its bound, and `full` otherwise. It holds no value the window shows. It runs on all three systems, through each back end's existing reads.

*Instead of* a synthetic key bound by focus (focus the element, prove the focus, send the key): the key would still go to the focused window if anything took the focus between the proof and the event, the stands draw no window and have no display, so nothing could prove it, and the route on Linux is the registry's device controller, which needs a display server. *Instead of* the toolkit's version from AT-SPI's application interface as the program's version: it is the toolkit's, not the application's.

## Consequences

- `tests/start.rs` proves on Linux, against the stand as a program of its own (a copy of the test binary that serves the stand when started under one of two names, declared by `stand_child!` as a start function the loader calls): a surface that allows it has its program started once and read, under the supervisor, and a second run attaches; nothing is started without `start`, in a discovery, or against another digest; a program in a folder another user can write is refused; a started program that publishes nothing is stopped at the deadline. On Windows and macOS it proves `start_not_built`.
- `tests/keys.rs` proves on Linux that an update committed by Enter on the stand's `New status` field, which saves on Enter, is refused without the ledger's token, stored once with the token, and read back afresh; that a key the field binds to nothing presses nothing; that a refused value is answered as `app_validation_error`; and that a silent save is `possible_commit`. On Windows and macOS it proves `keys_not_built`. Its compile test holds the closed list and the refusal of both ways at once.
- `tests/probe.rs` runs on all three systems against the stand: the finding names the program and the digest the test measures, and the tier `partial`, from the stand's control with no name; the stand counts nothing pressed and no value read.

## Not built, and what would reopen it

Starting an application on Windows and macOS (the wait for its first window: on Windows a hook for a window shown by any process, on macOS a notification of a launched application); a key on Windows and macOS; keys beyond the two; the process number of a started program in the supervisor's answer, which would bind the proof to the process the pack started. A field test in which an application saves only on a key no element binds, or a toolkit that spells Enter otherwise, reopens points 5 and 7.
