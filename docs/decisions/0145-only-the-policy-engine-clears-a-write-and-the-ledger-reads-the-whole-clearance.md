# 0145. Only the policy engine clears a write, and the ledger reads the whole clearance

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the designs of [`a2m-ledger`](../architecture/crates/a2m-ledger.md), [`a2m-policy`](../architecture/crates/a2m-policy.md), [`a2m-actions`](../architecture/crates/a2m-actions.md), and [`a2m-engine`](../architecture/crates/a2m-engine.md); sentences of spec sections [208](../spec/2-kernel/208-runs-the-ledger-and-resume.md), [212](../spec/2-kernel/212-policy-and-approvals.md), and [226](../spec/2-kernel/226-configuration.md), and the [ledger schema](../reference/ledger-schema.md). Builds on decisions [0080](0080-the-store-is-one-sqlite-file-and-a-crate-reaches-its-own-tables-through-the-transaction.md), [0081](0081-what-the-ledger-holds-as-data-the-token-doubt-locks-and-rule-three.md), [0082](0082-the-decision-core-is-the-policy-crates-own-evaluator.md), and [0083](0083-the-policy-engines-interface-as-building-it-settled-it.md); takes up what decisions [0147](0147-the-engine-after-its-safety-audit.md) and [0152](0152-the-action-registry-and-telemetry-after-their-safety-audit.md) asked of these two crates.

## Context

A safety review read `a2m-policy` and `a2m-ledger` and ran nothing. It found one serious gap, S-1, and ten minor ones: six in the policy engine (P-1 to P-6) and four in the ledger (L-1, L-2, and two the review folded into S-1). Each was checked against the code with a test that failed before the fix.

## Decision

1. **Only the policy engine writes its tables** (S-1, confirmed). `Tx::tables(owner)` let any crate that holds a transaction say it was the policy engine, insert an approval or a `write_without_person` decision, and begin a write with no person. The store now hands out a `PolicyKey` once for its life, `Store::policy_key`; `Policy::open` takes it, and `Tx::policy_tables(&key)` is the only way to the policy engine's tables. `tx.tables(Owner::Policy)` refuses every statement, and a key of one store opens no other. The other owners keep `tx.tables` as it was. Tests stand in for the policy engine through a `testing` feature of `a2m-ledger`, turned on only as a feature of a dev-dependency: `testing::approve`, `testing::pre_approve`, and `Tx::policy_tables_for_tests`. The ledger's own tests need no feature: they take the key from each store they open, as the policy engine does. *What remains:* a crate that depends on the ledger and is handed the key could still forge, and so could a program that opens the database file itself. The kernel hands the key to the policy engine alone, and a test holds that no other crate's source names it. *Instead of:* a key type per owner, which would change every crate's code for owners whose tables nothing trusts; and triggers alone, which cannot tell one crate's statement from another's.
2. **`begin_writes` reads the whole clearance** (S-1, confirmed). An approval clears a run only when it names this run and its workspace, carries its diff hash and tool version, names a principal, is unexpired by the store's clock, is not revoked, proves presence wherever its channel is not the engine's own prompt, and was marked used in this very transaction. A pre-approval clears a run only when the decision is an allowed `write_without_person` of this run and workspace, for its diff, made under a policy version, and recorded in this very transaction, so that no kill switch or newer set came between (this also closes P-4). Each refusal is a test. Migration 0012 adds triggers for what the data can show: a write run enters `running` only cleared, by a clearance of its own; an intent only for a cleared, running run, under the record's lock, and not while a record of an earlier lease is in doubt; a return to `planned` only after a read. Expiry and "used in this transaction" stay in code: one needs the clock, the other the connection.
3. **Smaller ledger changes.** `mark_failed` and `in_doubt` keep in doubt, with its lock, any record whose write was sent (`acted_at`), whatever class it failed with; `session_expired` is never a settled class (asked by 0147). `RecordRow` carries the intent's mode, and `a2m-actions` reads it from the row instead of from memory, so a restart keeps it. `Reconciled::Landed` carries the record's outputs and assigned key, the engine fills them, and a resume no longer reads such a record twice. `Reconciled::NotLanded` needs the evidence of its read (L-2); a `failed` record with no intent since it was planned goes back with `Reconciled::NeverSent`, which the ledger checks from its row. Migration 0002 says its triggers hold all nine rules, which was not true of rules 3 and 5 (L-1); migrations are not edited once applied, so 0012 says what it adds and what no trigger can hold.
4. **The policy engine opens once per store** (P-2, confirmed). A second `Policy::open` fails when it asks for the key, so there is one approval handle per store and no second opening can put another built-in set in force.
5. **The installation's policy settings are in force** (asked by 0152). `BuiltIn::with_settings` carries them into the built-in set, which stays the built-in set. `Settings` gains `agent_effect_ceiling`, `writes_outside_tests`, `two_person_irreversible`, and `pre_approval`, read as their defaults from a set stored before them. The policy engine keeps the installation's settings as a floor: under a published set, each setting in force is the tighter of the two. Three are forbids that follow the settings, hashed with the guardrails (revision 2): an agent may not use a tool above the ceiling; with `writes_outside_tests` off, a write proceeds only when every record is a declared test record of a test environment, a fact `Context::test_records` carries; with `pre_approval` off, no rule lets a write proceed without a person. Two approvals of two people clear an irreversible run where the setting asks for them. `a2m-actions` carries every setting and refuses by name only a named approver on one machine. *The window's ceiling:* one day, 1,440 minutes, in both the set and the schema, which said 10,080. An approval is a standing permission to write; a week of one is a week in which a stolen or forgotten link still writes.
6. **Approvals checked at the point of action** (P-3, P-6, confirmed). `consume` refuses under a kill switch that covers the run and for a declined run, whatever was decided before. `record_approval` refuses an approval for another tool version, a proof of presence older than two minutes or ahead of the store's clock, and a check that proves nothing on any channel but the engine's own prompt. `Approved` carries the proof's time and the prompt's name; the name is kept in the audit entry the desk writes. `explain` answers only for a decision of the caller's workspace.
7. **Presence words.** `polkit`, `local_authentication`, and `windows_hello` join `os_prompt` and `signed_in`; each proves presence, and is stored in `approvals.presence_check`. `a2m-local` records the prompt's own word, names the prompt in each proof, and reports its prompt through `PersonSurface::presence`.
8. **Limits that stand, stated in the design** (P-1, P-5, P-6 in part). A presence check is a word the surface hands in; the handle goes to the person surface alone, which is what keeps it honest. On the approval path the policy engine cannot know whether an agent drove the person's surface; an agent's not being able to operate the surface is what keeps it out. The approver role is not scoped to a workspace or a target yet.

## Consequences

- A crate's tests that wrote approvals through `tx.tables(Owner::Policy)` fail until they take `testing::approve` of `a2m-ledger` (with the `testing` feature on their dev-dependency) or the store's key.
- The presets `cautious` and `ci`, and a settings file that tightens a policy limit, no longer stop the kernel.
- A pre-approval decided in one transaction and used in another is refused.
