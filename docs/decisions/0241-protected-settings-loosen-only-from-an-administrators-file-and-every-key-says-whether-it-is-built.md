# 0241. Protected settings loosen only from an administrator's file, and every key says whether it is built

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the settings schema and loader in `a2m-actions` ([crate design](../architecture/crates/a2m-actions.md)), its dispatcher and `doctor.run`; the engine's start in `anything2mcp` ([crate design](../architecture/crates/anything2mcp.md)); one function of `a2m-local` ([crate design](../architecture/crates/a2m-local.md)); [section 226](../spec/2-kernel/226-configuration.md). Carries out [decision 0236](0236-a-declared-setting-whose-feature-is-not-built-is-refused-by-name.md) in full and points 4 and 5 of [decision 0237](0237-one-statement-of-what-is-said-at-which-scope-by-which-means-and-by-whom.md), and takes the smaller step its point 3 allows. Takes up findings 1 to 4, 7, 8, and 10 of the [configurability review](../reviews/configurability-review-2026-11-18.md).

## The fault, shown before the fix

`a2m-actions` `bounds::tests::an_installation_file_the_persons_account_can_change_never_loosens_the_policy_engine` was first written against the code as it stood: `A2M_HOME` set to a fresh folder of the test's own, an installation file there with `policy.max_records_per_run = 1000`, `Sources::read`, `Settings::load`, and the policy engine's settings carried from the result. It passed: the policy engine was opened with 1000 records a run, against a default of 50. Any program running as the person, an agent's shell among them, could do the same. The test now asserts the opposite: the load stops with `policy`/`setting_protected`, naming the key, the file, why, and `A2M_HOME`, and the same file that tightens to 10 is applied.

## What was not carried out as written

- **0237, point 4, says an installation-only key in a file that fails the check is refused.** It is not: only a loosening of a protected key, and a lock, are. An installation-only key that is not protected is a choice of how, not a loosening: the vault's place (the passphrase route is the documented way out on a machine whose key store does not answer), a pack switched off, the provider of a mode, the MCP revisions. Refusing them would leave a person with no administrator unable to make those choices, and would protect nothing a protected key does not. Where one of them turns out to loosen, the answer is to protect it.
- **0237, point 3, applying each project's file to its own requests,** is not built. The policy engine is opened once with the installation's policy settings (`BuiltIn::with_settings`), the kernel holds one `Settings`, and a run reads it in a dozen places; giving each request its own layer 6 reaches the policy engine and the runner, which this package could not prove safely. Owed: a per-request settings value carried into the call and the run, recorded with the run by digest. 0237's test of it names `policy.max_records_per_run`, a key of scope U that no project file may set; the keys a project file may set today are those of scope P (the scout's and recording's) and a pack's of scope P.
- **The Windows owner and access list of the installation's file** are not read. Reading them as the command pack does for a program is a few hundred lines of calls into the system that only a Windows machine can run; until then, no installation file loosens on Windows and the refusal says why. A Windows machine with an administrator who wants a looser value has no way to it today, which is the safe side.
- **No inert key was wired.** The two the review named as small, `sessions.attempt_limit` and `engine.time_limit_ceiling_seconds`, are written nowhere as ceilings in the design (section 215 gives the auth file's `attempt_limit`; the compiler that would check a ceiling is `a2m-files`), so their meaning is in doubt; both are marked not built. Retention, redaction patterns, and the place of logs need design and are marked not built.

## The test-only route, and why a product build cannot reach it

The product's tests of trust roots need an installation file that loosens `network.trust_roots`, in a temporary folder the test's account owns, with each command in a process of its own. They now run each command in a child process of the test binary itself (`one_command_in_a_process_of_its_own`, started with a variable only that test file reads), which opens the engine as the program does, inside itself, with `EngineOptions::with_installation_kept_by_an_administrator_for_tests`, and runs the one command through `cli::run_on`. The shipped program builds its options with `EngineOptions::of_machine` and never calls the switch; no file, variable, or flag reaches the private field it sets; and the rule test above fails if any product source but its definition names it. This is the pattern of [decision 0201](0201-a-resume-is-never-lost-the-browser-takes-no-proxy-and-no-product-build-speaks-a-stands-protocol.md), a registration only a test calls, held by a test that names who may call it, and it adds no feature, so `cargo build --workspace` unifies nothing into the program. The same test also runs the real program on the same folder and asserts that it refuses the root by name.

## Other routes checked, into the installation layer or a guardrail

- The flags: no command passes settings as flags (`EngineOptions.flags` is always empty), and `Sources.serve` is never set; a flag may only tighten a protected key in any case.
- A variable that names a profile (`A2M_PROFILE__NAME`): `profile.name` is scope I and taken only from the installation's file or the flags of `serve`; a variable is refused.
- A variable or the user's file that names a preset: a preset, built-in or a site's, is layer 3 and only tightens; a site's presets are read from the installation's folder, so under `A2M_HOME` they are the person's own, and still only tighten. The project's file cannot name a preset.
- The project's file: scope P keys only, and only tightening a protected one.
- Other variables that move the installation's folder: on Windows `PROGRAMDATA`, and `LOCALAPPDATA` where it is absent. The check is of the file found, wherever it is, so these are covered as `A2M_HOME` is.
- A published policy set: only tightens the installation's policy settings (`Settings::tighter`).
- A pack's own key: a pack key is protected only where its manifest says `protected = true`; `packs.command.max_timeout_ms` and `max_output_bytes` declare a safer direction and are not protected, so a user's file may raise them to their bounds. Left as the packs declare them; their crates are not this package's.

## Alternatives weighed

- **Ignore the installation's file entirely under `A2M_HOME`.** Simple, and closes the fault for that variable, but not for `PROGRAMDATA` or a system folder a careless installer left open, and it would also drop the person's tightenings and choices there. The check of the file itself covers every route. Turned down.
- **Refuse to load at all when the installation's file is not an administrator's.** Safe, and it breaks the first run of every person with no administrator, and every test home. Holding the file to the person's rule keeps both and refuses exactly the loosening. Turned down.
- **A feature that turns the check off for tests.** Features are unified across a workspace build (the finding of decision 0201), so a feature a test crate turns on can reach the program. Turned down for the switch the program never calls.
- **Take the keys not built out of the schema.** Turned down by decision 0236; followed.
- **Keep `AtOnce` for keys that would take effect at once once a reload exists.** A value in the schema that describes a reload nobody built is the untrue word the review found. When a reload is built, it brings the distinction back with its tests.
