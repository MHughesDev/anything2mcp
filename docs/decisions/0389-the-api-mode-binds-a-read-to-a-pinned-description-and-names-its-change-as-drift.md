# 0389. The `api` mode binds a read to a pinned description, and names its change as drift

**Status:** Accepted. Design decision, made by the agent that built package 4.4. The owner had not read this record when it was merged.

**Date:** 2026-11-24

**Changes:** the HTTP pack's manifest, a public contract (the mode `api`, the file kind `description`, a third drafting rule, the failure code `description_changed`); the [design of `a2m-pack-http`](../architecture/crates/a2m-pack-http.md); [spec section 303](../spec/3-packs/303-the-http-pack.md); the [file formats](../reference/file-formats.md); the test application (case 38); the roadmap and the build order (package 4.4 done).

## Context

Spec section 303 names two modes for the HTTP pack: `http`, over endpoint entries a person or the drafter writes, and `api`, "calls generated from a published description", whose binding fields are `operation_id` and `args`, and whose pinned copy of the description carries a digest. Two lint codes were listed and not built: `http.api_operation_missing` and `http.api_description_changed`. The import already read a description into `described_operation` findings and drafted an endpoint entry for each operation and an `http` read for each GET. What was not decided: what the pinned copy holds, what "the description changed" means once a version is published, which step kinds the mode has, and whether drafted reads use it.

## Decision

1. **The pinned description is the pack's reading of the description's reads, with the digest of its text.** The file kind `description`, in `descriptions/`, for `http` surfaces. One document for each GET whose read the import drafts (the description marks it safe, states its answer, and its path is one this pack can send): `description` (its name), `surface`, `digest` (of the description's text as the import read it, once redacted, with no byte-order mark and every line ending a line feed), `served_at` (the literal path it was fetched from; none for a file handed in), `operation_id` when the description gives one, `method`, `path` as the description writes it, `auth`, `parameters` (name, place, whether required), `response_schema`, and `responses`. Each document compiles into the same request template an endpoint entry compiles into, so an `api` call is sent, checked, and read exactly as an `http` request is. Every document of one description must state one digest, place, and surface; one that does not is `http.api_description_changed`. The file kind holds reads only, so it describes no write.
2. **A binding names the operation, not an endpoint.** `mode: api`, `description`, and either `operation_id` (the description's own) or `method` and `path` (as the description writes them), never both; `args`, a map from a parameter's name as the description writes it to an expression, for path and query parameters (a path placeholder with no entry takes the input of its own name, as in `http`); and `extract`, as in `http`. An operation the pinned description does not state, or a description no file pins, is `http.api_operation_missing`; an argument for a parameter the operation does not state, or one in a header or a cookie, is `http.api_arg_unknown`; a required query, header, or cookie parameter with no argument is `http.api_arg_missing`. Verbs: `read`, `list`, `search`. Steps: `call`, `validate`, `extract`, and `probe`. `call` never saves.
3. **The digest is pinned at publish, and a change is drift, by name.** The digest is in the plan, so a published version holds the digest it was built from. Before the first `call` of a pass that a pinned description serves, the driver reads the description again at `served_at`, with no credential, and digests it the same way. A text that differs, an answer that is not a success, or one larger than the driver reads stops the call as `drift`, `description_changed`, before any byte of the call is sent. Each description is read once a pass. The engine then holds the binding drifted (`binding_drifted`) until it is repaired and published again: a description served as it was pinned once more does not make the binding good by itself.
4. **Drafted reads bind `api` when their operation is pinned.** The third drafting rule, from `described_operation` to `description`, writes the operation's document into `descriptions/{surface}.yaml` when the finding carries a digest and the surface is certain, by the same rule that ties an endpoint entry to a surface. The read rule then binds the read in `api` by the description's `operationId`, or its method and path, and says so in the read's description. Otherwise, as for a surface that is not certain, the read binds its endpoint entry in `http` as before. The import drafts no endpoint entry for an operation it pins; every other operation, writes included, keeps its endpoint entry as before.
5. **The mode is ranked 10,** ahead of `http` (20), as section 201 orders it. The engine prepares a surface's discovery in the provider's first-ranked mode of its archetype, so `api` declares `probe`; one driver serves both modes, and the reads left running are counted once for the pack.
6. **The endpoint catalog has two kinds of entry, and an operation is in one.** Rule eight puts endpoints only in the endpoint catalog. The catalog is the endpoint entries in `endpoints/` and the pinned descriptions in `descriptions/`, whose documents are the entries of reads bound in `api`. One operation's request is stated in one of them: the import never drafts both, and the lint `http.endpoint_stated_twice` (an error) refuses an endpoint entry that states, on one surface, by one method and path, the request of an operation an `api` binding binds through its pinned description. The two are compared by surface, method, and path as a template of this pack. Spec section 303, the file formats, and the glossary define the catalog so.
7. **A reference to another file is named.** The import never follows one; an answer shaped only through such a reference is drafted with an open question that says the description states it by a reference to another file, which the import does not read. The rest of the description is read.

## Alternatives weighed

- **A verbatim copy of the description as the pinned file, parsed by the compiler.** It would let the compiler check the text against its digest, so a hand edit could not move a binding off the description. Not taken: a file kind holds YAML documents, so the text would be one quoted string of up to eight megabytes in the target's files, no person could review it, and the compiler would run the bounded import on every compile. The digest still guards what matters at run time, the service's text. What is lost is written below.
- **A digest over the parsed document**, so that whitespace and key order are not drift. Not taken: the project's YAML reader and the pack's JSON reader do not give one canonical form (a decimal number becomes text through a draft), so the same description could digest two ways and be called changed when it is not.
- **`api` as `http` with another source of templates** (hypothesis H-19). Partly true: the template, the driver, and the checks are `http`'s. It stays a mode because the binding names a different thing (the description's operation, not an entry a person keeps) and has its own check before it acts, and because a mode is how the binding order and the promotion page tell the two apart.
- **No run-time check: a changed description shows only when an answer stops fitting.** Not taken: the owner's rule is that unknown means stop, and a new text of the description is a known sign that what the binding was built from is not what the service now says, before any answer is misread.
- **Draft the endpoint entry beside the pinned document**, so that a person may bind either. Not taken: rule eight, which never bends, would see one operation stated twice. A person who wants `http` for such a read writes the entry and changes the binding, and the lint holds the two apart.
- **Pin every safe operation**, drafted read or not. Not taken: an operation no read binds would then have its request only in a pinned description, and no endpoint entry for a person to write `http` bindings over; and a pinned read whose parameter is named as a secret would invite an `api` binding with a secret as an argument.

## Consequences

- The import drafts, for the test application, a pinned description in place of the drafted reads' endpoint entries, and those reads bind `api`; the GETs no read is drafted for, and the writes, keep their endpoint entries. The first-hour tests promote and publish through `api`, and an agent's call of the published read stops as `description_changed` once the application serves a revised description, with nothing of the call sent, and stays stopped as `binding_drifted` (`crates/anything2mcp/tests/first_hour.rs`).
- Not built: writes through `api` (a write is an `http` binding over an endpoint entry); GraphQL and OData; the run-time check for a description handed in as a file, which names no place (the short path's `add --description` is such a case: its reads are pinned and are not read again); a stand case for a reference to another file (the reader's unit test holds it).
- Open: a description handed in as a file names no place it is served, so its reads are pinned with no `served_at` and are never read again at run time; the short path's `add --description` is such a case. A change of it shows only when an answer stops fitting, or when a person imports it again. A way to name where the service serves it, for the driver to read, is not designed.
- Open: a person who edits a pinned document by hand moves the binding off the description without changing its digest, and nothing says so. A lint that compares the documents with a fresh import of the text, or a digest over the documents themselves, would find it.
- Not measured: the cost of the description's second read at each pass, against the 15 ms budget of section 225's `api` row.

## Three systems

| Matter | Proven here | Only CI proves |
| --- | --- | --- |
| A drafted `api` read compiles, reads what the application stores, and a revised description stops it as `description_changed` with nothing sent | Linux, `crates/a2m-pack-http/tests/session.rs` and `crates/anything2mcp/tests/first_hour.rs` | Windows and macOS, run |
| The digest of a served text agrees with the digest of the text the import read | Linux; line endings are made one before digesting | Windows, where a checkout may write other line endings |
