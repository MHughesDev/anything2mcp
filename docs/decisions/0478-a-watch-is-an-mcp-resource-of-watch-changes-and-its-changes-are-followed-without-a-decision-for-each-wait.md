# 0478. A watch is an MCP resource of `watch.changes`, and its changes are followed without a decision for each wait

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-25

**Builds** the second half of what [decision 0283](0283-watches-reach-an-agent-through-the-registry-and-their-person-confirms-each-on-the-page.md) left, as package W2e: the MCP resource of a watch and its subscription, and the REST change stream that [decision 0234](0234-a-watch-is-a-read-repeated-on-a-schedule-a-person-confirmed-and-a-change-is-reported-never-acted-on.md) planned; and the product test of a watch of a data pack list against the data stand, which [decision 0472](0472-a-read-declares-its-records-over-its-list-outputs-and-a-driver-states-whether-it-returned-every-record.md) could not run. **Keeps** decision 0234's rule that a notice carries the resource and nothing else, and decision 0280's twelve listed tools: no tool is added.

**Changes** the faces of an action (a fifth, the MCP resource template, `ActionDef::resource`); the output of every `watch.*` action (`resource`, the watch's URI); the MCP methods served (`resources/templates/list`, `resources/list`, `resources/read` in both revisions, `subscriptions/listen` in the stateless one) and the capabilities each revision names; the REST routes (`GET /api/v1/watches/{watch_id}/changes`, no action's); the designs of [`a2m-actions`](../architecture/crates/a2m-actions.md), [`a2m-mcp`](../architecture/crates/a2m-mcp.md), and [`a2m-api`](../architecture/crates/a2m-api.md); the saved API description and both generated clients; the roadmap (W2e done).

## Plan, stated before the build

The slice: a resource face generated from the registry, read by dispatching its action; a subscription that follows a watch through the kernel; the REST stream over the same follower; and one product test through the real command against the data stand, a line removed by the stand's own client. It tests H-47 through the MCP resource for the first time.

## Choices

- **The resource is a face of `watch.changes`, not code of `a2m-mcp`.** The alternative weighed was a handler in `a2m-mcp` that knows the watch actions and maps a URI to them. It was not taken: every face of an action is generated from the registry, and a resource read is a call of an action like any other, with its decision recorded. The face names fields of the action, and the dispatcher checks them as for any call.
- **The subscription is the stateless revision's alone.** The alternative weighed was `resources/subscribe` of revision 2025-11-25, through the stdio proxy holding one standing request upstream for the client. It was not taken: that revision's notification travels on a stream the session holds, a stateless server has no session, and the proxy keeps nothing between lines but the requests still open. A client of that revision reads the resource, or calls `watch.changes` with `wait_seconds`, which waits on the same follower.
- **A wait is not an action.** The alternative weighed was a subscription that calls `watch.changes` with `wait_seconds` through the dispatcher in a loop. It was not taken: it records a decision a minute for each watch for as long as the watch lasts, decisions that say nothing the watch's own decisions did not. The read of what changed is still an action.
- **The URI carries `after` in its query, and the notice carries the URI as subscribed.** So the resource is stateless: what a client has seen is its own to say.
- **A watch's change stream stays open while the watch lasts,** unlike a run's events, which end when the run rests: a watch is meant to be followed for its whole life. Its end is its last change, then `ended`.
- **No new failure code.** The refusals are the dispatcher's and the kernel's own: `not_found`, `person_required`, `schema_invalid`, `query_invalid`.

## Not built

Retention of watches: it waits on retention of runs, which nothing builds yet, since a watch's history leaves with its runs. Keep-alive on an MCP subscription's stream, as for every MCP stream (`a2m-mcp`'s design). A resource listed by `resources/list` for each watch. `notifications/resources/list_changed`, `toolsListChanged`, and `promptsListChanged`, which no part of this build can say. The REST stream and the subscription through the real served program, rather than the engine's router and endpoint in process.

## What the work showed

- **H-47, through the MCP resource, against the data stand.** A line removed by the stand's own client, outside the product, reached an agent as one notice that the watch's resource changed, and the resource then gave one `removed` naming the line's key and no value. The command reported the same removal once, and two later checks reported nothing. What the bet's alternative names, values that move on every read, did not arise: the list read's outputs are an item code and a quantity, neither of which moves by itself. How many reads of a real application need `ignore` is still not known.
- **The whole path needed nothing new of the ledger or the scheduler.** Records by key, coverage from the driver, and the removal rule of decision 0472 held unchanged through the real command; what was missing was doors.
