# 0339. The access actions, the built-in toolsets, and where a reach is kept

**Status:** Accepted. Design decision, made under [decision 0294](0294-the-owner-hands-the-open-questions-to-the-agents.md). The owner had not read this record when it was merged. Builds the `a2m-actions` half of slices N3 and 6.3, on [decision 0327](0327-a-reach-is-a-record-in-force-only-on-the-network-it-was-named-on-and-via-gateway-is-derived-from-it.md) and [decision 0328](0328-a-toolset-only-narrows-a-role-is-a-bundle-of-grants-and-a-second-administrator-is-a-named-check.md).

**Date:** 2026-11-23

**Changes:** `a2m-actions`: the actions `net.current`, `reach.name`, `reach.list`, `reach.withdraw`, `toolset.remove`, `policy.versions`, `policy.tools_allowed`, and `policy.who_can`; real handlers for `toolset.create`, `toolset.update`, `toolset.list`, `grant.add`, `grant.remove`, `grant.list`, `policy.test`, and `policy.publish`; the failure code `network_not_recognizable`; the role word `Auditor or Admin` for `policy.explain`; which toolset a decision names. Nothing in `a2m-policy`, `a2m-provider`, `a2m-netstate`, or `a2m-engine`.

## Decision

1. **The reaches are kept as one fact of the installation's store**, `net.reaches`, a list of reaches as JSON, and not in a settings file. A settings file is text any program of the user's account may write, and the protection of a protected setting is that a loosening needs a person present. A reach loosens (it lets a destination be called `via_gateway`), and the settings loader has no writer that asks for presence. The store is written only by the engine, and the only writers of this fact are `reach.name` and `reach.withdraw`, each a person's act with the operating system's presence check, and each refusing an agent caller again in the handler. The fact is read, never written, by `reach.list` and by `Kernel::reaches_and_network`.
2. **No input of an agent carries a network, a destination, or a gateway.** `reach.name` takes a label and the person's own entries (`destination`, or `destination via gateway`); the network is read from the machine at the moment of naming with the fingerprint reader of `a2m-netstate`, on a blocking thread. An empty fingerprint, or one that is not recognized as the same network as itself (a core fact missing), is refused with `input`/`network_not_recognizable`: nothing is stored that could not be recognized again. A listing shows the label, the names of the facts the reach states, whether it is in force on the network the machine is on now, and the person's own entries. It shows no digest. `net.current` shows the same facts of the network now, and the facts left out with their reasons.
3. **The derivation of `via_gateway` has one input in this crate:** `Kernel::reaches_and_network` returns the reaches and the fingerprint now, which are the two arguments `NetworkPlace::of_in_reach` needs after the machine's state. Nothing in `a2m-actions` derives a destination's place today: the only caller of `NetworkPlace::of` is the web pack's `Origins::places`, which a run's engine side reaches. The wiring of `of_in_reach` into that derivation is a change to `a2m-pack-web-browser` and the engine's caller of it, not to this crate, and is left as the next step of N3.
4. **A change to the policy set is a person's act and one new version.** `toolset.create`, `toolset.update`, `toolset.remove`, `grant.add`, `grant.remove`, and `policy.publish` need the presence check (the registry's `PersonNeed::Presence`), publish through `Policy::publish_change` or `publish_reviewed` with the check as `PublishProof.presence`, and are written to the audit log. A change brings its own test rows as `tests` (a version's test table is stored and hashed but never read back, so the table of the version in force is not carried over, and the call says so). Where the set in force says `second_admin_publish`, the call names a `reviewer`, and the person surface asks that reviewer for proof of presence of their own, checked as theirs and of now; the policy engine then checks that the reviewer is a person, is not the publisher or the author, and holds the role. A local machine has one person, so the need cannot be met there, which is what a second administrator on one machine means.
5. **A policy file is JSON in the project folder.** `policy.test` and `policy.publish` read a relative path inside the call's checked project folder, with no `..`, no absolute path, no link out, and at most 1 MiB. The file is the layers, and `tests` is a list of rows of one form (the principal may use a tool): the engine builds the request and its context itself, because a context is built only by `a2m-actions`.
6. **A built-in toolset names no toolset in a decision unless the set defines one of that name.** `use`, `build`, and `admin` are lists of what a door shows first and hold no permit. Decision 0328 makes a toolset that a set does not define stop the call once the set defines any, which would stop every call through a built-in toolset the first time an administrator created a toolset of their own. So `Kernel::toolset_for_decision` leaves the name out of the context for a built-in name the set in force does not define, and keeps every other name. A set that defines `use` narrows it as any toolset narrows. If the set in force cannot be read, the name is kept, which only narrows.
7. **`policy.explain` is for an auditor or an administrator.** The registry could name one role, and the policy engine holds no order of roles, so the action is reachable by any viewer, and the handler asks the policy engine, as the dispatcher does, whether the caller holds the auditor role or the administrator role, and refuses with `policy`/`not_granted` if neither.
8. **`policy.tools_allowed` and `policy.who_can`** ask `Policy::tools_allowed` and `Policy::who_can` over the published tools, with each tool's own effect and hazard, as persons with no group. A group is a fact of a token or a directory, which no door yet gives.

## Alternatives

| Alternative | Why not |
| --- | --- |
| Keep the reaches in the settings file as a protected setting | The loader has no writer that asks for presence, and the file is writable by any program of the account |
| Let an agent ask `reach.name` and the person confirm it on a page | It would be sound (the network is read when the person presses), but a reach is the one record that widens where a call may go, and a page for it is more than this slice proves; the person's own command is enough, and the handler refuses an agent whatever the dispatcher lets through |
| Name the built-in toolsets in the context and have the set define them | Every set an administrator publishes would have to carry three toolsets it does not mean, and a file that omits them would stop the engine's own doors |
| Order the roles so that an administrator holds the auditor role | Changes the one decider's meaning of a role for every action; the question is asked in one handler instead |

## Proof

`tests/reach.rs`: an agent cannot name or withdraw a reach, and cannot carry a network in the input; a reach named on another network is listed, is not in force here, shows no digest, and is withdrawn by a person only; the network the machine is on is named when it can be recognized again, and refused with `network_not_recognizable` when it cannot. `tests/access.rs`: a toolset is created, listed with the tools it selects, updated, and removed by a person and never an agent; a toolset narrows a call through it and one the set does not define stops it, while `use`, `build`, and `admin` keep working; a set that defines `use` narrows it; grants are added, listed, and removed and `who_can` follows them; a policy file is tested and published only when its rows pass and a path outside the folder is not read; an explanation is refused a viewer and given an auditor and an administrator; a second administrator is asked for and must prove presence of their own.

## What this leaves open

The wiring of `NetworkPlace::of_in_reach` into the derivation of a run's destinations, which is in the web pack and the engine. An MCP endpoint for a toolset a set defines (`a2m-mcp` serves `use` and `build`). The groups a principal belongs to, which the questions over a catalog cannot yet use. The layers of a workspace and of target files.
