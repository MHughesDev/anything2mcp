# 0278. What the first runs on Windows and macOS showed about the desktop pack and the check of programs

**Status:** Accepted. A design decision by an agent, made on 2026-11-18 from the CI runs of pull request 14; any agent may supersede it with evidence. The owner has not read this record.

**Date:** 2026-11-18

**Supersedes in part** [decision 0209](0209-the-desktop-pack-reads-windows-applications-through-ui-automation-on-a-thread-of-its-own.md), point 5 (the shape of a list view in report view) and point 8 (what the stand witnesses of the password edit). **Records the result** of two assumptions of [decision 0244](0244-the-desktop-pack-reads-macos-applications-and-proves-the-record-before-every-act.md) and of assumption 8 of [decision 0250](0250-one-check-of-who-may-change-a-program-and-the-mcp-packs-local-server-on-windows.md). The rest of each record stands.

## Context

Decisions 0209, 0244, and 0250 were written and linted on Linux, and each listed what only a run on Windows or macOS could prove. Pull request 14 took them through CI in five rounds: the validated commit, then four commits that each mended what the round before had shown. The fifth round passed every check on Windows, macOS, and Linux, the two desktop jobs among them, and the pull request was merged into `main`. Four of the assumptions did not hold as written. This record says what the runs showed in their place, and what was built to match.

## Decision

1. **A list view in report view is a table by its shape (supersedes decision 0209, point 5, in part).** UI Automation on the hosted Windows runner gave the stand's report-view list view as a list (control type `List`) whose first child is a header (`Header`), with each row a list item (`ListItem`) directly in the list, and not as a data grid of data items. The Windows back end now reads a table by that shape, in `Uia::tree` of `crates/a2m-pack-desktop/src/backend/windows.rs`: a list whose first child is a header is a `table`, and each list item directly in a `table` is a `table_row`. The header keeps its word, `table_row`, and its header items `table_column_header`, as before. A data grid and its data items keep their words from the one table of control types, for an application that gives a grid in that form. The rest of point 5 stands.
2. **The system refuses another process's request for a password edit's text (supersedes decision 0209, point 8, in part).** On the runner, `WM_GETTEXT` sent to the stand's password edit from another process was refused with `Access is denied` before the edit saw it, so the stand's count of such requests can never be raised from outside. The stand's own test (`the_window_is_up_and_its_control_interface_counts_what_it_is_asked` in `targets/example-desk/tests/stand.rs`) now asserts that refusal, that the test's buffer stayed empty, and that the stand counted no secret read; it proves the witness itself on a plain field, the edit labelled `Order number`, whose `WM_GETTEXT` from the test is answered and counted once. Why the system refuses is known from this run alone; no documentation was read for it. That the pack never asks for a password's value stays proven by its own tests: the closed list of members of point 3 of decision 0209 and the refusal `password_read_refused` before any job is sent (`crates/a2m-pack-desktop/tests/read.rs`). The rest of point 8 stands.
3. **A title element must be the element the system lists for the label (a result for decision 0244, points 6 and 7).** On the hosted macOS runner, a text field given its label through `setAccessibilityTitleUIElement:` alone answered `AXTitleUIElement` with nothing, and one that answered with the label's own view named an element that is not the static text the window lists among its children. The stand's fields now answer with the element AppKit gives for the label's view (`NSAccessibilityUnignoredDescendant`), in `targets/example-desk/src/mac/window.rs`. The pack's rule of point 6, that a name is else its title element's name, was not changed. An application whose fields name an unlisted element as their title gets no name for them from that element.
4. **The hosted macOS runner allowed the Accessibility grant by an administrator's write (a result for decision 0244, point 10).** The job `desktop-macos` on the `macos-15` image wrote one row per test program into the runner's system permission database as an administrator, read the rows back, restarted the permission daemon, and then ran the desktop tests with `A2M_REQUIRE_DESKTOP=1`, so that a test program refused the interface would have failed by name instead of being skipped. They passed. The two older reports that such a write is forbidden did not hold for this image. The grant stays the runner's alone, as decision 0242, point 14, allows; no product code and no instruction to a person makes it.
5. **The folder Cargo builds in does not pass the check of who may change a program on a hosted Windows runner (a result for decision 0250, assumption 8).** The runner's checkout is on a drive other than the system's, where every signed-in user may change files, so a program left where Cargo built it was refused by `check_program`, as it should be. The other half of the assumption held: the system's temporary folder passes. The test stands of the command pack and the MCP pack now place their programs in a folder of their own under the system's temporary folder on every system (`Stand::start_with` in `targets/example-cli/src/harness.rs`; `StdioStand::new` in `targets/example-mcp/src/harness.rs`). The check was not loosened.

## Consequences

- The desktop pack's reads on Windows and macOS have run against their stands, and passed, on hosted runners. Writes on both systems are still not built.
- Decision 0209 points 5 and 8 and decision 0244 points 6, 7, and 10 are read together with this record. The index has no form for a record superseded in part, so their rows in it are unchanged; this record names what it supersedes.
- A person whose program sits on a drive other users may change meets the same refusal the stands met, `policy`/`program_path_unsafe` from either pack. That is the case the check is for ([decision 0271](0271-the-check-of-programs-the-product-starts-after-a-second-reader.md), Consequences).

## Alternatives weighed

- **Ask the list view for its rows through another pattern, such as the grid pattern.** It would add members to the closed list of decision 0209, point 3, to learn what the tree's shape already says. Not taken.
- **Keep counting the password edit's text requests in the stand, and skip the assertion on Windows.** The count could then never fail, so it would prove nothing. The system's refusal is asserted instead, and the witness is proven where it can be.
- **Teach the pack to follow a title element to the listed element itself.** It would add a call outside the closed list of decision 0244, point 3, for a fault that only the stand had. Not taken; a real application that shows the fault is the evidence that would reopen it.
- **Let the stands' programs stay where Cargo builds them, and trust the build folder in tests.** That would test a weaker check than the product runs. Not taken.

## Revisit if

A Windows application gives a report-view list view as a data grid, or a list view whose header is not its first child; a later Windows release answers another process's `WM_GETTEXT` to a password edit; a hosted macOS image stops allowing the administrator's write, in which case the job's named stop says so and the owner is told; or a runner's checkout drive passes the check.
