# 0138. The vault and the session keeper after their safety audit

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Settles:** the findings of a safety audit of `a2m-vault` and `a2m-auth` against the ten rules and the [vault's](../architecture/crates/a2m-vault.md) and the [session keeper's](../architecture/crates/a2m-auth.md) designs. The audit read the code and ran nothing, so each finding was first checked against the code and shown by a test that failed. Nine were confirmed; one is true as written and has no route to harm. **Changes:** how a root key and a passphrase's salt are made, in [section 216](../spec/2-kernel/216-the-vault-and-its-keys.md); what the redactor covers, in [section 217](../spec/2-kernel/217-traces-evidence-and-repair.md); when a lease places nothing, in [section 215](../spec/2-kernel/215-sessions-and-the-session-keeper.md). One failure code is added: `vault_passphrase_too_short` (`input`).

## The vault

| # | Finding | Fix | Instead of |
| --- | --- | --- | --- |
| V-1, serious, confirmed | Two engines that start at once on a fresh installation each found no root in the operating system's key store and each wrote one. A write there replaces what is there, so the root written first was gone, with everything wrapped under it. The read-back the code relied on only reads the engine's own write | A root is made under a creation lock: an exclusive operating-system lock on a file in the user's temporary directory, named for the installation. The engine that holds it reads the store again and writes only when it is still empty. And a key is always wrapped under the root the store holds at that moment, never under the one in memory | A create-if-absent decided by the key store. Neither store crate offers one: the macOS one adds an item and, when it exists, changes it; the Windows call replaces. Going around the store crate on macOS means matching its item's attributes in code that cannot be run here. Also weighed: recording the root's identifier in the key records, which cannot settle anything between two engines whose records are in different stores |
| V-1, the passphrase route | The root there is derived, so two engines differ only by their salt. The salt is made by the product crate, by reading a file and writing it when it is missing | The vault offers `PassphraseSalt::load_or_create`: the salt is made once, under a creation lock beside its file, written whole under another name and moved into place. The product crate must call it; see below | Leaving the salt to each caller |
| V-2, a secret divided between two pieces of a stream | `redact` keeps nothing between two calls. Confirmed, and inherent in a call that sees one text | `Redactor::stream` gives a `RedactStream`: `push` each piece, `finish` at the end. It holds back as much text as the longest registered form could still begin in, in every view that is searched, and 72 bytes more for an escape still arriving. Joined, what it lets out is what `redact` gives for the whole text | A tail of the longest secret's length minus one, counted in bytes of the text: an escaped secret is several times longer than the secret, so the tail is counted in each decoded view |
| V-2, letter case | Matching was byte for byte | A secret written only in hexadecimal digits, with or without hyphens or colons, is masked in any letter case. `register_folded` does the same for a secret whose form the registrant knows to be case-insensitive | Folding every secret: two secrets in base64 that differ only by case are different secrets, and every text would be searched twice |
| V-2, hexadecimal | A secret's bytes written out in hexadecimal were a stated limit. The device pack redacts frames written that way | The hexadecimal writing of a secret, in each letter case, is one more form searched for, from two bytes of secret up | Leaving it to each caller that writes hexadecimal |
| V-2, base64 with line breaks | A line break ended the run of base64 characters | Base64 forms are also searched with line breaks left out: a run of white space that holds a line break, between two base64 characters, in the text and in the text percent-decoded or JSON-unescaped once. Only base64 forms count there | Leaving every white space out, which would join two words into a match and double the search of every text |
| V-2, character references | No view decoded them | A view with the five named references and the numbered ones decoded | The two thousand other named references: a stated limit |
| V-2, base64 of an escaped form, and deeper nesting | Not found | Stated as limits in the design, with what is and is not affected. A secret of letters, digits, `-`, `.`, `_`, and `~` is unchanged by escaping and is found | Decoding every run of base64 characters in every text, which is every word; or a form for each spelling of each escape, of which there is no finite list |
| V-3, confirmed as a wrong sentence | `Vault::with_random` said "for tests", and the kernel builds its vault with it | The sentence was wrong, not the kernel: the kernel holds the engine's one random source and must hand it on. The documentation now says so, and that in a running engine the source is the operating system's. The vault refuses the faults of a source it can see: a new key whose halves are the same, and a nonce that is the beginning of the key drawn before it | A marker trait for a cryptographic source, which a test source can implement as easily; a feature gate, which the kernel's own use would switch on in every build. A source that is merely predictable is not detected, and the design says so |
| V-4, confirmed | Any passphrase was accepted, an empty one too | Fewer than 16 bytes is refused, `input`/`vault_passphrase_too_short`, before anything is derived. A length is no measure of strength; it refuses what falls to a short search. A guess costs one derivation and can be checked away from the machine against the root's identifier, so nothing slows a search but the passphrase | Refusing only the empty one. A measure of strength, which needs a word list and still guesses |
| V-5, confirmed | The redactor kept an unkeyed digest of every secret, in memory that is not wiped | No digest is kept. The registered set is the forms themselves, in the wiped memory they were already in, ordered so that a lookup needs nothing else | A digest under a key made for the process: it needs randomness where the redactor is made, which cannot fail |
| V-6, true as written, no route | `OwnerRef::of` an account and `OwnerRef::service("account:x")` are one owner | Kept and stated: a dedicated account is the service identity with that beginning to its name, and the store makes an owner again from the kind and identifier it kept, through `service`. No product code makes a service owner from text a caller chose; the only call outside tests is the ledger reading back a row it wrote. A test holds the rule | A third kind of owner, or refusing the beginning in `service`: either stops the ledger from opening an account's blobs until its reading changes in the same step |

**V-1 is not a defect in depth.** The engine lock of `a2m-local` holds one engine to a data directory. It does not cover this, by two routes. The root's entry is named for the installation, which the product crate always calls `local`, so engines of one user on different data directories share one entry, and they run at once by design. And a command that finds no engine runs one inside itself without the engine lock, so two commands started together on a fresh installation are two engines on one data directory.

## The session keeper

| # | Finding | Fix | Instead of |
| --- | --- | --- | --- |
| A-1, serious, confirmed | After a restart, a restore that reached the worker after a revoke put the old credentials back at the old epoch, and a lease from before the revoke placed them. `apply` compared epochs only | Three changes. An end names its epoch and the worker remembers it: nothing of an earlier epoch is held again, and `apply` refuses a lease of an earlier epoch whatever is held. The keeper records a restore by a statement that names the epoch, and when the session moved on meanwhile it has the worker drop what the restore brought back. A lease is recorded the same way, and is not given when it is not recorded | Raising the epoch on revoke: it is raised already, and the worker never learned it. Reading the record in `apply`: `apply` does not wait, and the home runner may be another machine |
| A-2, minor, confirmed | `Forget` and `SignOut` dropped whatever was held | They drop what is held at their epoch or an earlier one. Work whose compare-and-set was lost is dropped by the epoch it was held at, and not at all when other work made the session valid at that epoch meanwhile | A token for each piece of work, carried in the outcome and back: exact, and a change to two public types for a case that costs a restore |
| A-3, minor, confirmed | A provider's failure reached a caller unredacted | The worker passes the failure of a sign-in, a renewal, a sign-out, and an `inject` through the vault's redactor before it leaves | Replacing a provider's sentence by a fixed one, which loses what a person needs to correct an entry. A value nobody registered cannot be recognized; the contract forbids it |

## Wanted in other crates

| Crate | Change | Why |

| `anything2mcp`, `engine.rs`, the function `salt` | Replace its body by `PassphraseSalt::load_or_create(&paths.data.join(SALT_FILE), random).await`, and await it where it is called | It reads the file and writes it when missing. Two commands started together on a fresh installation write two salts, which are two roots; this is finding V-1 on the only route a Linux machine has |
| `a2m-pack-web-browser`, `tab.rs`, `Page::shown` | Redact the whole text, then cut, as the command pack does | It cuts to 200 characters and then redacts, so a secret the cut divides leaves its first part |
| `a2m-core`, `Redact` | A way to a stream, if a caller that holds only the trait must redact a text in pieces | `RedactStream` is the vault's own type. No caller redacts piece by piece today: the MCP front door redacts each message whole |
| `a2m-actions`, the job that will carry the keeper's work to a runner | Send a `SignOut` or `Forget` again until the runner answers | An end that does not reach the home runner leaves its credentials there for leases given before the end |
| `a2m-ledger`, `blob.rs`, where a blob's owner is read | When a dedicated account becomes a kind of owner of its own, read the kind and not only `person` or the rest | Finding V-6 |

## What stays open

Two engines of one user whose temporary directories differ do not share the creation lock. A predictable random source in a running engine is not detected. The creation lock's code for Windows and macOS is the standard library's file lock; it is type-checked from Linux and has run only there. These are in the designs' open points.
