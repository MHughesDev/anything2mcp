# 0258. Every crate declares its failure codes in one table, with a meaning, a way out, and whether it passes by itself

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the [design of `a2m-core`](../architecture/crates/a2m-core.md) (its interface, its failures, and its build order), `tools/failure_codes.py`, and the generated table of failure codes in the [technical reference](../reference/technical-reference.md#failure-codes). The [designs of `a2m-expr`](../architecture/crates/a2m-expr.md) and [`a2m-sources`](../architecture/crates/a2m-sources.md), the first two crates to move to the form.

## Context

A failure carries a class, a code, a sentence, and a next step ([section 220](../spec/2-kernel/220-actions-and-the-authoring-interface.md), Failures). The next step is written only where a failure is made, so nothing could say what a code means, or what to do about it, without one in hand. Crates declared their codes in six forms: six copies of one private `codes!` macro, hand-written `ALL` lists, constants whose class was read from doc comments or from the calls that used them, and literals. `tools/failure_codes.py` read all of them as text. Nothing said whether a call that failed may pass if made again unchanged, and the class cannot say it: most `busy` codes, such as a run on hold or a store that is corrupt, never pass by themselves.

## Decision

1. **One form.** `a2m-core` exports one macro, `failure_codes!`, which every crate calls once, in a public module named `codes`. Each row is `NAME = Class, "code", meaning "...", next "..."`, then optionally `, passes by_itself` or `, passes not_by_itself`, then optionally `, then ("noun.verb", "what it is for")`. It writes the constants, with the meaning and the next step as their documentation; `ALL`, every class and code, which tests use; and `TABLE`, every row as a `CodeEntry`.
2. **Checked when the crate is compiled.** An empty meaning or next step, a code that is not a checked name, a `then` that names no action, and a `busy` row that does not say `passes` each stop the build. A class other than `busy` that does not say it takes its default: `transient` passes by itself, every other class does not.
3. **A row's next step is the general one.** It is an instruction, as section 220 asks. A failure made for a case may say more; one whose case adds nothing carries the row's, read from the crate's own table, so the sentence is written once.
4. **The book.** `CodeBook` reads the tables of many crates. It refuses one code declared with two classes, naming both crates; gives the row for a code (`explain`); and answers whether a code of a class passes by itself (`passes`), falling back to the class's default for a code it does not hold.
5. **`Failure` can carry a next action and a wait as data.** `with_next(action, args)` and `next()`; `with_retry_after(Duration)` and `retry_after_ms()`, in whole milliseconds rounded up, counted from when the failure was made. Each is written only when present, so a failure without them reads and writes as before. The text of what the system said and the two new parts sit behind one pointer, so a failure is no larger than it was and the errors that hold one stay under the lints' limit. Nothing reads them yet; the dispatcher's use of them is a later record's.
6. **The generator reads the form** and adds two columns to the reference's table: what to do, and whether the code passes by itself (empty for a crate not yet moved). A row it cannot read, an empty meaning or next step, and one code given two answers to whether it passes are faults. A list `MIGRATED` in the tool names the crates that have moved; such a crate that declares a code anywhere else is a fault, so a crate cannot slip back. `--list` names every crate still outside the form. The older forms are read until the last crate moves.
7. **First moved:** `a2m-core`, `a2m-expr`, and `a2m-sources`. `FailureCode::SCHEMA_INVALID` and the core's other associated constants are now the table's constants, so the generator counts each once.
8. **One code renamed.** `a2m-sources` gave `key_not_unique` the class `input`, for a file given with two rows of one key; the data and file packs give it `drift`, for a system that holds them. One code may have one class, and the class decides what happens next, so the source reader's code is now `source_key_not_unique`. No release had carried it.

## Alternatives weighed

- **Keep the next step at the call site only, and give the table a meaning alone.** Smaller. It leaves nothing to answer "what do I do about `queue_full`" without a failure in hand, which `failure.explain` and the dispatcher's fallback both need.
- **Two new fields held in place in `Failure`.** Simpler serialization. It makes a failure 16 bytes larger, enough to push an error that holds a failure and a list, such as a rejected source, over clippy's limit for a large error.
- **A procedural macro, or a build script that reads a table file.** Either can check more, such as that a `then` action exists. Either adds a crate and a build step to every crate. The action registry, which knows the actions, is the place to check a `then` against them.
- **Passing by itself decided by class.** Wrong for `busy`, as above. It is stated per row, and a class's default applies only to classes whose codes all answer alike.

## Crates moved since

Added 2026-11-18. `a2m-telemetry` moved after the first three. Then sixteen more, each with no change to the class, code, message, or next step any call site gives: `a2m-vault` (10 codes), `a2m-policy` (12), `a2m-files` (6), `a2m-api` (12), `a2m-mcp` (4), `a2m-netstate` (4), `a2m-sched` (17), `a2m-ledger` (32), `a2m-auth` (25), `a2m-provider` (40), `a2m-engine` (36), and the packs `a2m-pack-web-probe` (8), `a2m-pack-stream` (27), `a2m-pack-device` (16), `a2m-pack-data` (22), and `a2m-pack-command` (17). Each crate's `codes` module says, for every `busy` code, whether it passes by itself and why.

- **No clash.** No code turned out to have two classes, and no code has two answers to whether it passes by itself. A code several crates declare keeps one class and one answer in each.
- **Busy codes that pass by themselves.** `key_record_conflict`, `request_timed_out`, `queue_full`, `caller_queue_full`, `session_in_use`, `resource_in_use`, `rate_limited`, `run_reconciling`, `record_locked`, `watch_check_running`, `watch_check_unfinished`, `subsystem_limit`, `no_rate_budget`, `control_unanswered`, `shadow_time_exceeded`, `subscription_in_use`, `store_locked`, and `program_busy`. Every other `busy` code of these crates does not: a person, a setting, or a repair must come first. Two of the plan's list do not pass by themselves, read from the code that raises them: `runner_unavailable`, most often no enrolled runner offers what the job needs; and `path_locked`, whose holder is another program a person closes. `watch_check_running` and `watch_check_unfinished` were added to that list.
- **One `transient` code does not pass by itself.** `stdio_read_failed`: once a read of the proxy's input fails, the same proxy cannot read it again, and the client starts it anew.
- **Lists kept beside the table.** Where a crate kept a public list of part of its codes, the list is now the table's last rows: `WATCH_CODES` in the `codes` modules of `a2m-sched` and `a2m-ledger`, and `tls::CODES` in `a2m-auth`. The stream pack's `class_of` reads its `ALL`.
- **A second table under a feature.** `a2m-pack-data` declares the five codes only its server store returns in a table of their own, `codes::server`, which exists only in a build with the feature `postgres`, so that its `ALL` stays what the embedded store's manifest declares. A book of every code lists both tables in that build.
- **Aliases, not rows.** The data pack's `connection_lost`, `timeout`, `no_confirmation`, `read_only_posture`, and `path_not_allowed` are now the provider contract's constants, as the command pack's already were, so the reference no longer names the data pack as declaring them.
- **A wait as data.** The scheduler's `queue_full`, `record_locked`, `resource_in_use`, and `rate_limited` carry the wait their sentence states, with `with_retry_after`. Nothing reads it yet.
- **Next steps that describe.** These call sites give a description, not an instruction, and were left as they were: `net_fact_refused` ("Nothing was changed. The fact is not available to this user..."), `shadow_not_counted`, `watch_run_not_its_own`, `capture_not_kept`, `shadow_not_kept`, and the shadow case of `no_rate_budget` (each "Nothing to do; ..."), and `certificate_expired` ("The system's operator must renew its certificate..."). Their rows give an instruction.
- **Two more packs, later the same day.** `a2m-pack-http` (19 codes) and `a2m-pack-mcp` (13), with no change to any class or to what any call site says. `reads_still_running` joins the busy codes that pass by themselves. Each keeps, beside its table, a list `codes::PASSED_ON` of the codes it returns from the crates below it and its manifest declares. The MCP pack returns the provider contract's `program_not_found` and its manifest does not declare it; that was so before, and is left for its own change.
- **Three more, the same day:** `a2m-pack-desktop` (21 codes), `a2m-pack-web-browser` (6), and `a2m-pack-web-ui` (17, and 5 in `PASSED_ON`). The web browser engine's `timeout` and `connection_lost`, and the web interface pack's five codes of the browser engine (`browser_unavailable`, `browser_not_owned`, `password_read_refused`, `address_invalid`, `address_value_refused`), are aliases, not rows; the web interface pack lists the five in `codes::PASSED_ON`, and the desktop pack's list is empty. `session_in_use` passes by itself in the desktop pack, as in the scheduler; `browser_unavailable` and the desktop pack's other `busy` codes do not. One call site changed class: the desktop pack's discoverer gave `step_not_usable` as `unknown_variant`, and now gives it as `input`, the code's one class. The desktop pack and the web interface pack return the provider contract's `timeout`, `connection_lost`, `no_confirmation`, and `read_only_posture` and do not declare them in their manifests, as the HTTP pack does not; that is left as it was.
- **The last two:** `a2m-actions` (27 codes) and `a2m-local` (13), with no change to any class or to what any call site says. `a2m-actions`' literal `run_not_completed` (`rejected`) is now a row, and `schema_invalid`, `not_found`, `idempotency_key_invalid` and `engine_degraded` stay the core's, the store's and the scheduler's constants. `prompt_busy` and `tool_changed` join the busy codes that pass by themselves; `data_directory_gone`, `engine_unreachable`, `engine_running`, `channel_unavailable`, `surface_unavailable`, `lease_too_short`, `run_call_unreadable` and `system_job_not_carried` do not.
- **No crate is outside the form.** One thing is owed in the generator: it still reads the older forms, which nothing now uses.
- **Which crate's wording a shared code's row gives.** For a code several crates declare, the generator showed the meaning of the crate first by name, kernel crates before packs, so the reference's row for `connection_lost` gave the local channel's wording where the provider contract's is the general one. It now orders those crates `a2m-core`, then `a2m-provider`, then the other kernel crates by layer, lowest first, then the pack crates, bases and packs alike, by name within each; the first gives the row's meaning. A pack base is not put before the packs, because its wording is its own kind of system's: the browser engine's `surface_not_declared` speaks of a tab. Eight rows changed order, six of them their wording. `answer_lost` keeps the local channel's wording, because `a2m-local` and `a2m-mcp` share a layer; `storage_full` now gives the log writer's (`a2m-telemetry`, layer 2), which speaks only of the log folder, and is better given a meaning that fits every crate that declares it.
