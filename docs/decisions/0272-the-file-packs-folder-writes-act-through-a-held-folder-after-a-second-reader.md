# 0272. The file pack's folder writes act through a held folder, after a second reader

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Changes:** the provider contract's checked paths (`crates/a2m-provider/src/path.rs` and `path/place.rs`), the file pack (`crates/a2m-pack-file`), [section 308](../spec/3-packs/308-the-file-pack.md), and the design of [`a2m-pack-file`](../architecture/crates/a2m-pack-file.md). **Builds on** [decision 0246](0246-the-file-pack-reads-folders-settings-files-and-growing-files.md) and [decision 0193](0193-the-core-the-contract-the-compiler-and-the-scheduler-after-the-second-pass.md). **Answers** section C of the sixth safety audit (findings C1 and C3 to C8; C2 was fixed before and is not repeated). **Adopts** the fixed place and the review statement of [decision 0252](0252-a-fixed-place-a-review-that-shows-what-runs-and-a-sign-in-before-its-probe.md) for the file pack. The provider contract gains a type (`HeldFolder`), an enum (`Removal`), and two methods (`CheckedPath::hold_folder`, `FileIdentity::to_bytes`); nothing that was there changes shape.

## Context

A second reader found that a folder's create, rename, and removal of an empty folder looked at the path and then acted by path. Each act resolved the whole path again, so a folder of the root swapped for a link between the look and the act took the write, or the removal, to where the link led, outside the declared root. On Windows a read at depth had the same gap. A file's identity on Windows was its creation time and length, which name tunnelling gives to a new file under a name just freed; a delete and a rename trusted that identity alone. The minor findings were about forms with two meanings in settings files, a log that one bad line stopped for good, and names the file system folds by its own rules.

## Decision

**1. A held folder (C1).** `CheckedPath::hold_folder` reaches the folder from the root down, following no link, and gives a `HeldFolder`. Each of its calls names one entry directly in that folder: `kind`, `identity`, `names`, `create_new`, `link`, `remove_file_if`, `remove_empty_folder`, `sync`. A name that is not one name under the roots' rules is refused, and no call follows a link at the name it acts on. The calls give the system's own `std::io::Error`, so the pack can tell "something has the name" from "no second name on this file system" and from "denied", and names the failure itself.

- On Linux and macOS the held folder is its own descriptor, and each call is made relative to it: `openat` with `O_CREAT | O_EXCL | O_NOFOLLOW`, `linkat`, `renameat`, and `unlinkat`, with `AT_REMOVEDIR` for a folder.
- On Windows every folder from the root down is opened with no reparse point followed and held open, shared for reading and writing and not for removing. While it is held, none of those folders can be renamed, removed, or replaced by a link. Each call then names the entry by its path through them. `CheckedPath::open` on Windows holds the folders the same way while it opens, and opens a link at the name itself and refuses it.

The pack's create, rename, and delete act only through the surface's folder held this way. `HeldFolder::still_at_its_path` tells whether the folder reached afresh from the root is still the one held. Asked just before the act, a "no" stops the write unsent; asked after it, a "no" makes the outcome unknown, because the change was made in the folder that was held, wherever it is now.

Weighed and not chosen: a second look by path just before each act, which narrows the window and does not close it; and, on Windows, opening each entry relative to a folder handle through the native call that takes a root directory. That is the exact form, and it needs a call outside the documented interface and more unsafe code. Holding the chain gives the same guarantee for every move but one, named below.

**2. A file removed only while its name holds it (C4).** `HeldFolder::remove_file_if(name, expected, holds)` removes a file only where it is the file `expected` names, and `holds` says yes of it, read through a handle of that very file from its start. On Windows the file is opened with the right to remove it, its identity is read from that handle, and it is marked for removal through the same handle, with the POSIX form where the file system takes it. On Linux and macOS what stands at the name is first moved to a name of 128 random bits beginning `.a2m-old-`, looked at there, and removed. Anything else is moved back, but only where nothing has taken the name meanwhile (`renameat` with `RENAME_NOREPLACE` where the system has it, otherwise a second name and the removal of the first). The answer is `Removal::Removed` or `Removal::NotThatFile { put_back }`. A temporary file is removed the same way.

**3. Identity is the system's file identifier (C3).** The pack's `Identity` is now the provider's `FileIdentity`: the device and the file number on Linux and macOS, and on Windows the volume's serial number and the 128-bit identifier of `FileIdInfo`, read from a handle, or the 64-bit index where a file system does not answer that question. A growing file's position digests the same identity (`FileIdentity::to_bytes`) on Windows, in place of its creation time. A delete of a file is now also held to the digest of the bytes it read: the step before the act reads the file, within `max_bytes`, and the act removes it only while its bytes still have that digest. A file larger than `max_bytes` is refused for a delete with `file_too_large`, unsent.

**4. Settings forms with two meanings (C5).** An INI section header that appears twice, in any ASCII case, is `shape_unsupported`, since programs read it as one section, its first block, or its last. A written INI value refuses every control character, the tab and NUL included, and U+0085, U+2028, and U+2029. A written property list value refuses those three, the control characters but the tab, and U+FFFE and U+FFFF, which XML does not allow.

**5. A growing file (C6, C7).** A line that is not UTF-8 text no longer stops the log. The read that reaches it gives the complete lines before it, with a position at its start. The next read gives no line, the new outcome `unreadable`, and a position after the bad line, so the read after that goes on. A file with the same identity whose first bytes changed is `truncated`, not `replaced`: it was cut short and written again. `replaced` now means another file stands at the name.

**6. Names the file system folds by its own rules (C8).** The pack does not repeat a file system's folding (macOS takes the two forms of an accented letter as one name; Windows folds case by its own table). It asks the file system instead. A read by a name the folder does not list, under any spelling the pack compares, that the file system finds all the same, is `name_case_conflict`, not "missing". So is a create or a rename to such a name: before the act, when the held folder finds an entry at a name it does not list; and at the act, when the second name fails because the name is taken and the folder lists no entry the pack takes for it. Normalizing names in the pack was weighed and not chosen: it needs a Unicode table of its own and could still differ from the file system's.

**7. The fixed place and the statement (decision 0252).** `FileKind::fixed_places` on `documents/` lists each record that declares no `key` and is one place (a `path` to one record of a JSON document or one section or dictionary of a settings file, or a named `cell`), as `document.record`. Rows, a table, or a sheet with no key are many records and are not listed. `Lowering::fixed_place` names `document.record` for a binding with no `key:`. The four settings writes of the test target declare `identity: {strategy: natural, place: fixed}` and no longer take a `settings` input. `Lowering::statement` says a file binding starts no program, sets no variable, and sends nothing (`Sends::Only { surface: false, addresses: [] }`) where the surface's folder is a local path in form. A folder that begins with two separators (`\\host\…`, `//host/…`) names another machine, and the pack does not state where it sends. That rule also takes a Windows path that begins `\\?\` for another machine, which errs toward saying less. A root that is itself a mounted share is the engine's setting and cannot be seen from the target's files.

## What is left

- **A folder moved whole.** On Linux and macOS a held folder moved away, whole, to a place outside the root on the same file system is still the folder the calls act in. That needs the right to rename a folder in the root. It is told by `still_at_its_path` before the act (unsent) and after it (unknown); the act in between is not prevented.
- **A mount point made on Windows.** One of the held folders made a mount point while it is held is followed. That needs the folder to be empty and the right to write it; `still_at_its_path` tells it too, since a folder that became a link is not held again.
- **A number reused.** A file system that gives a new file the number of one just removed (ext4 does; FAT's index comes from the entry's place in its folder) can make a different file with the same identity. A delete is held to the digest too. A rename reads no bytes and is held to the identity alone; it changes a name and loses nothing.
- **A crash in the moment a removal looks.** On Linux and macOS, a process that ends between the move aside and the removal or the move back leaves the file under its `.a2m-old-` name, and a resume that reads the old name sees nothing there. The window is a few system calls wide.
- **Windows and macOS are linted from Linux, not run.** The held chain on Windows, the removal through a handle, the file identifier in a log's position, and the macOS test of a folded name (`a_name_the_file_system_folds_into_a_listed_entry_is_a_named_stop`) are proven only when CI runs them there.

## Consequences

- The tests `a_folder_swapped_for_a_link_after_the_look_gets_no_created_file_outside_the_root`, `…_no_renamed_name_outside_the_root`, and `…_no_folder_removed_outside_the_root` swap the surface's folder for a link to a folder outside the root at a pause point between the last look and the act. They assert that nothing appears outside the root and that its folder is not changed, not even for a moment. `a_file_put_at_the_name_after_the_look_is_not_the_one_deleted` holds C4. In the provider, `a_held_folder_removes_a_file_only_while_its_name_holds_the_file_looked_at` and `a_held_folder_swapped_for_a_link_takes_every_call_and_the_link_none` hold the contract.
- For hypothesis H-26, the contract gained a held folder because a pack needed one. The type is neutral: it names no pack, mode, or kind of system.
