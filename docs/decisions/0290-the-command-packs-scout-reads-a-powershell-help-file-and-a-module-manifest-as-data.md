# 0290. The command pack's scout reads a PowerShell help file and a module manifest as data

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-18

**Carries out** the PowerShell half of point 2 of [decision 0276](0276-what-the-scout-may-learn-from-a-program-itself-and-by-which-means.md), as point 4 of [decision 0279](0279-what-the-three-surveys-left-open-against-decision-0276-is-settled.md) left it: roadmap package X4b, after [decision 0284](0284-the-command-packs-scout-reads-a-fish-completion-file-and-a-manual-page-it-is-handed.md) did the first half. **Changes** the command pack's manifest, its discoverer `help`, its `command_file` finding, and adds a finding kind, a drafting rule, and a failure code; [section 306](../spec/3-packs/306-the-command-pack.md) and the [design of `a2m-pack-command`](../architecture/crates/a2m-pack-command.md) say the same. The evidence is [research note 30](../research/30-what-can-tell-what-a-compiled-program-does.md), its row on PowerShell manifests and help.

## Context

A PowerShell module publishes two files about its commands: an XML help file in the format named MAML (`<module>-help.xml`), which states each command's parameter sets and, for each parameter, its type, whether it is required, its position, and whether it takes a value from the pipeline; and a manifest (`<module>.psd1`), written in PowerShell's data language, which names the module's version and the commands it exports. Research note 30 found that asking PowerShell itself (`Get-Command`) imports the module and runs its top-level code, and that reading the files as data needs about 300 lines for the manifest and a MAML reader on `quick-xml`, which the workspace already has. A PowerShell command runs in this pack only as a fixed pair: Windows PowerShell in its one form and a script the target keeps ([decision 0216](0216-the-command-pack-on-three-systems-the-administrators-group-and-a-script-the-target-keeps.md), [decision 0250](0250-one-check-of-who-may-change-a-program-and-the-mcp-packs-local-server-on-windows.md)).

## Decision

1. **Where the files come from.** The discoverer `help` declares two more file names (decision 0263): `powershell_help`, an XML help file, and `module_manifest`, a manifest. A person puts each in the project's `sources` folder and hands it with `scout run --files '{"powershell_help": "sources/<file>"}'` or `discover run --files`. The registry takes the names from the manifest.
2. **Nothing runs, and the files are read first.** No PowerShell is started, no module is imported, and nothing in either file is evaluated. Both files are read, with the completion file and the manual page, before any help form starts. A file that cannot be read ends the discovery before anything starts, as `input`, `powershell_file_unreadable`: it is not UTF-8 text, it is not well-formed XML, it declares a document type, it passes a bound, its root is not `helpItems`, or it is no manifest (one table of data). Each file's whole text passes the redactor before it is read, and each description passes it again after its paragraphs are joined, and is then cut to 400 characters.
3. **The help reader** parses the file with `quick-xml` into a small tree: at most 32 elements deep, 100,000 elements, 32 attributes on one element, and names of 128 bytes, inside the discoverer's bound of 1 MiB. A document type is refused before any element is read, so no entity is expanded and nothing it names is fetched; of references, only characters and the five names XML defines are read; an encoding other than UTF-8 is refused. Elements are known by their namespace and name, not by their prefix. Of each `command:command` it reads the name and synopsis under `command:details`, each `command:syntaxItem` of `command:syntax` as one parameter set, and the list `command:parameters`; a parameter's type is the full name in `dev:type` where the help gives one, else the text of its `command:parameterValue`, and a set takes from the list what its own entry leaves out. A parameter whose type is `SwitchParameter` is a switch. Prose sections (descriptions, examples, input and return types, notes, links) are passed over whole. Inside the parts it reads, an element or an attribute it does not know, or an attribute value outside the forms it knows (`required` true or false, `position` `named` or a number, `pipelineInput` false, true, or true by value or by property name), leaves that command unread, counted by reason: `unknown_element`, `unknown_attribute`, `unknown_value`, `not_plain_name`, `no_name`, `twice`, `bound`; any other child of `helpItems` is counted `not_command`. At most 500 commands, 32 sets of a command, and 128 parameters of a set are read.
4. **The manifest reader** tokenizes the data language and takes a value only when it is literal: a single-quoted string, a double-quoted one with no `$` and no backtick, a here-string of the same kinds, a number, `$true`, `$false`, `$null`, a list of these with `@(...)` or commas, or a table of these with `@{...}`. A string holding a typographic quote is not literal, because PowerShell may end it there. Any other value (a variable, a call, a script block, a type) leaves its key unread as `not_literal`; a wildcard in an exported name is counted `wildcard`; a name not plain is counted `not_plain_name`. It keeps `ModuleVersion` and the names in `FunctionsToExport`, `CmdletsToExport`, and `AliasesToExport`, at most 2,000. A file that is not one table, a key named twice, a string or comment that does not end, or brackets that do not match, is refused.
5. **What a finding claims.** Each handed file makes one `command_file` finding, as the other files do: its subject is the file by its digest, as `powershell_help` or `module_manifest`, in the form `maml` or `psd1`; it is `inferred` from `artifact`; its coverage is `complete` only when nothing was left unread. A manifest's finding also holds `exported` and `version`; both are left out of the text when empty, so the findings decision 0284 defined read as before. Where both files are handed, `unlisted` holds, for the manifest, the names it exports that the help does not describe, and for the help, the commands it describes that the manifest does not export. Each command the help file describes makes one `powershell_command` finding: its subject is the help file, with the command's name as the part; it is `inferred` from `artifact`, `not_exercised`, and derived from the help file's finding. It holds the command's `name`, `synopsis`, and `sets`, each parameter with `name`, `type`, `switch`, `required` (null when the help does not say), `position`, `pipeline`, and `about`.
6. **What the drafter makes.** One `commands/` draft for each `powershell_command` finding, with Windows PowerShell's form under `program.interpreter.args` (`-NoProfile -NonInteractive -ExecutionPolicy Bypass -File`, the provider's closed table, held together by a test), and one command for each parameter set (`<name>_1`, `<name>_2` where there are several). Each parameter is given by name: a switch as a `boolean` param whose flag is given when it is true, or, where the help marks the switch required, as a fixed flag; a parameter that takes a value as its flag followed by the value. A type that is a whole number (`Int16` to `UInt64`, `Byte`, `SByte`) is `integer`; every other type is a question that quotes the type and the help's description; a parameter the help does not mark required or not is a question too. `-WhatIf` and `-Confirm` are PowerShell's own and are not drafted; where the help lists one, the question of the effect quotes it as the command's own claim that it changes something. The script, Windows PowerShell's digests, the effect, and the output are questions; `effect` is never written (section 306). A draft applies to the target's first surface, as every drafted `commands/` file does, and the pack's lint refuses it unless that surface is Windows PowerShell.
7. **Position and pipeline are kept, and not drafted.** A parameter given by name binds the same parameter whatever the other parameters and sets are, where a position depends on both; and with `-File` nothing reaches the script from a pipeline, while every parameter that takes its value from the pipeline can also be given by name.

## Not built

The values a help lists for a parameter (`command:parameterValueGroup`), which would type a parameter as a choice; help for providers; help written as comments in a script, which is code; drafting from the names a manifest exports when no help file describes them; reading the system's own module folders; PowerShell 7 (`pwsh`), which the closed table of interpreters does not hold. **Discovery on a surface that is Windows PowerShell** needs one `commands/` file there that declares the pair first: the driver refuses to prepare an interpreter surface whose files do not, and discovery holds the surface's driver before any discoverer reads a file. The tests hand the help file to the discovery of another program's surface, which reads it all the same.

## Alternatives weighed

- **Ask a running PowerShell, with `Get-Command` or `Get-Help`.** The richer source: it knows dynamic parameters, validation attributes, and what a module computes. It imports the module and runs its top-level code, and starting PowerShell to ask is exactly what [decision 0282](0282-whether-the-command-pack-may-start-programs-that-run-what-their-arguments-name.md) leaves to the owner. Not taken.
- **Read the manifest with PowerShell's `Import-PowerShellDataFile`.** It refuses what is not data, as this reader does, but it needs PowerShell on the machine and started by the scout. Not taken, for the same reason.
- **Reuse the `command` finding.** Its subject is a program's subcommands, listed by the program's help, and its drafter runs the program itself. A PowerShell command is neither, and runs only as a pair. Not taken; the `command` finding is unchanged.
- **One kernel-level shape for a described operation** ([hypothesis H-41](../hypotheses/README.md)). A help file is such a description. The draft still needed the parameter sets, the switch, and the pair, which belong to this pack. This slice did not test the hypothesis; it is one more self-describing kind built as a pack's own finding, for the comparison H-41 asks.
- **Refuse the whole file on an element the reader does not know.** Safe, and one unknown element in one parameter would cost every other command. Not taken: the command is left unread and counted, and nothing about it is guessed.
- **Give positional parameters by position.** It would follow the help's own syntax. Not taken: see point 7.

## Dependencies

No new package. `quick-xml` 0.42.0 (MIT), already in the workspace for `a2m-pack-http` with its default features off, is now also a dependency of `a2m-pack-command`.
