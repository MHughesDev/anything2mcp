# 0146. The macOS and Windows presence prompts, as built

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Carries out:** [record 0133](0133-the-presence-prompt-on-each-operating-system-and-what-it-is-said-to-prove.md), the macOS and Windows parts of points 1, 3, and 7, on the interface of [record 0142](0142-the-presence-prompt-interface-and-the-linux-prompt-as-built.md). **Changes:** the design of [`a2m-local`](../architecture/crates/a2m-local.md), its section on the presence prompt and its build order.

## Context

Record 0133 chose `LAContext` on macOS and Windows Hello on Windows, and named their crates from [research note 20](../research/20-operating-system-user-presence-checks.md). Record 0142 built the interface and the Linux prompt. This package wrote the other two. Neither could be run: the machine that wrote them runs Linux, and the whole crate cannot be compiled for another system here, because its tree compiles C.

## Decision

**The crates.** Each was checked again on crates.io on 2026-11-17, and the licence, ban, source, and advisory checks pass with them in the tree, with no change to `deny.toml`.

1. **macOS:** `objc2-local-authentication` 0.3.2 (Zlib OR Apache-2.0 OR MIT), `objc2` 0.6.5, `objc2-foundation` 0.3.2, and `block2` 0.6.2 (MIT), all with no default features. Only `LAContext`, `LAError`, and blocks are turned on, which keeps the framework's keychain crate, `objc2-security`, and the rest of Foundation out. Five crates are new to the tree: those four and `objc2-encode`. None compiles C.
2. **Windows:** `windows` 0.62.2 with `Security_Credentials_UI`, `Win32_System_WinRT`, and `Win32_Foundation`, and `windows-future` 0.3.2, which holds the operation type and is not re-exported by `windows`. Ten crates are new (MIT OR Apache-2.0). **No second line of the `windows-sys` family:** `windows` 0.62 and `windows-sys` 0.61 share `windows-link` 0.2.1; the older `windows-sys` 0.52 already in the tree is someone else's and unchanged. The cost is the umbrella crate's size, a 9 MB download that unpacks to 114 MB, fetched only where Windows is built. The Win32 calls around the prompt (the session, the window station, the owner window) use `windows-sys`, already in the crate, with four more features.
3. *Rejected for now:* bindings generated by `windows-bindgen` for exactly the verifier, its interop, and their two enums. They would drop `windows`, `windows-collections`, and `windows-numerics`, three crates and the large download, but they still need `windows-core` and `windows-future`, they add a generated file to review and regenerate with every bump, and generating at the 0.62 line here could not be checked against a running Windows. The umbrella with three features is the path the note verified. Reopen with the move of `windows-sys` to the 0.100 line, when generated bindings over one `windows-core` are the lighter tree.

**The shape.**

4. **The same shape as polkit:** one small trait over the system (`Authenticator` on macOS, `Verifier` on Windows) whose methods speak in plain numbers and enums of our own, the real system behind it in a module compiled on its own system only, and total functions from every number to an answer. The two files are compiled into the tests on every system, so the mapping is proved on Linux too, against a made-up system.
5. **Dropping the system's ask takes the dialog away.** macOS invalidates the context; Windows cancels the operation, then closes the owner window. *Instead of* an explicit cancel call after the deadline, as polkit does: a drop also closes the dialog when the ask is dropped for any other reason, such as a surface task that ends.
6. **Before anybody is asked, the session is read.** macOS: `CGSessionCopyCurrentDictionary`, null in no graphical session (documented), not on the console, or locked. Windows: session 0 or a window station other than `WinSta0` (`no_window_station`), a remote desktop session (`session_remote`), and the session's lock flag (`session_locked`). Then the system's own check that shows nothing: `canEvaluatePolicy`, `CheckAvailabilityAsync`. *Instead of* the system's check alone: what it answers at a locked screen or over remote desktop is not documented, and a prompt answered from another machine proves nobody at this one.
7. **Seven new reasons**, each with a remedy: `no_window_station`, `session_remote`, `session_locked`, `not_set_up`, `disabled_by_policy`, `device_busy`, and `locked_out`. `session_not_active` and `check_failed` are reused.
8. **The answers.** Only success on macOS and `Verified` on Windows are `Present`. Cancelled by the person, the system, or the engine is `Dismissed`; a failed check, a lockout after the prompt, and `RetriesExhausted` are `Denied`; every code or result this build does not know, an error of another domain, a failed call, and an unknown lock state are `not_available`, `check_failed`, with the number. A macOS error is read as LocalAuthentication's only when its domain is `LAErrorDomain`.
9. **The words** are `{title}: {detail}` of `PromptText`, as the surface makes them: the tool and the first twelve characters of the change's hash. They are never empty, which macOS refuses with an exception.
10. **macOS keeps no answer.** Every context's reuse duration is set to none, so an unlock of the Mac a moment before does not pass the prompt.
11. **macOS holds each context on a thread of its own**, because the class may not move between threads and no claim is made that it may. The check that shows nothing runs on Tokio's blocking pool.
12. **Windows makes one owner window per ask:** hidden, of the system's `STATIC` class, so no window procedure of ours, on a thread that runs its messages so that the dialog can talk to its owner; the thread quits when the ask ends. No attempt is made to bring the dialog to the front, nor to find the system's dialog by its class and raise it: that acts on another process's window, and Windows refuses a foreground change to a process the person did not just use.

## What each proves, and what it does not

As record 0133 says: the system drew the prompt and checked the answer, so someone with the user's finger, face, PIN, or password answered at that moment. It does not prove that the engine that raised it is the real one, that its words are true, or that the store was not changed afterwards; the answer is a value in the engine's process. The macOS password, unlike a finger, can be typed by a program the person gave the Accessibility permission, if it knows the password.

## What was run, and what was not

- Run, on Linux: every session, every answer of the system's check, and every answer of the prompt, for both systems, against a made-up system; the deadline and a dropped ask take the dialog away; nothing is raised at or after the deadline.
- Compiled and linted with warnings denied, tests included, for `aarch64-apple-darwin` and `x86_64-pc-windows-msvc`, through a scratch crate holding `presence.rs`, its files, and their tests with a stand-in for `BoxFuture`. Every call, feature, and signature is type-checked; nothing is linked.
- **Not run anywhere:** any call into either system. CI on macOS and Windows is the first full compile and the first run of the real `available()`.
- **Not verified:** that the session's lock key on macOS, which Apple does not document, is present while the screen is locked (if not, the prompt is raised at a locked screen and ends at the deadline); that `WTSSessionInfoEx` gives a known lock state on the console of Windows 10 and 11 (if not, every ask there is `check_failed`, and the person's check shows it at once); that a program with no bundle gets the macOS dialog, and what its title says; that the Windows prompt comes to the front; that cancelling closes either dialog; and that `RequestVerificationForWindowAsync` accepts an owner window that is never shown.

## What follows

- The next CI run on macOS and Windows must show: `a2m-local` compiles and its lints pass; `the_codes_are_the_frameworks` and `the_values_are_the_systems` pass; `on_a_mac_the_real_prompt_says_what_it_can_do_by_name` and `on_windows_the_real_prompt_says_what_it_can_do_by_name` pass, and the reason each writes to the log is the one expected for a hosted runner (most likely `not_set_up` or `session_not_active` on macOS, `not_set_up` or `no_window_station` on Windows); a `check_failed` there is a finding to read, not a pass to wave through.
- A person, once on each system: the prompt comes to the front after a press in the browser; it shows our words, with the twelve characters the page shows; a prompt left alone closes at the deadline and the page says so; synthetic input from an ordinary program cannot press it; and on Windows with no Hello set up, and over remote desktop, the page names the reason.
- The record of an approval still says `os_prompt` until the policy engine has the three names (record 0142, point 6).

## What would reopen it

The Windows prompt failing to come to the front in the person's check; either dialog staying up after its ask is dropped; an advisory on either tree; the move of `windows-sys` to the 0.100 line; or a macOS release that drops the session's lock key or changes what `canEvaluatePolicy` answers at a locked screen.
