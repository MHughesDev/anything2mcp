# 0160. An idempotency key gives back its run, and `run.list` shows a caller's own runs

**Status:** Accepted. Design decision. The owner had not read this record when it was merged.

**Date:** 2026-11-17

**Changes:** the designs of [`a2m-actions`](../architecture/crates/a2m-actions.md), [`a2m-ledger`](../architecture/crates/a2m-ledger.md), [`a2m-mcp`](../architecture/crates/a2m-mcp.md), and [`a2m-api`](../architecture/crates/a2m-api.md); sentences of spec sections [208](../spec/2-kernel/208-runs-the-ledger-and-resume.md), [221](../spec/2-kernel/221-the-tool-surface-agents-see.md), and [222](../spec/2-kernel/222-front-doors-and-the-local-engine.md); the [ledger schema](../reference/ledger-schema.md). Takes up what [decision 0159](0159-a-lost-answer-is-a-write-in-doubt-at-the-doors-and-in-the-clients.md) left owed; follows [decision 0152](0152-the-action-registry-and-telemetry-after-their-safety-audit.md) on whose a run is and [decision 0116](0116-the-rest-router-takes-its-caller-from-the-mount-and-chooses-its-status-in-one-table.md) on the REST door's header.

## Context

Every door and both client libraries tell a caller whose answer was lost not to call again and to look at its runs. `run.list` answered "not built", and the `Idempotency-Key` the REST door carried was read by no handler: the ledger's run identity ties a second call to the first only while the first is unfinished, by its input.

## Decision

| Question | Decided | Alternative weighed |
| --- | --- | --- |
| What a key means | A call of `tool.call` that carries a key is the same call as the first one the same person made with it in the same workspace. It is given back that call's run, unfinished or finished, with the stored result shown and redacted as any result is, marked `repeated: true` and with a warning, and no other run is started. The same key with another tool, environment, input, or source is `input`, `idempotency_key_reused`, and starts nothing. The tool's version is not compared: the same call after a publish is still the same call | Folding the key into rule 6's identity. It would tie only unfinished runs, which is what a caller after a lost answer cannot rely on; and the same key with another input would be a new run, silently |
| How long it holds | For as long as its run is kept: a bound key leaves only with its run, when retention purges it (a trigger refuses any other delete, and the foreign key cascades). Nothing purges today | A time to live, as the draft schema's `expires_at` had. A key that ran out before its run did would let the same call start a second run |
| How it is stored | The workspace's keyed digest of the key, in `caller_idempotency` (migration `0013`, owned by the ledger), beside the digest of the call. A key is the caller's own text and can hold anything: an order number, a token pasted by mistake. A keyed digest lets the store match a key without keeping it, and confirms no guess to someone who reads the store. The digest is made under the purpose of record keys, with bytes that begin with a zero byte, which no record key's canonical form does, because `a2m-core` has no purpose of its own for it | The key as given. It is shown to nobody, but it would sit in the store and its backups. A plain digest: a short key could be guessed and confirmed |
| Its form | 1 to 200 printable ASCII characters, no space: the REST door's rule, now `CallerKey::new` in the ledger, checked by the dispatcher whatever door it came through (`input`, `idempotency_key_invalid`). Two different keys on one request are refused the same way | A wider set, such as any UTF-8. Headers carry ASCII, and one rule for every door is simpler |
| Order of writes | The key is held, with the call's digest, in the transaction that keeps the run's call, before the scheduler admits the run; bound to the run once admitted; let go when nothing was admitted. A key held with no run (a call stopped in between) is bound to the run that call was admitted as, found by caller, tool, environment, input, and time, before another run is started. In one process, two calls with one key are one at a time from the look at the key to the binding | Binding in the scheduler's admitting transaction. It would be one transaction, but `NewRun` and `Submission` are public types of other crates, built in a dozen test helpers; holding first and finding the run after a stop gives the same outcome |
| How MCP carries it | Neither revision the door speaks has an idempotency key, and a request's JSON-RPC id belongs to its connection: it is not carried to a new one, and the stateless revision has none. So a call carries `anything2mcp/idempotency_key` in its `_meta`, as the door already reads `anything2mcp/` keys, for a call by a published tool's own name; and `a2m_tool_call` has the argument `idempotency_key`, because it is a field of `tool.call` and every face is generated from that. A key in both places must be the same | An argument alone. A published tool's input schema is the target's, and a field added to it would change the tool. `_meta` alone: `a2m_tool_call` is the route a client takes for a tool it found by search, and an argument there is what an agent sees in the schema |
| `run.list` | The caller's own runs only, whatever role: a run is its person's ([decision 0152](0152-the-action-registry-and-telemetry-after-their-safety-audit.md)), and section 214 gives the auditor audit logs and traces, which `trace.show` and `audit.query` serve; no role lists another person's runs. Newest first, by when the run was opened, then by insertion. Filters: `state`, `tool`, `target`, `since`, `idempotency_key`. At most 100 a page, 20 by default; `after` names the last run of the previous page. Each entry: `run_id`, `tool`, `target`, `status`, `created_at`, `started_at`, `ended_at`, `in_doubt`, `waits_for_person`, the failure's class and code, and `next`. Served at `GET /api/v1/runs` | An offset, as the placeholder definition had. A run started between two pages would move every entry by one; a cursor does not |
| The lost-answer advice | With a key: "make the same call again with the same key". Without one: the exact call that lists the caller's runs since a minute before the call was sent, by the clock of the machine the door or proxy runs on, with the tool it named. The moment is shown and decides nothing | The engine's clock. The proxy and the client libraries have none, and a minute's margin covers the difference on one machine |

## Consequences

- An agent that lost an answer can make the same call again safely when it sent a key, and can find the run when it did not.
- A key given to an action that starts no run is answered with a warning that it was not used.
- `a2m-core` would do better with a digest purpose of its own for caller keys; moving to one makes every key held then unknown, so it is best done before a release.
- What the product's client and the two client libraries must change is in the report of this package: sending a key with every `tool.call`, and the exact advice.

## Added before merge: a key beside a listing

The command line and the client libraries have one place for a key, beside the input. For `run.list` a key carried there is the key to look for, the same as the `idempotency_key` filter in its input; two different keys in the two places are refused. So `anything2mcp run list --idempotency-key <key>` finds the run that key started, and the generated command line has no second flag of that name. A key beside any other action that starts no run is still answered with a warning that it was not used.
