# Research: the public landscape of tools that let agents reach software

**Status:** completed on 2026-11-18 from the projects' own repository pages, registry pages (npm and PyPI), and a few search results. Nothing was installed or run. Partial in one respect that matters: the repository pages were read through a page fetcher that returned the numbers the page shows, and could not show the date of the last commit or the date of a release. Activity is therefore given as stars, forks, open issues and commits as rendered on 2026-11-18, plus the date of the latest release on npm or PyPI where the project has a package. Several numbers are very large (see "What could not be verified"); they are recorded as the page rendered them, not vouched for. Feeds [spec section 106](../spec/1-product/106-what-it-latches-onto.md), the [roadmap](../plan/roadmap.md), and the open question of what the product should cover next. Extends [note 03](03-product-landscape.md), which covers web-to-API products only, and [note 16](16-rea-methods.md), which read one project from source.

## Question

The owner asked what else exists, so that the product can cover more of what a computer can reach and can learn from what is popular. Which projects matter in each of eight families; what can they do that this product, as its documents describe it, cannot; what makes the popular ones popular; and what does this product have that they do not.

## Answer in short

- **REA today** is an npm package (`rea-agents`, latest 6.9.0 published 2026-11-12, 35 versions, MIT) and a repository the page shows with 466k stars, 114k forks, 740 issues, 8,160 commits. Its README now leads with "one MCP for reverse engineering across binaries, applications, and runtime behavior", and `npx rea-agents setup` registers it with the person's agents. Note 16 read it at commit `8ffea11` when it had about 200 tools; the README no longer gives a count and links a generated tool catalog. It still discovers and explains; it still does not verify a write.
- **The closest projects to REA are the decompiler and debugger bridges**: a Ghidra bridge (12.0k stars, Apache-2.0), an IDA bridge (13.5k, MIT), a radare2 server (366, MIT), and x64dbg and Binary Ninja plug-ins that were found only by search. None carries more than a read-mostly doctrine: they hand an agent a large set of tools, some of which write into the analysis database or run arbitrary code.
- **The most used projects in this survey are not generators or bridges. They are browser drivers and reference servers**: the reference servers repository (92.1k stars), the Chrome DevTools server (58.0k), the Playwright server (39.8k), agent-browser (52.4k), the browser-use library (121.3k). Each is installed with one line from a package runner and gives a first result in one step.
- **Nearly everything popular in the browser and desktop families puts a model's choice inside every action** (the calling agent decides each click), or the project's own library does. This product's rule 1 forbids that at run time. Compiling tools from files is the product's difference, and it is also why a first result takes more steps here.
- **The biggest capabilities this product lacks** are, in order: the use of the person's own logged-in browser; an operating system's scripting interface as a reach (AppleScript and JXA, COM, D-Bus); catalogs and registries of ready-made integrations; screenshot-and-pixel control; and mobile applications. Two of these meet a rule. See the findings.

## 1. What REA is today, and its nearest neighbours

REA ([repository](https://github.com/morluto/rea), [package](https://registry.npmjs.org/rea-agents)): MIT, TypeScript on Node 22 or newer. Its README ([raw](https://raw.githubusercontent.com/morluto/rea/main/README.md)) says it lets an agent inspect native binaries, JavaScript and Electron applications, .NET assemblies, websites, and runtime behaviour without the source. Native analysis uses Hopper, Ghidra, IDA, or a fourth engine named Kuna; offline inspection covers ELF, PE, Mach-O, Go, Rust, Android packages, WebAssembly, EVM bytecode, and firmware. The first command is `npx rea-agents setup`, which asks which agents to register with and shows the changes before it makes them. It says results "include the evidence and limitations behind each conclusion" and that analysis runs locally; it states no write policy and no secrets policy. [Decision 0053](../decisions/0053-rea-is-studied-for-method-and-used-only-as-an-optional-provider.md) took its method and allowed it as an optional, read-only, off-by-default discovery provider; nothing in this survey changes that. What has changed since note 16 is only scale and positioning (version 6.9.0, the tool count no longer stated, a hosted-agent list that now names several agents).

The projects most like it, by what they do:

What they have that this product, as designed, does not: they sit inside the analysis tool and read its database, which gives an agent a decompiler view. The product has no such provider; REA is the optional bridge to the same engines. They are discoverers in the product's sense, never compiled tools, and none has a read-back for a write.

## 3. Findings

### 3.1 Capabilities the landscape has that this product lacks

Ranked by how many popular projects have them and how much of "anything a computer can reach" each opens. Each says what it would take, and whether it meets a rule.

1. **The person's own logged-in browser.** Playwright MCP (extension mode), Browser MCP, browser-use, agent-browser (attach to a running Chrome), reverse-api-engineer, and Chrome DevTools MCP (connecting to a running Chrome) all have it; together they hold the largest stars in the browser family. It opens every site the person is already signed into without a sign-in flow. **Meets rule 5**: the engine "never reads, copies, or drives" the everyday profile ([section 301](../spec/3-packs/301-the-web-pack.md), [decision 0031](../decisions/0031-the-browser-always-runs-with-a-profile-the-engine-owns.md)); decision 0031 itself says "a browser extension inside the user's profile, with consent: possible later as its own mode". This is an owner question, not a task. Browser MCP's pairing step (Allow once per computer, a six-digit code, a Stop button, incognito and browser pages blocked) is the model of a consent step if the owner ever wants the extension mode. Without it, the answer here remains: sign in once inside the engine-owned profile, which the person does by hand.
2. **An operating system's scripting interface as a reach.** macOS AppleScript and JavaScript for Automation (macos-automator-mcp, 883 stars and a knowledge base of hundreds of scripts), Windows COM (several Office servers, search only), PowerShell (a tool in Windows-MCP), and D-Bus (one server, search only). None is designed here: [section 106](../spec/1-product/106-what-it-latches-onto.md) lists "application with an automation interface" as **Cataloged** under the bridge archetype ("read-back: the matching read function"; "discovery: the interface's own type library or dictionary"). It would take a pack per system, each a helper process that calls the interface with typed arguments (the same shape as the command pack), the dictionary or type library as a discoverer, and read-back by a matching read call. **It meets no rule on its face**; it meets rule 7 (unknown means stop) only if the dictionary is the source of what may be called, and the refusal of "a general shell" and a general script runner stays. The risk is that a scripting bridge can reach anything the application can, so each write needs a declared effect. Of all gaps this opens the most (nearly every desktop application on two systems has such an interface, and many have no accessibility tree worth reading), and it has no rule against it.
3. **A catalog or marketplace of ready-made integrations.** Composio (1000+ toolkits), Zapier MCP (about 8,000 apps, per its own page), Activepieces (about 400 servers, 60% community-contributed), Pipedream (a component repository), the MCP Registry, the Docker catalog, and the curated lists, which lead the number of stars in the family. **Meets rule 9** for any target file for a real application: the project publishes no catalog of them, and "target files for real applications live outside this repository" ([AGENTS.md](../../AGENTS.md)). Two parts do not: (a) an agent-facing directory of the product's own packs and of third-party packs under the plug-in protocol ([section 202](../spec/2-kernel/202-kernel-and-packs.md)); (b) a way for people to publish target files themselves in their own places, in a form the product can find. Part (a) needs no rule change. Part (b) is the owner's question: is a listing of other people's target files, which the project does not host, within rule 9? Registry-style namespace checks (GitHub sign-in, DNS) are a tested way to say who published what.
4. **Pixel control and vision.** UI-TARS-desktop, the computer-use reference, Cua, Peekaboo, and Windows-MCP's screenshot tool. **Meets rules 1 and 7**, and [section 106](../spec/1-product/106-what-it-latches-onto.md) refuses "clicking by pixel or image" for that reason ("nothing improvises, and nothing can be verified against a picture"). Not proposed. What can be taken without a rule: a screenshot as evidence at build time in the scout, never as a run-time action.
5. **Mobile applications.** mobile-mcp (10.7k stars; accessibility tree first, pixels as fallback) and appium-mcp (520). No rule; it is cataloged, not designed, and needs a test stand (an emulator image). It would take a pack on the accessibility route, which is the route the desktop pack already takes on each system ([note 26](26-desktop-pack-before-it-is-built.md)).
6. **A natural-language task given to a browser, executed by a model at run time** (browser-use, Stagehand, UI-TARS). **Meets rule 1 directly.** Listed because it is the largest single reason these projects have stars; not proposed. The scout may use an agent at build time ([section 402](../spec/4-building-tools/402-the-scout-and-who-does-what.md)), and the product's answer is to compile what the agent found.
7. **Gateways that wrap REST and gRPC at run time** (Context Forge, grpc proxies). No rule is met by wrapping; the question is how a run-time wrapper would fit the guarantee that a tool was proven before it ran: it would be unverified. The design already imports published descriptions into findings pinned with a digest ([section 106](../spec/1-product/106-what-it-latches-onto.md)) and the compiler proves them. A gRPC reflection reader is a small addition to the HTTP pack's import formats; section 106 lists "procedure-call" services as designed.
8. **A debugger and decompiler bridge for binaries.** Present in four projects; REA covers the whole of it. [Decision 0053](../decisions/0053-rea-is-studied-for-method-and-used-only-as-an-optional-provider.md) already allows REA as an optional discovery provider; an equivalent for one of the single-engine servers (such as the radare2 server, which ships a read-only mode and a sandbox lock) would be another entry of the same kind. Not a gap in the design.
9. **Industrial and serial reach by named protocol.** OPC UA servers exist (one with writes off by default behind a control profile); section 106 designs Modbus-style registers and serial consoles and does not name OPC UA. A candidate for a device-pack mode.
10. **Telemetry and hosted services** (usage statistics in Chrome DevTools MCP and Windows-MCP, hosted catalogs). The product has a rule against phoning home. Not a gap.

### 3.2 What makes the popular ones popular

Taken from what the pages show, not from guesses.

- **A first result in one line, with no authoring.** Every most-used project in the browser and reference families starts with one line from a package runner: `npx @playwright/mcp@latest`, `npx -y chrome-devtools-mcp@latest`, `npx -y @modelcontextprotocol/server-memory`, `npm install -g agent-browser` then `agent-browser install`, `npx rea-agents setup`, `uvx windows-mcp serve`, `uvx workspace-mcp --tool-tier core`, `pip install 'markitdown[all]'`, `npx @bytebase/dbhub@latest --transport http --port 8080`, `npx @toolbox-sdk/server --config tools.yaml`. The nearest thing here is a command that reads one value from the test application.
- **They are installed by the package manager the person already has.** In the first commands listed above, most use `npx` (Node), several use `uvx`, `uv` or `pip` (Python), and one each use `cargo` (Apollo MCP Server) and `brew` (Peekaboo, container-use). This product's packaging is designed for pip, npm, and crates.io ([note 21](21-wheel-and-npm-packaging.md)), but none of the three names was held on the date publishing setup records ([section 605](../spec/6-running-it/605-packaging-and-release.md)).
- **The README leads with the client config and a one-line description.** Playwright MCP and Chrome DevTools MCP lead with the JSON that goes into an agent's configuration; REA leads with a screenshot of the product in its host and a warning to get it only from official sources; ha-mcp leads with a hosted demo that needs no Home Assistant of one's own; Windows-MCP lists the tools. Each README names the agents it works with.
- **Many agents, no preferred one.** REA lists Claude Code, Codex, Cursor, Gemini CLI, and Grok Build; Chrome DevTools MCP lists Antigravity, Claude, Cursor, Copilot. The product states the same rule (no client is special).
- **A registry and a list.** The reference-server repository points the reader to the MCP Registry for community servers; the Registry (7.5k stars) checks namespaces and was in preview, with an API freeze at v0.1 per its page; the curated list has 97.8k stars. Smithery, Glama, and mcp.so exist in search results (not opened).
- **A place for the community to add.** Activepieces says 60% of its pieces are community-contributed; Pipedream hosts all its components in the repository and lets people publish actions; macos-automator-mcp ships a searchable script corpus. The product's equivalent is the plug-in protocol and target files kept outside the repository.
- **Release cadence.** npm and PyPI records on 2026-11-18: Playwright MCP 438 versions, latest 2026-11-09; Chrome DevTools MCP 66 versions, 2026-11-11; Stagehand 1,103 versions, 2026-11-04; agent-browser 139 versions, 2026-11-12; Desktop Commander 131 versions, 2026-11-12; FastMCP 148 releases, 2026-11-17; browser-use 153 releases, 2026-11-16; Composio's core package 158 versions, 2026-11-17; REA 35 versions, 2026-11-12. The projects with the most stars published within the last two weeks.
- **A tool to see the tools.** The MCP Inspector is one command. It is how people check a server before trusting it.
- **A named, narrow safety control, usually stated honestly as limited.** Several READMEs say their own switch is "not a security boundary" (Playwright MCP, DBHub, Windows-MCP's takeover, Desktop Commander). This candour is itself a feature of the more trusted ones.
- **Where announced** was not read from any source in this survey and is not claimed.

### 3.3 What this product has that they do not

Stated modestly, and only where the documents say it and the pages read here show no equivalent. "Not stated on the page" is weaker than "absent"; a project may do more than its page says.

- **No model at run time, as a rule.** Only two projects here say anything like it: Terminator (recorded workflows replay as code, with a model "only when recovery is needed") and the code generators (OpenAPI, GraphQL, SQL servers), which are themselves deterministic. Every browser and desktop project that leads in stars chooses each action with a model.
- **A write is recorded before it is made and read back after.** No page read states this. The nearest are ha-mcp (automatic backups, user approval policy), OPCUA-MCP (writes need an explicit control profile), Kubernetes and Desktop Commander (blocklists and non-destructive switches), none of which says a written value is read back and compared.
- **A person at the machine approves a write, and an agent cannot approve its own.** The pages show read-only switches and per-tool switches that the same configuration controls. Ha-mcp's approval policy is the nearest.
- **Secrets never reach the caller, by a rule and a wrapper type.** Playwright MCP and browser-use describe their own secret options as conveniences ("not a security feature"; "model-written Python can read the value"); Desktop Commander logs tool arguments without redaction and says so.
- **Nothing phones home.** Chrome DevTools MCP and Windows-MCP ship usage statistics on by default with an opt-out; the product has none.
- **An evidence ladder for what the scout found, and findings that cannot be raised above their source.** REA records evidence with levels ([note 16](16-rea-methods.md)); this product's contribution is that a finding cannot exceed `discovered` without proof.
- **Safety audits and fault-injection tests as a condition of merging** ([AGENTS.md](../../AGENTS.md)); not something a README in this survey claims.
- **One engine for many kinds of system** under one policy gate, one ledger, one set of tool names. The surveyed projects are one server per kind.

A README could lead with: *"Your agent proposes; a person approves; the write is recorded first and read back after; no model runs when a tool does."* That sentence is supported by the design; it is **not yet shown by running code for any real write over several kinds of system**, and the roadmap says so (package 3.3 is marked ready, with one write built through a test pack). It should not be said before it is true.

## What it means for the design

- **Nothing in this note overturns a spec section.** The survey confirms the rules cost the product the browser and desktop projects' main draw (a model that does anything now) and the reuse of the person's session.
- **Candidate additions, none yet proposed as a decision** (the owner decides which become packages): (1) a bridge pack for operating-system scripting (AppleScript and JXA, COM, D-Bus), at the cataloged row of section 106; (2) mobile accessibility as a pack after the desktop pack; (3) a gRPC-by-reflection reader in the HTTP pack's import formats; (4) an OPC UA mode in the device pack; (5) a one-command first result and a tool inspector for compiled tools (an `anything2mcp` command that lists a built server's tools), taking the Inspector's example; (6) a plain-language page that says what the product has that others do not, with the claim held until it is shown.
- **Questions for the owner, not decisions** (each touches a rule):
  1. Rule 5 and decision 0031: is a consented browser extension in the person's own profile, as its own mode, ever permitted? (Five of the most-used browser projects have it.)
  2. Rule 9: may the project list or link target files that other people publish and host, without hosting them or naming a real application in this repository?
  3. Rule 1 and section 106's refusal: is a screenshot ever permitted as build-time evidence in the scout only? (This repository's design already uses an agent at build time; the question is only about pictures.)
  4. Section 106's refusal of "a general shell" stays; Desktop Commander's popularity shows the demand, and its own page shows what its safeguards cannot do.
