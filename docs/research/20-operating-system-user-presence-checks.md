# Research: operating-system user-presence checks

**Status:** completed on 2026-11-17 by reading primary sources and by a small type-check probe. It answers brief 27 of [open research](11-open-research.md). Feeds [spec section 503](../spec/5-security/503-approval-and-sign-in-surfaces.md), the local-engine part of [spec section 222](../spec/2-kernel/222-front-doors-and-the-local-engine.md), the protected settings of [section 502](../spec/5-security/502-defending-against-a-manipulated-agent.md), the design of [`a2m-local`](../architecture/crates/a2m-local.md), and hypothesis H-12. Nothing here pressed a real prompt: no person was at a Windows or macOS machine, and the Linux container has no system bus. Each claim says whether it was run, read in source, read in documentation, or reasoned.

## Question

When a person presses Approve on the engine's page, which prompt that the operating system owns can the engine raise to prove a person is at the machine? The engine is a background process running as the user, with no window of its own. For each system: what the prompt shows, what it needs, when it is missing, what a program running as the same user can do against it, how Rust calls it under this project's dependency rules, and what happens where there is none.

## Answer in short

| System | The prompt | Our text in it | What it needs | Rust path |
| --- | --- | --- | --- | --- |
| Windows 10 and 11 | Windows Hello through `UserConsentVerifier`, by its desktop interop `IUserConsentVerifierInterop::RequestVerificationForWindowAsync`: face, fingerprint, or the Hello PIN | Yes: one message string | Windows Hello set up for the user, at least a PIN; a window handle; an interactive session | The `windows` crate 0.62.2, features `Security_Credentials_UI` and `Win32_System_WinRT`; 10 crates new to the workspace |
| macOS 13 and later | `LAContext.evaluatePolicy` with `deviceOwnerAuthentication`: Touch ID, a paired watch, or the account password | Yes: the reason line; the system adds the program's name | A logged-in graphical session | `objc2-local-authentication` 0.3.2 with `objc2`, `objc2-foundation`, `block2`; 5 crates new |
| Linux desktops | polkit `CheckAuthorization` over the system bus, for an action of our own with `auth_self`; the desktop's agent asks for the user's password | **No.** The message is fixed in the action's policy file. An unprivileged caller may not pass details or change the message | An administrator installs the policy file; polkitd and a session agent run; the engine runs inside the local, active session | `zbus` 6.3.0 (no default features, `tokio`, `proxy`) and `zbus_polkit` 6.0.0; 14 crates new; passes the licence and advisory checks, run here |
| Headless Linux, containers, SSH, remote shells | None | | | `NotAvailable` |

What every one of them proves: at that moment, someone with the user's finger, face, PIN, or password answered a prompt the operating system drew. What none of them proves: that the engine which raised it is the real engine, that the text it showed is true, or that the engine's store was not changed afterwards. Section 222's "an agent with a shell cannot answer it" is true of the prompt itself and is corrected below to say what it protects.

Recommendation: build Linux first, because only there can the whole path be proved by a machine; then macOS and Windows in one slice, each checked once by hand. No fallback dialog in the first build.

## Windows

**The interface.** `UserConsentVerifier` "checks for availability of a verification device (such as a Microsoft Passport PIN, Windows Hello biometric, or fingerprint reader), and performs a verification" ([class documentation](https://github.com/MicrosoftDocs/winrt-api/blob/docs/windows.security.credentials.ui/userconsentverifier.md)). A desktop program must not call `RequestVerificationAsync`, which is for packaged apps; it gets the class's activation factory as `IUserConsentVerifierInterop` and calls `RequestVerificationForWindowAsync(hwnd, message)` ([interop method](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/userconsentverifierinterop/nf-userconsentverifierinterop-iuserconsentverifierinterop-requestverificationforwindowasync.md)). The message is "a message to display to the user for this biometric verification request", so the tool, the target, and a short form of the diff's hash can appear in it. The answer is one of `Verified`, `DeviceNotPresent`, `NotConfiguredForUser`, `DisabledByPolicy`, `DeviceBusy`, `RetriesExhausted`, `Canceled`. `CheckAvailabilityAsync` answers `Available` or one of the same reasons without prompting, which is what `doctor.run` needs. Read in source.

**What it needs.** A window handle, "the window of the active application". The engine has none. The choice is a small window of the engine's own, or a handle it does not own. Whether the prompt then comes to the front is not known: Windows limits which process may take the foreground, and the press that led here went to the browser, not the engine. This must be tried by hand. Windows Hello must be set up for the user; a PIN is enough and needs no special hardware. A service in session 0 cannot show any interface, so the hardened Workstation service cannot raise this prompt itself. Over remote desktop and at a locked screen the behaviour was not verified; the design must read the availability before each prompt and treat anything but `Verified` as no.

**The other Windows prompt.** `CredUIPromptForWindowsCredentials` can show the "Windows Security" password dialog on the secure desktop with `CREDUIWIN_SECURE_PROMPT`, and takes a caption and a message ([function](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/wincred/nf-wincred-creduipromptforwindowscredentialsw.md), [its text fields](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/wincred/ns-wincred-credui_infow.md)). It hands the typed credential back to the caller, packed, and "does not save credentials". The engine would then hold the person's Windows password and would have to check it itself with a logon call. That breaks rule 4 in spirit and is refused. It is in `windows-sys` already; not needed.

**Against a program running as the user.** A biometric cannot be typed. The PIN and the face are checked by the system, not by the caller. A pull request to an open-source password manager, written in September 2026, reports that since a January 2026 update the "Windows Security" credential prompt belongs to `CredentialUIBroker.exe` at an integrity level above an ordinary program's, so a normal program's synthetic keys and UI Automation calls are dropped ([the report](https://github.com/keepassxreboot/keepassxc/pull/13648)). That is a third-party measurement, not Microsoft's word, and it was about the credential prompt, not certainly the Hello prompt. Whether a low-level keyboard hook running as the user can read a PIN typed into it is not verified. The answer is a value in the engine's own process: Microsoft's own blog has said this API "confirms that the user is there, but it doesn't protect any data" (title read in a search result; the blog's host is blocked here, so the post was not opened: [the post](https://devblogs.microsoft.com/oldnewthing/20240924-00/?p=110308)). A program running as the same user can open the engine's process for writing, as Windows allows for an unprotected process of the same user at the same integrity, and change the answer.

**Rust.** `windows-sys` holds plain functions and constants only; it has no WinRT activation and no COM interfaces (searched in its 0.61.2 source). The `windows` crate 0.62.2 has `UserConsentVerifier`, its result enums, and `IUserConsentVerifierInterop` with `RequestVerificationForWindowAsync` (read in source). Its factory call initializes the multithreaded apartment by itself when none is set (read in `windows-core` 0.62.2). The returned operation is awaited through `windows-future`, and has `Cancel` for the end of the approval window. The probe type-checks. It adds 10 crates on Windows: `windows`, `windows-core`, `windows-future`, `windows-collections`, `windows-numerics`, `windows-result`, `windows-strings`, `windows-threading`, and two macro crates. All are MIT OR Apache-2.0. The project behind them now steers libraries away from the `windows` and `windows-sys` umbrella crates, towards focused crates and bindings generated by `windows-bindgen`, and has published its focused crates at 0.100 while the umbrella stays at 0.62.2 of October 2025 ([the project's guide](https://github.com/microsoft/windows-rs/blob/master/docs/readme.md)). For the first build the umbrella crate with two features is the verified path. Generating the dozen needed bindings with `windows-bindgen` over `windows-core` 0.100 is the later, lighter one, best done when `windows-sys` in the workspace moves to the same line.

## macOS

**The interface.** `LAContext.evaluatePolicy(_:localizedReason:reply:)` with `LAPolicy.deviceOwnerAuthentication`. In macOS that policy uses Touch ID or a nearby paired watch first, and the user's password when those are not available ([policy](https://developer.apple.com/documentation/localauthentication/lapolicy/deviceownerauthentication)). The reason string is ours. Apple says not to put the program's name in it, because the system shows the name in the dialog's title ([method](https://developer.apple.com/documentation/localauthentication/lacontext/evaluatepolicy(_:localizedreason:reply:)), [the reason](https://developer.apple.com/documentation/localauthentication/lacontext/localizedreason)). So the tool, the target, and a short hash can appear. The result comes back as a yes or no to a callback ([logging a user in](https://developer.apple.com/documentation/localauthentication/logging-a-user-into-your-app-with-face-id-or-touch-id)). When no interface may be shown, the call fails with `notInteractive` ([error](https://developer.apple.com/documentation/localauthentication/laerror-swift.struct/code/notinteractive)). Read in documentation.

**What it needs.** A graphical login session for the user. No bundle and no entitlement is named in the documentation for this call. That a plain program with no bundle gets the dialog, what name its title shows, and what happens over SSH and at a locked screen were not verified. The binary should be signed with the hardened runtime in any case: it is what stops another program of the same user from attaching to the engine or loading code into it. Release signing is section 605's concern.

**Against a program running as the user.** Biometrics and the watch cannot be typed. The password fallback can be typed. Posting synthetic events on macOS needs the Accessibility permission, which a person grants to a program; many developers have granted it to their terminal, and so to whatever runs in it. Whether the password field of this dialog accepts such events was not found in any source; one security researcher's write-up describes synthetic clicks that got past other system prompts in the past ([secondary source, not opened](https://objective-see.org/blog/blog_0x36.html)). Apple's own words fix the main limit: the app "receive[s] only a Boolean result". A stronger form exists: a key item in the keychain whose access needs user presence, so that the Secure Enclave gates the item, not the app ([keychain items](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)). That would let the engine sign the diff's hash with a key nobody can use without the gesture. It is a later option, noted under the design consequences.

**Rust.** `objc2-local-authentication` 0.3.2 (October 2025; licence Zlib OR Apache-2.0 OR MIT, so MIT applies) has `LAContext::new`, `canEvaluatePolicy_error`, `evaluatePolicy_localizedReason_reply`, `invalidate` for the end of the window, and `setInteractionNotAllowed` (read in source). With `objc2` 0.6.5 (October 2026), `objc2-foundation` 0.3.2 and `block2` 0.6.2 it adds 5 crates and no C. The calls are `unsafe` and live in one module, as the crate already does for its Windows calls. The probe type-checks.

## Linux

**The interface.** polkit's `org.freedesktop.PolicyKit1.Authority.CheckAuthorization(subject, action_id, details, flags, cancellation_id)` on the system bus, with the flag `AllowUserInteraction`, which the interface says to pass only when a person's action led to the check, as a press of Approve does ([the interface](https://github.com/polkit-org/polkit/blob/main/data/org.freedesktop.PolicyKit1.Authority.xml)). The subject is the engine's own process, given as process id, start time, and user id; for its own process the id cannot be reused while it runs. The action is ours, declared in a `.policy` file under `/usr/share/polkit-1/actions`, which only an administrator can write ([polkit manual](https://github.com/polkit-org/polkit/blob/main/docs/man/polkit.xml)). Its defaults must be `allow_any` no, `allow_inactive` no, `allow_active` `auth_self`. Never `auth_self_keep`, which keeps the answer for about five minutes and would let the next approvals pass with no prompt. The session's agent shows a dialog with the action's message and a password field. `polkit-agent-helper-1`, which runs with privilege, checks the password through PAM, so a fingerprint works where PAM is set up for one. The manual warns that `auth_self` "is not restrictive enough for most uses on multi-user systems". Here that is the point: the person is proving it is them, not gaining a right.

**Our text cannot appear.** A caller that is not root and not named as the action's owner may check its own processes only if it passes no details: "otherwise you'd be able to spoof the dialog" ([polkit source, `polkitbackendinteractiveauthority.c`](https://github.com/polkit-org/polkit/blob/main/src/polkitbackend/polkitbackendinteractiveauthority.c)). The `polkit.message` override and the `$(key)` substitution both come from details. So the dialog says what the policy file says, the same for every approval and every protected setting. An action can name owner users in an annotation, who may then pass details; an installed file cannot know a machine's users in advance, and an owner may also check other users' processes. Not recommended.

**What it needs, and where it is missing.** polkitd, a system bus, our policy file, and a session agent; the engine must sit in a local, active login session, or the `allow_any` default, no, applies. Over SSH, in a container, on a headless server, and for an engine started outside the login session (for example by a user service manager), the answer is no, which is right. With no agent registered, `pkcheck` exits 2 for "no suitable authentication agent"; the bus call is expected to answer not authorized in the same way (not run). On the container here the call failed at once because there is no system bus.

**Against a program running as the user.**

- Any process of the same user may register its own authentication agent for the engine's process (polkit source: a process subject is allowed, and the caller and the subject must be the same user). The request then never reaches the screen. That agent must still pass the password through the privileged helper, so it needs the password.
- Under X11 any program on the display can read keystrokes and send synthetic ones, so a typed password can be captured once and replayed. Under Wayland, a dialog drawn by the compositor or by another client cannot be read or driven that way. Reasoned from how the two display systems work; not run.
- A person who has typed their password into a terminal that a coding agent controls, for `sudo` for example, has given that agent the password.
- So on Linux the check proves "someone who knows the user's password, or holds the finger PAM accepts". It is weaker than on Windows and macOS, and its text says nothing about the diff.

**Rust.** Decision 0123 removed `zbus` 5 because three crates under it were declared unmaintained when they merged into `zbus` 6. `zbus` 6.3.0 (2026-11-13) and `zbus_polkit` 6.0.0 (2026-10-20), MIT, with `zbus` default features off and `tokio` and `proxy` on, add 14 crates on Linux: `zbus`, `zbus_macros`, `zbus_utils`, `zbus_polkit`, `zruntime`, `zcheapstr`, `endi`, `async-trait`, `futures-io`, `hex`, `ordered-stream`, `serde_repr`, `static_assertions`, `uuid`. Tokio, serde, `rustix`, `libc`, and `socket2` are already in the workspace. The advisory check passes on this tree (run). `zbus_polkit` gives `AuthorityProxy::check_authorization`, `Subject::new_for_pid`, and `CheckAuthorizationFlags::ALLOW_USER_INTERACTION` (read in source); the cancellation id, with `CancelCheckAuthorization`, ends a prompt at the end of the approval window. This also bears on decisions 0120 and 0123, whose crates still stand on `zbus` 5: two major versions of `zbus` in one tree should be avoided.

**The helper-program path.** `/usr/bin/pkcheck --action-id <ours> --process <pid>,<start-time>,<uid> --allow-user-interaction`, started by the engine with its absolute path and an empty environment, makes the same call and answers by exit code: 0 authorized, 1 not, 2 no agent or no interaction, 3 dismissed, 126 and 127 errors ([pkcheck manual](https://github.com/polkit-org/polkit/blob/main/docs/man/pkcheck.xml)). It must never get `--enable-internal-agent`, which would ask for the password in the engine's own standard input. It proves exactly what the bus call proves: the program is root-owned, so a same-user program cannot swap it, though it can swap the engine. Its weaknesses: a child process per prompt, the answer as an exit code, ending a prompt by killing the child (whether polkit then closes the dialog was not verified), and distributions that package it apart from polkitd. It needs no crate, and is the fallback if the bus crates fail a later check. `pkexec` runs a program as another user and is not a prompt for this; PAM alone shows nothing.

## What the prompt proves, plainly

A coding agent with a shell runs as the person. Against the prompt itself:

| It can | Windows Hello | macOS | Linux polkit |
| --- | --- | --- | --- |
| Press Approve on the page | Yes, if it fetches the page first; the prompt follows | Same | Same |
| Answer the prompt by synthetic input | Not for a face or finger. For the PIN, the dialog drops ordinary programs' input since early 2026 by one third-party report; not verified for this dialog | Not for Touch ID or the watch. For the password, it needs the Accessibility permission and the password; whether the dialog accepts the events is not verified | Under X11, yes if it knows or has captured the password. Under Wayland, no |
| Take the prompt away from the screen | No | No | Yes, by registering its own agent for the engine's process; it still needs the password |
| Read the answer | It is a value in the engine's process | Same | Same |

Against the engine around the prompt, all three systems are alike. A program running as the user can replace the engine's binary or start its own build in its place; that copy can raise a real prompt with false words ("approve the change you just looked at") and record whatever it likes. It can change the store, and so the recorded approvals, as section 222's limit already says. On Windows and Linux it can also write into the running engine's memory: Windows allows a same-user process to open another unprotected one at the same integrity, and on Linux, where the Yama setting is 1 (some distributions' default), tracing is limited to a process's own descendants, which an engine started detached is not; where it is 0, any process of the user may trace it; and nothing stops the agent from starting the engine itself under a tracer. Reasoned from each system's documented default rules; not run. On macOS a hardened, signed engine refuses attachment, but its files are still the user's.

So the prompt stops: an agent that acts only through the engine's tools, commands, and page; scripts and synthetic clicks; and a person approving by accident. It does not stop a hostile program that rewrites the engine or its files. Section 222 says the second half in its "limit" paragraph but says the first half too broadly. The dialog alone stops less than it says: UI Automation on Windows, the Accessibility permission on macOS, and the X test extension on X11 let a same-user program press an ordinary dialog's button.

## The fallback where none is usable

The "dialog-only fallback" of section 503 is a native window that shows the tool and the counts and has two buttons. It proves nobody. It stops a person approving by mistake, and an agent that has only the engine's tools and no shell. On Linux it would need either a GUI toolkit or a helper program such as a desktop dialog tool, and a display; on a headless machine it does not exist. It is worth building only after the real prompts, and an approval through it must stay recorded with the check `not_available`, as `PromptAnswer::Confirmed` already does, with protected settings refused.

`doctor.run` should report the kind and the reason, with the remedy:

| Kind | Reason | What doctor says |
| --- | --- | --- |
| `os_prompt` | | "Approvals on this machine need Windows Hello", "need Touch ID, your watch, or your password", or "need your password through polkit; its dialog cannot show which change it is for, so check the page first" |
| `not_available` | Windows Hello not set up | Set up a Windows Hello PIN in the account settings |
| `not_available` | Windows Hello disabled by policy, or remote session | Approve at the machine itself, or use a server profile |
| `not_available` | No graphical session, SSH, container, headless | Nothing on this machine can approve; use a server profile or approve at the desktop |
| `not_available` | Linux: policy file missing | An administrator installs the shipped policy file into `/usr/share/polkit-1/actions` |
| `not_available` | Linux: no system bus, no polkitd, or no agent | Start a desktop session with a polkit agent |
| `dialog_only` | (later) | "Approvals use a confirmation dialog alone. It stops mistakes; a program running as you can press it" |

## What this means for the design

1. **The interface stays.** `PresencePrompt` with `kind` and `ask` fits all three. Three changes: `presence_available` becomes a check made at run time that returns the kind and a reason, because Windows Hello can be set up or removed while the engine runs; `system_prompt` picks the system's prompt; and `ask` takes a deadline, at which it cancels the prompt (`Cancel` on Windows, `invalidate` on macOS, the cancellation id on Linux) and answers `Dismissed`.
2. **One prompt at a time.** A second press while a prompt is up is refused with `busy`, not queued, so a person never answers a prompt meant for another change.
3. **The words.** On Windows and macOS the prompt carries the tool, the target, and the first twelve characters of the diff's hash, and the page shows the same twelve characters beside Approve, so the person can match them. On Linux the policy file's fixed message tells the person to check the page, and doctor says the dialog cannot name the change.
4. **What is recorded.** The approval records which prompt answered (`windows_hello`, `local_authentication`, `polkit`), so an audit can tell a strong check from a weak one.
5. **Section 222 is corrected** to say what the prompt stops and what it does not, and that the dialog alone can be pressed by a program running as the user.
6. **Later, a signed approval.** Windows Hello's key credentials and a macOS keychain key gated by user presence can sign the diff's hash with a key the engine cannot use without the gesture. That makes a forged approval in the store detectable by anyone holding the public key outside the user's reach, as a server's console could. Linux has no equivalent without a hardware key. Not for the first build.

## Not verified

- Nothing was pressed. No real prompt was raised on any system.
- Windows: whether the Hello prompt comes to the front for a process with no foreground right; its behaviour over remote desktop and at a locked screen; whether its PIN field drops synthetic input and hooks, as one third-party report says of the credential prompt; which process draws it.
- Windows: the blog post that says the verifier protects no data was not opened; its host is blocked here, as is Microsoft's documentation site. Microsoft's documentation was read from its published source repositories instead.
- macOS: whether a program with no bundle gets the dialog and what its title shows; behaviour over SSH and at a locked screen; whether the password field accepts synthetic events from a program with the Accessibility permission.
- Linux: the bus call against a real polkitd with no agent; whether killing `pkcheck` closes the dialog; whether every mainstream distribution installs `pkcheck` with polkitd; the Wayland and X11 claims, which are reasoned.
- Decision 0120's desktop crates were not checked against `zbus` 6.
