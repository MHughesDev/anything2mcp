# 220. Actions and the authoring interface

Everything a person, an agent, or a program can ask Anything2MCP to do, apart from calling a target's own tools, is an action. An action is defined once, and its command, MCP tool, REST route, and SDK method are generated from that one definition. This section says what an action is, how its faces are made, what a developer or a coding agent holds in its hands when it builds tools over a system, and the rules every action and tool follows so that agents can use them well. The full list of actions is the [action catalog](../../reference/action-catalog.md). What the building actions do, step by step, is in [section 401](../4-building-tools/401-overlaying-tools-on-an-existing-system.md) and [section 402](../4-building-tools/402-the-scout-and-who-does-what.md). The tools a finished target offers agents are in [section 221](221-the-tool-surface-agents-see.md). Built today: partly; [section 704](../7-project/704-readiness.md) gives the detail.

## Which interface, for whom

| Interface | Role | Why |
| --- | --- | --- |
| Commands plus target files | **Primary for building.** Coding agents with a shell, and people | Agents are strongest at running commands and editing files; nothing enters the agent's context until it is used; works with every agent |
| MCP authoring tools | **Second door for building.** Agents with no shell, such as desktop chat clients and hosted agents | The only route for those agents; structured results; but every listed tool costs context, so the list stays short |
| Python and TypeScript SDKs | For software that calls finished tools, and for tests | Building through code would replace the declarative files that keep tools reviewable |
| REST API | For other software and the admin console | An agent gains nothing from it over commands |
| Guidance file | Always | Teaches the loop; makes every other interface work better |

Published comparisons of commands and MCP for coding agents agree on the main point: tool definitions that load up front cost context on every turn, while a command costs nothing until it runs. Several also note that the real difference is loading eagerly against loading on demand, not the protocol. Anything2MCP therefore makes both faces load on demand ([research note 12](../../research/12-packaging-and-agent-interfaces.md)).

## One action registry

Every action is defined once, in Rust, in `a2m-actions` ([crate design](../../architecture/crates/a2m-actions.md)). A pack or a plug-in may contribute actions under its own name space, through `a2m-provider`; the registry refuses a duplicate name and a contributed action outside its provider's name space.

| Part of a definition | Meaning |
| --- | --- |
| Name | `noun.verb`, checked; the noun is a word of the command line |
| Summary | One line; its first 240 characters are enough to choose the action |
| Input and output schemas | Strict input, no unknown fields; the output schema is published |
| Examples | One to three, from recorded tests |
| Shape | Inspect, list or search, trace, compare, observe or capture, or change: one per action |
| Effect | A fixed effect class, or, for `tool.call`, the effect of the published tool called |
| Lowest role | The role column of the catalog ([section 214](214-access-control-toolsets-and-tenancy.md)) |
| Listed | Whether its MCP tool appears in the `use` or `build` toolset, or is reached through `a2m_action_run` |
| Long-running | Whether it returns a `run_id` at once |
| Health need | Whether it can run with the engine degraded or stopped ([section 224](224-when-the-engine-itself-fails.md)) |
| Person need | Whether the act is a person's, such as `version.publish` or a protected `config.set`, and needs proof that a person is present |
| Handler | The kernel's own function, a provider's handler, or, for the `engine.*` actions that act on the process, the client end ([section 222](222-front-doors-and-the-local-engine.md)) |

**Recording an approval is not an action.** Recording a person's approval or refusal has no definition in the registry and so no generated face: no command, tool, or route can approve. The approval surface is given a handle that can record an approval or a refusal and nothing else ([section 212](212-policy-and-approvals.md), [section 503](../5-security/503-approval-and-sign-in-surfaces.md)). A test walks every generated face and fails if one reaches it.

### Every face generated

| Face | Form | For the action `target.probe` | Generated by |
| --- | --- | --- | --- |
| Command | `anything2mcp <noun> <verb>` | `anything2mcp target probe https://app.example.com` | The product crate, from the registry, when the program starts |
| MCP tool | `a2m_<noun>_<verb>` | `a2m_target_probe` | `a2m-mcp`, when a tool list is asked for |
| REST route | `POST /api/v1/actions/<noun>.<verb>` | `POST /api/v1/actions/target.probe` | `a2m-api`, when its router is built, with any resource-shaped alias the definition declares |
| SDK method | `client.<noun>.<verb>()` | `client.target.probe(url=...)` | A code-generation task, from the action catalog, written to `bindings/` |
| Reference page | `anything2mcp docs <name>` | `anything2mcp docs target.probe` | The same task, from the action catalog and the documents |

- **No hand-written face.** A parity check enumerates the live command tree, MCP tool list, router, and SDK method list, and compares each with the registry. It fails on anything extra or missing. Process commands and shortcuts are the only words allowed beside the nouns.
- **Same behavior everywhere.** All faces call the same dispatcher, so a result is identical whichever way it was asked for. A parity test calls each action through each face with the same input and compares the results.
- **A action catalog.** The build writes the catalog of actions and tools with a digest. The engine checks the digest at start; CI fails when the checked-in SDKs were generated from another digest; and a test compares the action catalog with a live listing through a real client library.

### The dispatcher

A front door authenticates the caller and builds a request; it decides nothing. The dispatcher then does, in this order, and every refusal is an ordinary failure:

1. **Find.** An unknown name is `input` / `schema_invalid`, with the nearest names as the fix.
2. **Validate.** The input against the action's full schema, never the compact one a tool list showed.
3. **Health.** The action's health need against the engine's health state.
4. **Decide.** One decision from the policy engine, recorded whether it allows or refuses. The dispatcher refuses to go on without one.
5. **Person.** For an act that is a person's, proof of presence from the role's person surface. A caller marked as an agent never satisfies it: its ask is shown to the person on a page of the person surface, and only a press there, and the prompt it raises, carries the act out, once ([decision 0163](../../decisions/0163-a-persons-act-an-agent-asks-for-is-carried-out-on-a-page-of-the-person-surface.md)); on one machine the proof comes only from the operating system's prompt.
6. **Run.** The handler. A long-running action is submitted to the scheduler and returns its `run_id` at once.
7. **Shape.** Every outgoing string passes the redactor. Text that came from a target is marked untrusted. The result is cut to its size cap, and says which limit cut it. A large result is kept as a blob and returned as a reference with a size and a summary. `next` is added.

The response has the same structure for every face: `ok`, `action`, `result` or `error`, `warnings`, `next`, and an exit class. Each face renders it without branching on its content.

### Shortcuts and process commands

Single-word commands remain for people: `init`, `add`, `learn`, `lint`, `try`, `test`, `ready`, `publish`, `status`, `call`, `run`, `diff`, `rollback`, `connect`, `doctor`, and `docs`. Each is a fixed sequence of registry actions, held as data, and adds no behavior of its own. Three process commands, `serve`, `runner`, and `stdio`, start a long-lived role and are not actions. Beside them, `completion` prints a script that completes commands and flags in a named shell, made from the same command tree; the program answers it itself, with no engine, and it is not an action ([decision 0266](../../decisions/0266-the-engines-log-says-each-start-and-stop-and-what-asked-and-engine-logs-reads-it-where-the-engine-runs.md)). The catalog lists what each shortcut does. A shortcut is offered only when every one of its steps is built: the command tree, its help, and its completions hold no other, and a word that is not offered is no command. Two more are defined, `bundle` and `migrate`, each the `version` action of its name; neither action is built, so neither is offered, and each is offered by itself once its action has a handler. `rollback`, the third, is offered since `version.rollback` was built ([decision 0470](../../decisions/0470-a-rollback-is-a-persons-act-and-moves-to-any-version-a-person-published.md)). `learn` is `capture.start` alone: it asks for a capture of the person's own use and gives the page where the person begins and ends it; `capture.stop` afterwards says how it ended and scouts what it found ([decision 0456](../../decisions/0456-the-first-release-leaves-out-what-its-first-hour-never-meets-and-a-shortcut-is-offered-only-when-built.md)).

## The command face, as an agent uses it

**Output.**

- With `--json`, or whenever output is not going to a terminal, a command prints exactly one JSON object to standard output. Text meant for people goes to standard error.
- Success: `{"ok": true, "action": ..., "result": ..., "warnings": [...], "next": {...}}`.
- Failure: `{"ok": false, "error": {"code": ..., "class": ..., "message": ..., "fix": ...}}`, using the failure classes and codes in the [technical reference](../../reference/technical-reference.md#command-output-contract).
- An authoring or admin action whose own part is done and whose remaining step is a person's act, such as a publish asked for, is a success with exit code 3: `ok: true`, and the result's `state` says what it waits on. A run that rests on a person, such as a write waiting for its approval, is `ok: false` with exit code 3 and its result: nothing was written. A call refused for want of a person is a failure with exit code 3 ([decision 0458](../../decisions/0458-an-answer-that-did-its-part-and-waits-for-a-person-is-ok.md)).
- `next` names the most useful following action and its arguments, so an agent that has read nothing else can still proceed.

**Exit codes.**

| Code | Meaning |
| --- | --- |
| 0 | Succeeded |
| 1 | The action failed; the error object says why |
| 2 | The command was malformed |
| 3 | A person is needed: sign-in, approval, or input |
| 4 | The engine could not be reached or started |

**Large results stay out of the context.** A snapshot, capture, trace, or diff is written to a file under `.anything2mcp/out/` in the project, with a name the engine chose. The command returns the path, the size, and a short summary. The agent reads the parts it needs with its own file tools. Defaults are compact: a screen snapshot is limited to roughly 2,000 tokens, with a flag to widen it and a cursor to page through it.

**No prompts.** When output is not a terminal, a command never waits for typed input. If a person is needed it returns exit code 3 and says exactly what the person must do.

**Help says what a command does to the world.** Help is generated from the registry. An action's help gives its usage, its summary, its effect, who may run it, and whether a person at this machine is asked; the help of an action that is not built says so on its first line, and every listing marks each verb that is not built. Help is wrapped to the terminal's width: `COLUMNS` when it is a whole number of 40 or more, else 80.

**Discovery on demand.** `anything2mcp action search` returns names and one-line summaries only. `anything2mcp docs <topic>` prints reference pages built into the binary, so file formats, verbs, and failure codes are available offline and only when asked for.

**Stable output.** Fields keep a fixed order, lists are sorted, and element references stay the same within one snapshot, so two identical commands give identical text.

## The MCP face, for agents without a shell

The build toolset lists at most 15 tools:

- the authoring tools of the build loop ([section 401](../4-building-tools/401-overlaying-tools-on-an-existing-system.md));
- `a2m_action_search`, `a2m_action_describe`, and `a2m_action_run`, which reach every other action in the registry without listing it;
- `a2m_draft_read` and `a2m_draft_write`, which stand in for a file system. A draft is validated and linted before it is written.

A built-in toolset never lists more tools than its cap: an action marked for it beyond the cap is reached through `a2m_action_run`. Large results come back as resource links, the MCP counterpart of the files above.

An agent with no shell also has no guidance file and no `docs` command, so the same material is offered through the protocol where the client supports it:

- **Server instructions** carry the handful of rules every caller needs.
- **Prompts** carry the build loop as a guided start: add a target, explore it, draft a read tool.
- **Resources** carry the built-in reference pages and the project's draft files.

All three are generated from the same sources as the guidance file and the `docs` command.

## The project folder

Target files live in a project folder: any directory holding an `anything2mcp.toml`. It should be its own private Git repository. A file handed to a pipeline as its source is put in the project's `inputs` folder and named from the project folder, as in `inputs/items.csv`.

```text
my-targets/
  anything2mcp.toml    # project settings: which targets, which environments
  AGENTS.md            # written by init: the build loop, the rules, a command list
  targets/
    example/           # one folder per target, laid out as in section 205
  .anything2mcp/       # local working data, ignored by Git; made by init
    engine             # the engine store the project is worked from
    out/               # snapshots, captures, traces, diffs
  .gitignore
```

- **Finding the project.** A command looks for `anything2mcp.toml` in the current directory and then in each parent; `--project` overrides. The path is turned into a checked path before any use ([section 502](../5-security/502-defending-against-a-manipulated-agent.md)).
- **One store for a project.** The first call from an engine whose store is on disk writes `.anything2mcp/engine`, naming that store; a call that names the project to another engine's store is refused whole, `project_of_another_store` ([decision 0445](../../decisions/0445-the-first-hours-faults-a-list-on-the-command-line-a-key-off-a-list-and-a-project-held-to-one-store.md)).
- **What is not in the project.** The store, the vault, and every session's live state live in the user's data directory, never in the project, so cloning or sharing a project never shares a session.
- **Real targets stay private.** This is where target files for real systems belong. They are never added to the Anything2MCP repository, and the project publishes no catalog of them ([decision 0058](../../decisions/0058-a-toolkit-for-developers-with-no-catalog-and-no-preferred-agent.md)).

## Drafts and versions

Files in the project are drafts. `version.publish` copies them into the store as an immutable, hashed version: one compiled target ([section 206](206-the-compiler-and-the-compiled-target.md)); a person publishes, never an agent. Normal callers run only published versions. `draft.try` and `test.run` run drafts, inside the sandbox, where writes go only to declared test records.

## The build loop as a visible state

Each target has a build state, and `target.status` (the `status` shortcut) reports it with the next action:

`added` → `signed_in` → `explored` → `drafted` → `tried` → `tested` → `published`

An agent that loses its place, or a new agent picking up someone else's work, asks for the status and continues. Two steps always need a person: signing in and approving a publish.

## The guidance file

`init` writes a short `AGENTS.md` into the project, plus the small pointer files that particular agents look for. It is kept under 150 lines and contains:

- the build loop and the status command;
- the rules: read-only exploration, test records only, no secrets in files, stop on anything unknown, never attempt to approve;
- the command list, one line each;
- how to fetch detail on demand with `anything2mcp docs`.

Everything longer stays in the built-in reference, so the guidance costs little context and cannot drift from the installed version.

## What an agent may and may not do while building

An agent may run every building action its role allows: probe, detect sign-in, explore, capture, infer, draft, lint, try, test, and request a publish. It cannot, through any face:

- approve a write or a publish;
- read a cookie, token, or password, since no action reads a secret back;
- make exploration send anything but reads;
- write to a record that is not a declared test record before a version is published;
- change a published version;
- run as another person: `session.end` cannot be used to enter a session;
- raise a protected limit or change a protected setting without the operating system's presence prompt.

[Section 222](222-front-doors-and-the-local-engine.md) says how far these hold when the agent has a shell on the same machine, and [section 502](../5-security/502-defending-against-a-manipulated-agent.md) what holds when the agent is steered.

## Rules for tools

These rules hold for every action and for every tool a target publishes. Several are taken from the REA project's written doctrine for tool design, the most careful treatment of the subject found ([research note 16](../../research/16-rea-methods.md)).

### Finding out what is there

| Action | Answers |
| --- | --- |
| `provider.list` | Every pack and provider: installed, enabled, ready, or what it lacks and how to get it |
| `provider.describe` | One provider's manifest: what it supplies, its effects and how strongly each is held, its requirements |
| `provider.enable`, `provider.disable` | Switch one on or off. On one machine, a protected setting where the provider starts processes or reaches a network |
| `component.list` | The outside programs providers need: found or not, at which path, with which digest, known or unverified |
| `discover.run` | Run the discoverers that suit a target's surfaces; returns findings ([section 218](218-discovery-and-findings.md)) |
| `finding.list`, `finding.describe` | Findings for a target, filtered by level, kind, or source |
| `unknown.list`, `unknown.settle` | The unknowns ledger; settling one requires evidence |
| `doctor.run` | Everything above, checked, with a fix for each problem |

These are ordinary actions, with all four faces.

### When to add an action or a tool

1. **Add one for a distinct outcome or a materially different authority.** Matching an outside interface function for function is not a reason.
2. **One shape per action.** An action never mixes discovery with change.
3. **Primitives first.** An action reports one reusable fact about one identified thing. A workflow is composed only after repeated use has shown the same sequence. Pipelines are the place for sequences, and they are declared in files.

### Descriptions

- The first 240 characters must be enough to choose the tool: what it does, on what, and what comes back.
- Effects, and the line between this tool and its nearest neighbor, come early.
- A description is written for choosing and for making a valid first call. It is not documentation.
- Text from a target never enters a description, or a tool's name, without a person reviewing it ([section 502](../5-security/502-defending-against-a-manipulated-agent.md)).

### Schemas

- Inputs are strict: no unknown fields, the target named explicitly. Flat, with about ten properties or fewer.
- What is advertised in a tool list may be a compact form of the schema, provided every difference is exact or wider. The full schema is what the server validates against, always.
- Output schemas are published and are not sent in a tool list by default. REA measured that complete output schemas were about 92% of its tool list by size. They are returned by `tool.describe`, and in the list for a client that asks.
- One to three example inputs, taken from recorded tests.

### Results

- Short by default: a summary, and a reference to the full result, which is kept.
- One shared way to page through a kept result, by offset, limit, and fields. A tool does not invent its own.
- When a result is cut, it says by which limit, and returns a continuation that is ready to call.
- Every result says how complete it is. Missing coverage is unknown, never absence.
- Anything that came from a target is marked untrusted.

### Limits

- Every limit is a named setting with a unit ([section 226](226-configuration.md)).
- A failure caused by a limit names the setting, its value, its bounds, and where it is changed.
- A fixed ceiling says that it is fixed, so that nobody goes looking for a setting.
- An agent cannot raise a protected limit. In this Anything2MCP differs from REA, where limits are editable through a tool.

### Failures

Every failure carries a class, a stable code, a plain sentence, and a next step, as the [technical reference](../../reference/technical-reference.md#failure-codes) lists them. Three rules go with it.

| Rule | Detail |
| --- | --- |
| Whether a retry is safe | Stated, per failure. Never implied by the class name |
| A fix is an instruction | "The file was not found" describes; "Pass a path inside an allowed root" repairs. Every failure carries the second kind |
| Malformed is not unresolvable | An input that breaks the schema, and a valid input that names something that does not exist, are different failures with different next steps. Only the first suggests reading the schema |

The list of every failure code is generated from the code that classifies them, and the documentation audit fails when the documents and the code disagree, as it does for failure classes.

### Progress and cancellation

- Progress is sent only to a caller that asked for it. It is a count that only rises. Percentages are not invented.
- Cancellation is one signal, the same from a command, an MCP client, or a program.
- A cancelled run says what was completed before it stopped, and what cleanup achieved, as separate facts ([section 204](204-supervising-subsystems.md)).

### Found tools become real tools

The `use` toolset lists few tools and finds the rest through search, calling them through one generic action ([section 221](221-the-tool-surface-agents-see.md)). Where a client supports notice that the tool list has changed, a tool found by search is added to that client's list, so that the client validates its arguments against the real schema. The generic `a2m_tool_call` stays for clients that do not, and every call is checked against the full schema either way.

### Proving that agents can use the tools

The usability gate of Phase 5: an agent with no prior knowledge reaches a first published read tool using only the guidance file, the status command, and `docs`. Its method:

- a real agent client, in a throwaway home directory, set up through the public installation path and nothing else;
- closed questions with one right answer, checked against a fixture and against what the tools actually returned;
- at least one task whose right answer is to call nothing;
- scores kept separately for choosing the tool, filling the arguments, recovering from a failure, and the final claim. A valid schema and good keywords do not show that a tool will be chosen.

Conformance is tested against the protocol with at least two unrelated clients, and no client is preferred ([decision 0058](../../decisions/0058-a-toolkit-for-developers-with-no-catalog-and-no-preferred-agent.md)).

## Speed and ease targets

- A command reaching a running engine adds no more than 30 ms.
- The usability gate above passes.
- Both are targets until measured.

## Open points

- **The build toolset's cap against the catalog.** Settled by [decision 0094](../../decisions/0094-the-action-layers-interface-as-building-it-settled-it.md): the cap limits what is listed, not what may be marked. A toolset lists the three `action.*` tools and then its marked actions in catalog order up to its cap; the rest are reached through `a2m_action_run`. Which of the 22 actions marked `build` deserve the twelve places is still to be chosen by use, and the catalog's order is what decides today.
- **Found tools on a revision with no per-connection lists.** The stateless 2026-07-28 revision of MCP has no per-connection tool list, so a tool found by search cannot be added to one client's list. Until a client can be told of a changed list without a session, the generic call is the route ([section 222](222-front-doors-and-the-local-engine.md)). Which clients support notice of a changed tool list well enough to rely on is also open.
- **Actions the catalog still lacks.** Starting a project stays without an action: the `init` shortcut is the client's, and writes the project's first files through `a2m-actions` ([decision 0164](../../decisions/0164-the-authoring-actions-served-through-the-engine.md)). Still lacking: exporting a toolset's description as an OpenAPI document; managing webhook destinations; and listing the open subsystems the supervisor holds. Each needs a row in the catalog.
- The size budget for a tool list, and for one tool's compact schema; and how compact schemas are derived from full ones mechanically, so that "exact or wider" is proven, not reviewed.
- Whether findings and unknowns are exposed as MCP resources as well as through actions.
- Whether the `engine.*` actions keep an MCP tool and a REST route at all, since they act on a process a remote caller cannot see.
- How a shortcut threads one action's output into the next without the client holding logic. Declared field mappings in the shortcut's data is the proposal.
- Where large results go when the caller is a remote program: a blob reference and a fetch route, most likely.
- How an operation's own input, which a compiled target carries as a JSON Schema document, is checked at the dispatcher. An action's input is checked by the schema type of `a2m-files`; a tool's input is checked by the engine against the compiled target's inputs.
